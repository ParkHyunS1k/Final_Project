## 2. 최대 리스크 — 안전고리에 positive 클래스가 없다

507의 안전고리 관련 클래스는 `WO-06`(미착용), `UA-01`(미체결) **둘 다 부정 상태 라벨**이다.
"안전고리"라는 물체 자체를 가리키는 클래스가 없다.

이것이 갖는 의미:

- **박스가 무엇을 감싸는지 모른다.** 작업자 전신이면 사람 단위 상태 분류에 가깝고, 하네스·고리 영역이면 부품 탐지에 가깝다. 어느 쪽이냐에 따라 모델 설계와 달성 가능한 성능이 완전히 달라진다.
- 체결된 정상 상태의 고리에는 라벨이 없을 가능성이 높다. 그러면 "체결 vs 미체결" 2클래스 학습이 불가능하고, **미체결 단일 클래스 탐지**만 가능하다.

> **Phase 1에서 이 문제를 먼저 검증한다. 검증 전에 대용량 원천 데이터를 받지 않는다.**

안전난간은 `SO-01`이 positive 클래스로 65,086개 있어 이 문제가 없다.

### 3.3 다운로드 명령

```bash
# 최초 1회
curl -o aihubshell https://api.aihub.or.kr/api/aihubshell.do
chmod +x aihubshell && sudo mv aihubshell /usr/local/bin/

# 파일 트리 확인
aihubshell -mode l -datasetkey 507

# 선택 다운로드 (filekey 콤마 구분)
aihubshell -aihubapikey $AIHUB_KEY -mode d -datasetkey 507 -filekey 68026,68027,68028,68029,68030,68031
```

`AIHUB_KEY`는 AI Hub 계정의 API 키다. 데이터셋별 **승인**이 선행되어야 한다.

## 4. 단계별 다운로드 계획

용량이 커질수록 되돌리기 어려우므로, 검증을 통과할 때만 다음 단계로 넘어간다.

### Phase 0 — 라벨 전량 (약 0.76 GB)

| 대상 | filekey |
|---|---|
| 507 Training 라벨 | 68026,68027,68028,68029,68030,68031 |
| 507 Validation 라벨 | 68020,68021,68022,68023,68024,68025 |
| 71407 추락 라벨 전량 | TL 487824~487843, VL 488050~488069 |

산출물:

1. **작업유형 × 클래스 인스턴스 교차표** — `SO-01`, `UC-01`, `UC-04`, `WO-06`, `UA-01`이 어느 작업유형에 몰려 있는지 실측
2. **`WO-06`/`UA-01` 박스 크기 분포** — 박스 면적이 `WO-01`(작업자)과 비슷하면 사람 단위 라벨, 훨씬 작으면 부품 단위 라벨. 2절 리스크를 이미지 없이 1차 판정
3. `WO-06`과 `UA-01`의 좌표 중복률 — 동일 인스턴스 가설 검증
4. `UC-01` vs `UC-04`, `UC-03` vs `UC-06` 중복 명칭의 실제 차이

**게이트: 산출물 1·2가 나오기 전에는 원천 데이터를 받지 않는다.**

### Phase 1 — 안전고리 시각 검증 (3 GB)

507 `TS_04_로프작업`(filekey 68016). 로프작업은 안전고리 체결이 필수인 작업이라 밀도가 가장 높을 것으로 기대되고, 3 GB로 가장 싸다.

산출물: `WO-06`/`UA-01` 박스를 실제로 잘라 본 판독 결과. 2절의 리스크를 확정한다.

**분기**

- 박스가 고리·하네스 영역 → 안전고리를 부품 클래스로 학습. 원안대로 진행
- 박스가 작업자 전신 → 안전고리는 **사람 단위 상태 분류**로 재설계. 아래 5절 B안 채택
- 라벨 품질이 쓸 수 없는 수준 → 안전난간만 진행하고 안전고리는 별도 라벨링 검토

### Phase 2 — 본 학습 데이터

Phase 0 통계로 확정하되, 현재 정보 기준 기본안은 다음과 같다.

**확정안 (65 GB)** — `scripts/download_aihub.sh phase2`

| 대상 | filekey | 용량 |
|---|---|---|
| 507 Validation 원천 **전량** | 68032, 68033, 68034, 68035, 68036, 68069 | 56 GB |
| 71407 추락 03·04·05 TS | 487713,487714,487715,487723,487724,487725 | 8 GB |
| 71407 추락 03·04·05 VS | 487939,487940,487941,487949,487950,487951 | 1.3 GB |

507은 **Validation 파티션을 우리 데이터 전량으로 쓰고 영상 단위로 재분할**한다.

근거: 507은 zip이 작업유형 단위라 클래스별 선택이 불가능하다. Validation 원천 56 GB가 **6개 작업유형을 모두 포함하는 최소 단위**이며 전체의 약 11%다. Training 원천 450 GB를 받는 것보다 압도적으로 효율적이고, 작업유형 편향도 없다.

11% 기준 클래스별 잔존 인스턴스 추정:

| 클래스 | 전체 | VS 추정 | 판단 |
|---|---|---|---|
| `SO-01` 안전난간 | 65,086 | 약 7,200 | 충분 |
| `UA-01` 안전고리 미체결 | 40,499 | 약 4,400 | 충분 |
| `UC-05`+`UC-08` 전도방지대 | 약 20,800 | 약 2,300 | 충분 |
| `UC-02` 작업발판 미설치 | 7,445 | 약 820 | **얇다** |

`UC-02`가 얇다. 9종 전체로 확장할 때 문제가 될 수 있으므로 Phase 0 교차표로 어느 작업유형에 몰려 있는지 확인하고, 해당 작업유형의 Training 원천을 선택 추가한다. 안전고리·안전난간 두 대상만 보면 문제없다.

**증량이 필요할 때** 507 `TS_01_개구부작업`(4 GB, 68011) + `TS_04_로프작업`(3 GB, 68016)을 먼저 추가한다. 싸고 대상 밀도가 높다.

> `TS_05_비계작업`(185 GB)은 **받지 않는다.** 같은 작업유형의 Validation 23 GB로 대체 가능하다.

## 5. 학습 클래스 설계

### A안 — 안전고리가 부품 단위 라벨인 경우 (Phase 1에서 확정)

| ID | 클래스 | 소스 |
|---|---|---|
| 0 | `guardrail` | 507 `SO-01` + 71407 `SO-01`, `SO-04`, `SO-06` |
| 1 | `hook_unfastened` | 507 `UA-01` (또는 `WO-06`, 중복 시 택1) |
| 2 | `worker` | 507 `WO-01` + 71407 `WO-01` |

### B안 — 안전고리가 사람 단위 라벨인 경우

탐지는 난간과 작업자만 하고, 안전고리는 작업자 박스에 대한 상태 속성으로 다룬다.

| ID | 클래스 | 소스 |
|---|---|---|
| 0 | `guardrail` | 위와 동일 |
| 1 | `worker_hook_fastened` | 507 `WO-01` 중 `UA-01` 미부여 |
| 2 | `worker_hook_unfastened` | 507 `UA-01` |

### 공통 원칙

- **`UC-01`/`UC-04`(안전난간 미설치)는 학습 클래스에 넣지 않는다.** 물체가 없는 상태에 박스를 그린 라벨이라 탐지 대상으로 부적합하다. `guardrail` 탐지 결과에 룰을 얹어 미설치를 판정하고, `UC-*`는 그 룰의 **평가 정답**으로만 쓴다.
- `worker`는 그 자체가 목적이 아니라 안전고리 판정의 앵커다.

- **프레임 단위 랜덤 분할 금지.** 507·71407 모두 동영상에서 프레임을 추출한 데이터다. 인접 프레임이 train과 test에 갈라져 들어가면 성능이 크게 부풀려진다. 반드시 **영상 ID 단위**로 분할한다.
  - 507 영상 ID: `H-210717_E01_E_WS-20_201` 형식 (파일명 끝 프레임 번호 제외)
  - 71407 영상 ID: `H-220609_G18_SO-42_001` 형식
- 비율 train 70 / val 15 / test 15, 작업유형별 층화
- 분할 스크립트와 seed를 저장소에 커밋
