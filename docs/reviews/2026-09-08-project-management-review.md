# ProjectMate 프로젝트 관리 방식 검토

검토일: 2026-09-08

검토 범위: README.md, CLAUDE.md, docs/features.md, docs/tools.md, docs/eval.md, eval/valset/README.md, Python 업무·에이전트·일정·문서 처리 구현, web/README.md와 데모 상태 관리. 음성 파일은 전사하지 않았으므로 검토에 포함하지 않았다. 외부 협업 도구에서 실제 팀이 운영하는 방식은 확인하지 않았다.

이번 검토에서는 기존 제품 코드와 정책 문서를 수정하지 않았다. 아래 정책·일정은 제안이며 확정된 운영 규칙이 아니다.

## 1. 결론

현재는 업무 변경 엔진, 일정 계산 엔진, 단기 완주 웹 데모가 각각 존재한다. 제품의 중심인 ‘상태 관측 → 병목 감지 → 복구안 승인 → 계획 갱신 → 결과 확인’은 아직 연결되어 있지 않다.

기존 문서는 대학생 팀플과 소형 모델 성능 실험에 맞춰져 있고, 최근 방향은 7~10일 완주 프로그램과 참여 보증금이다. 8주 개발 계획 자체가 10일짜리 서비스와 모순인 것은 아니다. 문제는 두 목표 사이의 우선순위와 공통 완료 기준이 정의되지 않은 점이다.

## 2. 현재 운영 모델: 설계와 구현 구분

| 영역 | 문서의 의도 | 확인한 구현 |
|---|---|---|
| 시작 | 공고·계획서에서 마감·결과물·업무 추출 | 공고 텍스트 추출 및 이미지/PDF 전사 경로 존재. 계획서→업무 생성은 데모에서 sample_plan.json 사용 |

| 완료 | 업무 done 처리 | 결과물 증빙·검수·완료 시각·환급 판단 구조 없음 |

| 개발 운영 | 8주 로드맵·4인 역할·주차별 종료 조건 | 상세 문서는 있으나 현재 실행 백로그·담당자·기한·증거를 묶은 별도 관리 문서는 확인되지 않음 |
| 품질 | 모델 정확도·CSR·실사용 지표 | 단위 테스트와 파일럿 기록 존재. 정식 평가 하네스는 없음 |

유지할 기반: 모델과 계산의 역할 분리, 프로젝트 범위 검사, 승인 전 제안 기록, 실행 로그, 제약 검증기, 테스트·개발 데이터 구분.

## 3. 우선순위별 개선

### P0 — 먼저 제품의 기준을 통일

- README: 타깃, 핵심 사용자 흐름, 구현 상태, 데모 한계를 최신 방향으로 정리한다.
- CLAUDE.md: 기존 소형 모델 실험 목적을 유지할지 별도 연구 과제로 둘지 명시하고 MVP 순서를 업데이트한다.
- docs/features.md: 대표 기능을 회의 제안에서 병목 복구로 재정의한다. 회의는 결정이 해결되지 않을 때의 수단으로 둔다.
- docs/eval.md: 제품의 완주 성과와 모델 실험 성과를 구분한다. 모델 실험을 삭제할 필요는 없다.
- 가격 예시는 확정 정책과 분리한다. 웹의 체크박스 환급 조건을 실제 정책으로 재사용하지 않는다.

완료 기준: 팀원 누구에게 물어도 ‘누구를 위한 제품인지, 첫 버전이 무엇을 하는지, 무엇을 하지 않는지’가 같다.

### P0 — 하나의 프로젝트 상태로 웹과 엔진 연결

첫 통합 범위는 프로젝트 하나에 한정한다.

1. 프로젝트·팀원·업무를 서버에서 조회한다.
2. 체크인에 완료 내용, 막힌 사유, 남은 예상시간을 기록한다.
3. 변경 시 같은 상태를 기준으로 일정과 위반을 다시 계산한다.
4. 복구 제안에 변경 전후, 근거, 영향을 받는 작업을 담는다.
5. 승인 시 계획을 검증하고 변경을 저장한다.
6. 새로고침·다른 팀원의 화면에서도 같은 결과를 읽는다.

서로 의존하는 복구안은 한 묶음으로 검증·적용해야 한다. 기존 ‘독립 업무는 부분 승인 가능’ 정책은 유지하되, 범위 삭제와 일정 변경이 함께 필요한 복구안에는 원자적인 적용 경계를 둔다. 제안 이후 체크인이나 가용시간이 바뀌면 오래된 안임을 알리고 다시 계산한다.

완료 기준: 체크인 → 복구안 → 승인 → 새로고침 후 동일 계획 확인이 샘플 문자열 없이 동작한다.

### P0 — 일정 계산의 전제를 짧은 스프린트에 맞추기

- 공강 비율 추정 대신 날짜별 본인 확정 가용시간을 우선한다. 입력 없음과 실제 가용시간 0을 구분한다.
- 처음의 예상 공수와 남은 예상 공수를 분리한다. 이미 수행한 시간을 재계획에 다시 배정하지 않는다.
- 외부 마감은 시각과 시간대까지 보관한다.
- 1시간짜리 선행·후행 업무를 무조건 다른 날에 놓지 않도록 당일 인계가 가능한 최소 시간 구간을 지원한다.
- 내부 목표일과 늦어도 끝내야 하는 시점을 구분한다. 역산 결과의 ‘최늦 착수일’을 곧바로 권장 착수일로 쓰지 않는다.
- 초기 MVP에서는 각 작업을 지나치게 세분화하기보다 반일~1일 내 검증 가능한 결과물 단위로 만든다.

완료 기준: 가용시간 0, 당일 인계, 오후 마감, 부분 완료 후 재계획 사례를 회귀 테스트로 통과한다.

### P1 — 회의 알림보다 병목 해결

기존 docs/features.md의 ‘2일 지연’, ‘주 1회 상한’, ‘7일 쿨다운’은 단기 스프린트에 그대로 적용하지 않는다.

운영 가설:
- 합의한 체크인 시점에 잔여 작업과 가용시간을 갱신한다.
- 후속 담당자가 실제로 대기 중이거나 마감 내 용량이 부족하면 결정 카드를 만든다.
- 동일 문제는 반복 알림 대신 같은 카드를 갱신한다.
- 비동기 결정으로 해결되지 않으면 짧은 회의를 제안한다.
- 저녁 1회 요약과 중요한 상태 변화 알림을 시작점으로 검증한다. 임계값은 사용자 응답과 방해 정도를 보고 조정한다.

완료 기준: 알림 발생률이 아니라, 제안 뒤 병목이 해소됐는지와 걸린 시간을 기록한다.

### P1 — 업무 완료와 검증된 결과를 분리

업무에는 최소한 완료 기준, 결과물 근거, 제출 시각, 검토 결과를 연결한다. 진행 상태는 todo/in_progress/blocked/review/done처럼 검토 단계를 둘 수 있다. 개인 작업을 먼저 끝낸 경우를 금지하기보다는 선행 업무 미완료를 경고하고 통합 검증을 별도로 한다.

프로젝트 완료는 작업 수의 비율만 보지 않는다. 처음 합의한 핵심 사용자 흐름이 실제로 동작하고 테스트·데모 근거가 있는지 확인한다. 범위 축소는 이전 약속과 변경 사유를 남겨 완료율을 인위적으로 높이는 것을 막는다.

완료 기준: 체크만 한 결과와 확인 가능한 결과물을 구분할 수 있다.

### P1 — 보증금은 개인 기여 기준과 변경 이력을 먼저 설계

결제 연동보다 참여 약속의 버전, 동의 시각, 개인 의무, 제출 근거, 중도 이탈 처리, 팀 사정으로 바뀐 목표, 운영자 검토와 이의제기 기록을 우선 정의한다.

프로젝트 전체 성공과 개인의 성실한 참여는 별개로 판단한다. 팀원 이탈 때문에 성실한 참가자의 보증금이 자동으로 사라지지 않도록 한다. 초기는 실제 돈 없이 판정 사례를 검토하고, 유료 운영 전에는 취소·환불 정책을 별도로 확정한다. 이는 법률 적합성 검토를 대신하는 문서가 아니다.

완료 기준: 팀원 이탈, 정상 완주, 성실한 기술 실패 사례에 대해 사람이 같은 근거로 일관되게 설명할 수 있다.

### P1 — 개발팀의 실행 백로그를 간결하게 운영

현재 저장소에는 장기 설계가 상세하지만 이번 스프린트의 담당자·일정·결정 사항을 모은 실행판은 보이지 않는다. 외부 도구를 안 쓴다는 뜻은 아니다.

새 시스템을 만들지 말고 기존 협업 도구 또는 docs/current-sprint.md 한 곳을 기준으로 삼는다. 각 항목에는 담당자, 다음 확인 시점, 선행 작업, 완료 기준, 확인 증거, 상태를 둔다. 실제 날짜는 팀원 가용시간 확인 후 정한다.

매일 짧게 완료·막힘·남은 시간을 공유하고, 중간에 통합 데모를 한다. 중요한 제품 결정은 이유와 함께 한 줄로 기록한다. 각 PR에서 구현과 해당 문서의 상태를 함께 갱신한다.

보조 정리: 현재 web/은 자체 Git 저장소이고 부모 저장소에서는 미추적 디렉터리다. Sites 소스 저장소라는 이유가 있으므로 무작정 .git을 삭제하지 말고, 별도 저장소로 관리할지 명시하고 팀의 체크아웃·재현 경로를 문서화한다. 설치 문서도 Windows 전용 명령과 현재 macOS 환경을 구분하고 재현할 의존성 버전을 기록한다.

## 4. 추가 검증으로 확인한 사례

기존 테스트는 통과하지만 다음은 현재 테스트 범위 밖의 사례다.

| 사례 | 실제 관측 | 영향 | 근거 |
|---|---|---|---|
| 7일 모두 24시간 busy, 주간 가용시간 14h | 매일 2h 배정 | 불가능한 용량을 가능한 것으로 계산 | server/scheduler/capacity.py:36 |
| 오늘 2h 가능, 각 1h인 A→B, 오늘 마감 | A를 어제로 배정하고 1일 초과로 표시 | 당일 순차 실행 가능한 일을 과도하게 지연 판정 | server/scheduler/backward.py:164,188 |
| 공고 마감 2026-09-17 15:00 | 추출 결과에는 time=15:00, milestone 저장에는 날짜만 존재 | 오후 마감 기준 검증 불가 | server/extract/bootstrap.py:120, server/db/schema.sql:35 |
| 확정된 마일스톤 없음 | DEPENDENCY_CYCLE 오류 코드 반환 | 날짜 확인이 필요한 상황을 의존 사이클로 잘못 안내 | server/scheduler/validate.py:44 |

두 번째 사례는 현재 일 단위 설계에서 나온 제약이며 범용 스케줄러가 모두 잘못됐다는 뜻은 아니다. 단기 스프린트에서는 이 제약을 개선해야 한다.

## 5. 제품 지표

모델 성능과 별도로 다음을 수집한다.

- 핵심 결과물의 기한 내 검증 완료율: 시작 기준과 합의된 변경 기준을 함께 기록.
- 병목 해소 시간: blocked 인지부터 해소 확인까지.
- 복구 제안 결과: 수락·수정·거절과 이후 실제 해소 여부.
- 일정 예측 오차: 예측 완료 시점과 검증 완료 시점의 차이.
- 관리 부담: 체크인·계획 검토에 쓰는 시간.
- 참여·보증금 판정 이견: 사람 검토로 바뀐 건수와 사유.

Tool 정확도, 인자 정확도, CSR 등 기존 기술 지표는 유지한다. 소규모 파일럿에서 완주율이 높다고 곧바로 에이전트의 인과적 효과라고 해석하지 않는다.

## 6. 다음 개발 스프린트 제안

이는 사용자의 서비스 이용 기간과 별개인 우리 개발팀의 작업 순서이며, 10일 내 가능 여부는 팀 가용시간 확인이 필요하다.

| 순서 | 작업 | 종료 조건 |
|---|---|---|
| 1 | 제품 범위·완료 정의·상태 기준 통일 | 최신 문서로 다음 작업을 선택할 수 있음 |
| 2 | 서버 상태와 웹 업무 조회·변경 연결 | 새로고침 후 상태 유지, 권한 범위 확인 |
| 3 | 날짜별 가용시간·남은 공수·시각 보존 | 위 경계 사례 검증 |
| 4 | 체크인 → 병목 감지 → 복구안 승인 | 실제 상태로 복구 전후 계산, 오래된 제안 차단 |
| 5 | 결과물 제출·검토 및 통합 데모 | 한 팀이 시작부터 결과 검증까지 실행 |

이번 범위에서 뒤로 둘 것: 실제 결제·환급 자동화, 모집·자동 매칭, 대규모 자체 모델 학습. 학업상 연구가 필수라면 별도 담당·일정으로 유지한다.
