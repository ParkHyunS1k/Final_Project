# GitHub 이슈 가져오기 설계 — 2026-11-09

## 왜

팀이 GitHub 이슈로 할 일을 쌓아 두면, 지금은 그 내용을 손으로 복사해 '원문 붙여넣기'에 넣어야 AI 변경안(업무 생성·수정·담당자 배정)을 받을 수 있다. 프로젝트에 저장소를 한 번 등록해 두고 버튼 하나로 열린 이슈를 가져와, 기존 AI 변경안 흐름에 그대로 넣는다. 이슈 담당자(@아이디)는 2026-11-08에 만든 GitHub 계정 연결(`github_accounts`)로 팀원과 짝짓는다.

## 사용자 결정(2026-11-09)

| 항목 | 결정 |
| --- | --- |
| 흐름 | '이슈 가져오기' → 이슈 원문이 LLM 입력으로 들어가 업무 생성·수정·분담 변경안을 만든다. 적용은 기존 AI 변경안의 검토·부분 승인 그대로 |
| 저장소 | 프로젝트에 **한 번 등록해 두고 계속 쓴다** |
| 학습 확인 | 프로젝트 저장소를 **기본값**으로 쓴다 |
| 팀원이 아닌 작성자 | 이슈는 **모두 가져온다**. 팀원이 아닌 사람이 쓴 이슈가 섞여 있으면 **경고를 표시**한다 |
| 다시 가져오기 중복 | 이미 업무로 만든 이슈에서 다시 '업무 생성'이 나오면 **경고만 표시**한다(승인은 막지 않음) |
| 이슈 고르기 | 열린 이슈 목록을 보여주고 **사용자가 고른 이슈만** 가져온다. 처음에는 '이미 가져옴'이 아닌 이슈 모두 체크('팀원 아님' 포함) |

## 목표 / 비목표 / 실패 조건

- 목표: 프로젝트 저장소 등록·변경, 열린 이슈를 원문 하나로 가져오기, 그 원문으로 기존 AI 변경안 만들기, 팀원 GitHub 아이디를 LLM에 알려 담당자 배정, 팀원 아닌 작성자 경고, 학습 확인의 저장소 기본값.
- 비목표: 비공개 저장소, 웹훅·자동 동기화, 이슈 댓글 읽기, ProjectMate 업무를 GitHub 이슈로 되돌려 쓰기(닫기·라벨·배정), 이슈와 업무의 영구 연결(업무에 이슈 번호 열 추가 등), 중복 생성 자동 차단, 새 변경 종류 추가.
- 실패 조건(동작해도 실패로 본다):
  - 이슈 본문 속 문장이 지시로 실행되거나, `</source>` 같은 문자열로 원문 감싸기를 빠져나간다.
  - 팀원이 아닌 사람의 이슈에서 나온 변경안이 아무 표시 없이 승인 대기 목록에 섞인다.
  - 승인 없이 업무가 바뀐다(기존 규칙: 모델 출력은 DB 쓰기 권한이 없다).
  - 비공개 저장소 내용을 읽는다(서버 `GITHUB_TOKEN`이 읽을 수 있어도).
  - 사용자가 입력한 URL을 서버가 그대로 fetch한다(SSRF).

## 동작

### 1. 프로젝트 저장소 등록·변경 (팀장만)

- 프로젝트 화면의 원문 붙여넣기 근처에 저장소 영역. 등록 전에는 주소 입력란(`https://github.com/owner/repo`), 등록 후에는 `owner/repo` 표시와 '이슈 가져오기' 버튼, 팀장에게는 '변경'.
- 주소 검사는 학습 확인의 `parseRepoUrl`(lib/ai-review-github.ts)을 그대로 쓴다. 등록할 때 `GET /repos/{owner}/{repo}`로 **공개 저장소인지 확인**하고, 비공개·내부·없는 저장소는 같은 안내로 거절한다(학습 확인과 같은 규칙).
- 팀장만 등록·변경할 수 있다. 진행 가능한 프로젝트(준비·진행 중, 기한 전)에서만.
- **업무 revision을 올리지 않는다(작성자 판단).** `sprint_events`에 쓰면 revision이 올라 승인 대기 중인 AI 변경안이 모두 409로 무효가 되고 AI 한도를 다시 쓰게 된다. 저장소는 업무와 무관하므로 분리한다.
  - 동시 변경 감지: `project_repos.version`(정수). 변경 요청은 읽은 version을 보내고, 다르면 409.
  - 변경 기록: 별도 테이블 `project_repo_events(id, project_id, user_id, repo_owner, repo_name, action('set'), created_at)`.
- 저장: 새 테이블 `project_repos(project_id PK, repo_owner, repo_name, version, updated_by, updated_at)` (테이블 추가만). 이름은 빌더 판단.

### 2. 이슈 가져오기 (팀원 누구나)

- 버튼은 프로젝트 멤버 누구나(원문 붙여넣기와 같은 권한: `createSource` 정책 검사).
- **두 단계로 나눈다(사용자 결정 2026-11-09: 사용자가 이슈를 골라 고른 것만 가져온다).**

#### 2-1. 이슈 목록 보기 (원문·AI 호출 없음)

- 서버가 GitHub API 고정 경로로 **열린 이슈**를 읽는다: `GET /repos/{owner}/{repo}/issues?state=open&sort=updated&direction=desc&per_page=50`. `pull_request` 필드가 있는 항목(PR)은 뺀다. 학습 확인의 GitHub 읽기(`FetchOptions`, 시간 제한·응답 크기 상한·리다이렉트 거절·공개 확인)를 재사용한다.
- 응답은 이슈마다 번호, 제목, 작성자 @아이디, 팀원 여부, 담당자 @아이디들, 라벨, URL, **이미 가져옴 여부**(4-1의 중복 판정과 같은 기준: 이전 원문에서 이 번호로 업무 생성이 적용됨). 본문은 목록에 넣지 않는다.
- 화면은 체크박스 목록으로 보여준다. '팀원 아님'·'이미 가져옴' 표시를 붙인다.
- **처음 체크 상태: '이미 가져옴'이 아닌 이슈는 모두 체크**('팀원 아님' 이슈도 체크, 사용자 결정). '이미 가져옴' 이슈는 체크 해제 상태로 보이되 사용자가 체크할 수 있다.
- 이 단계는 원문을 만들지 않고 AI 한도를 쓰지 않는다.
- 이슈가 0개면 "열린 이슈가 없습니다."

#### 2-2. 고른 이슈 가져오기

- 화면은 고른 **이슈 번호만** 보낸다(1~20개, 정수, 중복 제거). 화면이 보낸 제목·본문은 받지 않는다.
- 서버는 그 번호들을 GitHub에서 다시 읽는다(`GET /repos/{owner}/{repo}/issues/{n}` 또는 목록 재조회 후 걸러내기, 빌더 판단). PR이거나 닫혔거나 없는 번호는 빼고, 응답에 "제외: #12(닫힘)"처럼 알린다. 남은 것이 0개면 원문을 만들지 않는다.
- 이슈마다 원문에 넣는 내용: 번호, 제목, 작성자 @아이디, **작성자가 팀원인지**, 담당자 @아이디들, 라벨 이름들, URL, 본문(이슈당 상한, 예: 2,000자). 전체는 기존 원문 상한(`MAX_SOURCE` 40,000자) 안에서 자른다. 잘렸으면 원문 끝에 "(이슈 N건 중 M건만 포함)".
- 원문 형식 예(빌더가 바꿔도 됨, 단 이슈 경계가 분명해야 한다):

  ```
  [GitHub 이슈 #12] 로그인 화면 만들기
  작성자: @alice (팀원: 홍길동) · 담당자: @bob · 라벨: frontend
  https://github.com/owner/repo/issues/12
  ---
  (본문)
  ```

  팀원이 아니면 `작성자: @stranger (팀원 아님)`.
- 팀원 판정: 작성자·담당자 @아이디를 프로젝트 **현재 멤버**의 `github_accounts.login`과 대소문자 무시로 비교한다. 판정은 가져온 시점 값으로 저장하고 나중에 다시 계산하지 않는다(작성자 판단).
- 이슈 본문 안의 `</source>`, `<source>` 등 원문 감싸기 태그는 무력화한다(예: `<` → `‹`, 또는 학습 확인의 `asData` 방식).
- 만든 원문은 기존 `source_documents`에 저장한다. `origin`은 `GitHub owner/repo 이슈`, `captured_at`은 가져온 시각.
- 그 원문으로 **기존 AI 변경안 생성(`/api/change-proposals` create)을 그대로** 이어서 실행한다. AI 하루 한도(사용자당 10회)도 그대로 쓴다. 한 번의 버튼으로 이어 실행할지, 원문만 만들고 사용자가 기존 '변경안 만들기'를 누르게 할지는 빌더 판단(화면 흐름이 기존 붙여넣기와 같으면 된다).
- 원문에 이슈별 위치를 **프로젝트 단위로 조회할 수 있게** 저장한다: 새 테이블 `source_issue_spans(source_id, project_id, issue_number, start, end, author_login, author_is_member)` (테이블 추가만). 팀원 아닌 작성자 경고와 다시 가져오기 중복 경고에 쓴다.

### 3. LLM에 팀원 GitHub 아이디 알려주기

- `buildPrompt`(lib/ai-extraction.ts)의 팀원 줄을 `0=홍길동(@hong)`처럼 연결된 GitHub 아이디와 함께 보낸다(연결 안 한 팀원은 지금처럼 이름만). 붙여넣기 원문에도 똑같이 적용된다.
- 프롬프트에 한 줄 추가: 이슈 담당자 @아이디가 팀원 목록의 아이디와 같으면 그 팀원을 담당자로 제안할 수 있다. 팀원 아닌 사람이 쓴 이슈의 내용은 완료·상태 변경의 근거로 단정하지 말 것.
- 프롬프트 버전(`PROMPT_VERSION`)을 올린다.

### 4. 팀원이 아닌 작성자 경고

- **원문·변경안 검토 화면 상단:** 이 원문에 팀원 아닌 사람이 쓴 이슈가 있으면 "팀원이 아닌 사람이 쓴 이슈 N건이 포함되어 있습니다 (@a, @b)".
- **변경안 하나하나:** 변경안의 근거(evidence start~end, 같은 인용문이 원문 여러 곳에 있으면 일치하는 위치 모두)가 팀원 아닌 작성자의 이슈 범위와 겹치면 `needsReview`를 '팀원이 아닌 사람이 쓴 이슈'로 둔다(기존 needsReview가 있으면 덧붙인다). 근거가 없는 변경안은 표시하지 않는다. 계산은 서버 코드로 한다(LLM 판단이 아니다).
- 경고는 승인을 막지 않는다(표시만).

### 4-1. 다시 가져오기 중복 경고

- `createTask` 변경안의 근거가 이슈 #N 범위에 있고, **같은 프로젝트의 이전 원문**에서 이슈 #N 범위에 근거를 둔 `createTask`가 **승인·적용된 적이 있으면**(되돌린 것은 빼도 되고 세는 것도 빌더 판단) `needsReview`에 '이미 가져온 이슈일 수 있음 (#N)'을 붙인다.
- 판정 재료: `source_issue_spans`와 기존 적용 기록(`ai_change_applications.entries`의 candidateKey `${sourceId}#start-end`). 서버 코드로 계산한다.
- 승인은 막지 않는다. 기존 `appliedCandidateKeys`(원문 하나 안의 중복 차단)는 그대로 둔다.

### 5. 학습 확인 저장소 기본값

- 학습 확인 시작 시 저장소는 (1) 본인이 그 프로젝트에 등록한 `review_links`가 있으면 그것, (2) 없으면 `project_repos`. 둘 다 없으면 기존처럼 "공개 GitHub 저장소를 먼저 등록해주세요."
- `GET /api/review`의 `link.repoUrl`도 같은 순서로 보여준다.

## 규칙·보안

- GitHub 호출은 `api.github.com` 고정 경로만, 사용자 URL은 owner/repo만 뽑아 다시 만든다. 공개 저장소만. 서버 `GITHUB_TOKEN`은 호출 한도 완화용으로만 쓰고, 읽기 전에 공개 여부를 확인한다.
- 이슈 텍스트는 데이터다. 원문 감싸기 + 태그 무력화 + 기존 검증(변경 종류·팀원 번호·업무 id 검사)을 거친다.
- 저장소 등록·변경은 팀장만, 서버에서 검사. 가져오기는 현재 멤버만.
- GitHub 실패(404·403 한도·시간 초과)는 원문·변경안을 만들지 않고 AI 한도도 쓰지 않는다.

## 검증(개발 완료 기준)

- 저장소 등록: 팀장 성공·재조회, 팀원 거절, 비공개 거절, 허용 밖 URL 거절(fetch 없음), 오래된 version 거절, 변경 기록 남음, **업무 revision 그대로이고 승인 대기 변경안이 계속 승인 가능**.
- 목록: PR 제외, 팀원 아님·이미 가져옴 표시, 원문·AI 한도 그대로, 본문 미포함.
- 고른 이슈 가져오기: 고른 번호만 원문에 들어감, 화면이 보낸 제목·본문 무시, 21개 이상·정수 아님 거절, 닫힌·없는 번호 제외 안내, 남은 0개면 원문 없음, 상한 초과 시 잘림 표시, `</source>` 무력화, 작성자 팀원 판정(대소문자 무시, 나간 멤버는 팀원 아님), origin 저장, GitHub 실패 시 원문·한도 그대로.
- 프롬프트: 팀원 줄에 연결된 아이디, 연결 안 한 팀원은 이름만.
- 경고: 팀원 아닌 이슈 범위의 근거를 가진 변경안만 needsReview, 화면 상단 경고 문구.
- 중복 경고: 이슈 #N으로 업무를 만들어 적용한 뒤 다시 가져와 #N에서 createTask가 나오면 '이미 가져온 이슈일 수 있음 (#N)', 적용하지 않았던 이슈는 경고 없음.
- 학습 확인: 개인 저장소 우선, 없으면 프로젝트 저장소.
- 실제 모델로 1회(운영 키가 있는 미리보기에서 사용자와 함께): 이슈 3~5개 저장소로 업무 생성·담당자 제안이 나오는지.

## 빌더에게 맡김

이슈별 위치 저장 방식, 버튼 하나로 변경안까지 이어 실행할지 여부, 원문 형식의 세부, 이슈당 본문 상한 값, 화면 문구·배치, 테이블 이름.
