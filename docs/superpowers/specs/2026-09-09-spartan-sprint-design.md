# ProjectMate 집중 스프린트 설계

작성일: 2026-09-09. 제품 규칙은 사용자와의 Q1~Q25 인터뷰에서 합의했다. 이 문서는 **구현 전 설계 검토본**이며, 아래 기능이 이미 구현되었다는 뜻이 아니다.

기준 코드: `phs`, `d6cc356f9db596d5782d2001666c7f7a5830317c`.

## 1. 제품과 대상

포트폴리오가 시급한 취준생·대학생이 다른 일정 없이 7~10일 동안 소프트웨어 개발 프로젝트에 전념하도록 돕는 팀 작업 공간이다. 노션형 업무 관리에 고정 목표, 기한, AI 가이드, 마감 독촉을 결합한다.

AI는 사용자가 정한 목표를 달성할 방법과 업무 변경안을 제안한다. AI 제안을 따르는 것은 의무가 아니다. 완주는 처음 약속한 결과물이 기한 내 완성되었는지만으로 판정한다. 보고 횟수, AI 제안 수용 여부, 독촉 응답 여부는 완주 조건이 아니다.

## 2. 확정한 운영 규칙

| 항목 | 합의 |
|---|---|
| 팀 | 최소 2명. 혼자 준비할 수 있지만 단독으로 스프린트를 시작하지 못함 |
| 시작 | 최소 2명이 초대를 수락하고 목표에 동의한 뒤 시작 |
| 기간 | 7~10일 동안 전념. 시작 후 기한 연장 불가 |

| 가용시간 | 개인별 입력 없음. 전원 하루 8시간을 내부 계산의 초기 공통 가정으로 사용 |

| 적용 | 사용자가 변경안을 편집·선택·제외하고 승인한 내용만 반영 |
| 복구 | 승인한 변경은 권한과 현재 버전을 확인해 되돌릴 수 있음 |
| 진행 보고 | 하루 한 번 완료·남은 일·막힘을 안내. 대화 붙여넣기로 대체 가능. 누락은 완주 차단 사유가 아님 |
| 참여 중단 | 당사자가 알리고, 남은 팀 기준의 재배정·실행 변경안을 팀장이 검토 |
| 마감 이후 | 해당 스프린트의 업무 추가·수정·완료 처리 금지. 열람·내보내기는 허용 |
| 이월 | 자동 연장 및 다음 스프린트 이월 기능 없음 |
| 독촉 채널 | 이메일. 직접 독촉은 개인에게 전달 |
| 팀 공개 정보 | 지연 업무, 막힌 선행 작업, 남은 기한 등 객관적인 상태 |

업무를 나누거나 합치는 것으로 약속한 기능을 제거해서는 안 된다. 처음 약속에 포함된 기능은 부가 기능이라는 이유로 보류할 수 없다. 참여 중단이나 일정 위험도 목표 축소·기한 연장의 근거가 되지 않는다.

## 3. 준비, 시작, 종료

사용자 경험은 준비 → 진행 → 완주 또는 기한 종료 순서다. 준비 중에는 기획서를 붙여넣고 업무 초안을 검토할 수 있다. 준비 기간은 스프린트 기간을 소모하지 않는다.

진행 전에는 팀원이 최종 목표·결과물·완료 기준을 확인한다. 준비 중 이 내용이 바뀌면 이전 동의로 시작할 수 없다. 시작 시 합의한 내용을 별도로 보존하고 이후 일반 편집과 되돌리기 모두에서 변경을 막는다.

완주 확인 자료는 코드 저장소와 실행 방법, 핵심 기능 데모 또는 시연 영상, 팀원별 기여 내용이다. 배포 URL 자체를 모든 프로젝트의 필수 조건으로 삼지 않는다. 프로젝트별 결과물과 검증 방법은 시작 전에 합의하며, 팀장이 그 기준으로 확인한다. AI가 증빙의 진실성을 자동 보증하지 않는다.

체크리스트의 모든 행을 끝냈는지와 합의한 결과물을 달성했는지는 구분한다. 결과물별 근거와 확인 상태를 관리한다. 업무 수나 체크인 수를 채우는 것으로 완주를 대체하지 못한다.

서버는 마감 시점 이후 상태 변경을 거절한다. 화면 버튼만 숨기는 것으로 끝내지 않는다. 마감 시점의 결과를 보존하며, 미완주 프로젝트도 기존 자료를 읽고 내보낼 수 있다.

### 구현 제안 — 이번 문서의 검토 대상

- 준비 완료 후 팀장이 명시적으로 시작한다. 기존 최대 4명 제한은 이번 변경 범위에서 유지한다.
- 정확한 기간은 시작 시각부터 선택한 7·8·9·10일로 계산하는 방식을 제안한다. 저장은 UTC 시각, 화면과 이메일은 한국 시간으로 표시한다. 현재 코드의 마지막 날짜 18시 고정 규칙과는 다르므로 이 제안은 사용자 확정 규칙과 구분한다.
- 상태 이름은 `draft`, `active`, `completed`, `expired`로 구분한다. 시계 기준의 서버 검사를 우선하므로 종료 처리 작업이 늦어져도 쓰기가 열리지 않는다.

## 4. 권한과 변경 검토

담당자는 본인 업무의 진행 상태·남은 공수·완료 보고를 승인할 수 있다. 신규 업무 생성, 담당자 변경, 전체 실행 일정 변경은 팀장이 승인한다. 전체 프로젝트 완주 확인도 팀장이 수행한다. 여기서 실행 일정 변경은 개별 업무의 순서·마감 조정이며, 프로젝트 최종 기한을 바꾸는 권한은 아니다.

편집 가능한 AI 변경안과 실제 적용 가능한 권한을 구분한다. 사용자가 내용을 자유롭게 고쳐도 승인 시 서버가 권한, 현재 버전, 목표 고정, 프로젝트 마감을 다시 검사한다.

변경안에는 대상 업무, 변경 전후, 근거 원문 위치, 원문 사실인지 AI 추정인지, 확인이 필요한 항목을 표시한다. 오래된 원문이나 다른 업무의 발언을 자동 적용하지 않는다. 기존 업무와 연결할 근거가 부족하면 미정 상태로 검토하게 한다.

원문과 변경안은 분리해 저장한다. 원문 안의 명령문을 시스템 지시로 실행하지 않는다. 같은 입력을 다시 처리해도 승인된 업무가 중복 생성되지 않도록 원문 버전·변경안·적용 기록을 연결한다.

되돌리기는 기존 변경 기록을 지우지 않고 새로운 변경으로 남긴다. 이후 다른 사용자가 같은 값을 수정했다면 자동으로 덮어쓰지 않고 복구할 차이를 다시 검토하게 한다. 되돌리기로 목표 고정이나 종료 상태를 우회할 수 없다.

## 5. 계획과 가이드

개인별 가용시간 설정을 제거하고 하루 8시간이라는 동일한 공수 계산 가정으로 초기 실행안을 만든다. 이는 출퇴근 시각이나 실제 연속 근무를 강제하는 규칙이 아니다. 기존의 오전 9시부터 개인별 슬롯을 만드는 방식은 새 요구와 분리해 재설계한다.

AI의 예상 공수와 제안 일정은 추정임을 표시하고 승인받는다. 진행 기록이 쌓이면 새 추정과 변경안을 제안할 수 있지만, 승인 없이 업무 값을 바꾸거나 목표·최종 기한을 보정하지 않는다.

일정 위험이 생기면 업무 분담, 진행 순서, 구현 방법 변경을 제안한다. 달성 불가능한 상태를 가능하다고 표시하지 않는다. 기존 기능 보류 복구안은 이 설계에 맞지 않으며 제거 대상이다.

승인된 개별 업무 마감은 계산기가 매번 산출하는 예상 종료 시각과 구분해 저장한다. 일정 재계산만으로 독촉 기준 시각이 이동하지 않는다. 마감 변경은 승인된 업무 변경으로 처리하며 프로젝트 최종 기한을 넘길 수 없다.

## 6. 이메일 독촉 — 확정한 발송 조건

| 대상 | 발송 단계 | 수신자 | 발송 조건 |
|---|---|---|---|
| 개별 업무 | 마감 2시간 전, 1시간 전, 30분 전 | 현재 담당자 | 발송 직전에도 업무가 미완료이고 프로젝트가 진행 중 |
| 프로젝트 | 마감 48시간 전, 24시간 전, 2시간 전, 1시간 전, 30분 전 | 현재 팀원 각자 | 발송 직전에도 프로젝트가 미완주이고 진행 중 |

하루 3회나 오전 9시·오후 2시·오후 8시 같은 고정 시각 발송은 채택하지 않는다. 체크인 누락을 이유로 보내는 별도 이메일 일정도 이번 범위에 넣지 않는다. 매일 보고 안내와 마감 이메일은 별개의 기능이다.

완료된 업무의 남은 알림은 발송하지 않는다. 프로젝트가 완주 또는 기한 종료 상태면 모든 남은 독촉을 중단한다. 같은 수신자에게 같은 예정 시점의 개별 업무·프로젝트 알림이 겹치면 한 통으로 묶는다. 별개의 예정 시점 알림까지 임의로 합치거나 없애지는 않는다.

개별 알림에는 업무명, 승인된 마감, 남은 시간, 현재 기록 상태와 해당 업무 링크를 담는다. 프로젝트 알림에는 고정된 최종 기한, 미확인 필수 결과물, 미완료 업무를 담는다. 팀원 전체에게 보내는 경우에도 각자의 주소로 별도 발송하고 다른 사람의 이메일 주소를 노출하지 않는다.

문구는 단호하고 구체적으로 다음 행동을 요구한다. 보고가 없다는 이유만으로 일을 하지 않았다고 단정하지 않는다. AI 제안 거절이나 메일 무응답을 처벌하지 않는다. 완료 판정은 결과물 기준을 유지한다.

## 7. 알림 처리 구조 — 구현 제안

기존 웹 API·D1을 상태의 기준으로 유지하고 알림 예약, 발송 처리, 이메일 전송 연결을 분리한다. 아래는 기존 운영 환경에서 동작한다고 검증한 구현이 아니라, 구현 단계에서 충족해야 할 설계 계약이다.

1. 승인된 업무 마감, 담당자 변경, 프로젝트 시작·완료에 따라 유효한 발송 항목을 생성하거나 취소한다.
2. 정기 실행기가 도래한 항목을 조회한다. 브라우저가 열려 있어야 실행되는 타이머로 대체하지 않는다.
3. 항목을 원자적으로 확보한 뒤 최신 업무·프로젝트 상태, 현재 담당자·멤버십·수신 주소를 재확인한다.
4. 수신자와 예정 시점별로 유효한 항목을 묶고 이메일 전송 연결에 전달한다.
5. 항목과 발송 묶음의 상태, 시도 시각, 제공자 메시지 ID, 실패 원인을 기록한다.

### 필요한 데이터

- 업무: 승인된 `due_at`, 마감 변경 버전. 담당자 변경도 미발송 예약 재검토 대상이다.
- 연락처: 인증된 사용자 ID와 이메일의 연결. 요청 본문에 들어온 임의 주소를 인증된 연락처로 간주하지 않는다.
- 알림 항목: 프로젝트·대상 업무, 수신 사용자 ID, 마감 버전, 단계, 예정 시각, 처리 상태와 발송 묶음 ID.
- 발송 묶음: 수신자, 포함 항목, 안정적인 전송 식별자, 제공자 응답과 처리 상태.

### 시간, 중복, 실패 처리

- 예정 시각은 승인된 마감에서 해당 간격을 뺀 절대 시각이다. 마감 변경 시 이전 버전의 미발송 항목을 취소하고 새로 계산한다.
- 새 업무 생성 또는 마감 변경으로 이미 지난 단계는 소급 생성하지 않는다. 미래 단계만 예약한다.
- 처리 지연으로 여러 단계가 한꺼번에 도래했다면 같은 대상의 가장 최근 단계만 보내고 앞선 단계는 건너뛴 기록을 남긴다. 기한이 지난 대상은 보내지 않는다.
- 같은 논리적 알림 항목은 DB 고유성 제약과 원자적 확보로 중복 실행을 막는다. 같은 묶음의 재시도는 동일한 전송 식별자를 사용한다.
- 네트워크 응답이 불명확한 경우 DB 기록만으로 외부 이메일의 중복 전달까지 보장할 수 없다. 제공자의 멱등 전송·배송 조회 기능을 확인하고, 확인 없이 무조건 재발송하지 않는다.
- 재시도 때에도 현재 완료 상태와 수신 자격을 다시 확인한다. 이미 전송 제공자가 접수한 메일의 회수까지 보장하지 않는다.
- 전송 실패를 성공으로 기록하지 않는다. 실패 상태는 운영자가 확인할 수 있어야 하며, 사용자 업무 상태와 완주 판정을 바꾸지 않는다.

발송 주기의 정확도, 제공자 재시도 계약, 인증된 정기 실행 진입점은 운영 연결을 선택하면서 검증한다. 이메일 제공자와 운영 스케줄러는 아직 선정·설정하지 않았다. 현재 Sites에서 외부 정기 실행과 메일 발송이 지원된다고 가정하지 않는다. 운영 연결 전에는 가짜 전송기로 예약·취소·묶음·중복 처리만 검증하며 실제 사용자에게 메일을 보내지 않는다.

## 8. 현재 구현과의 차이

| 현재 코드에서 확인한 내용 | 필요한 변경 |
|---|---|
| 생성 시 날짜·기한을 저장하고 1명으로 생성 가능 | 준비와 시작 분리, 시작 시 최소 2명과 최신 목표 동의 검사 |
| 결과물·완료 기준이 프로젝트 텍스트로 저장됨 | 시작 당시 합의 내용 고정, 결과물별 증빙·확인 |
| 개인별 `sprint_capacity`와 오전 9시 슬롯 사용 | 개인 입력 제거, 공통 하루 8시간 기준 계산 |
| 복구안이 부가 업무를 `deferred`로 전환 | 목표 축소·보류·이월 제거, 목표를 유지하는 실행 변경안 |
| 완주 처리에 체크인 존재 검사 | 보고 횟수 조건 제거, 결과물 기준 판정 |
| `finished` 상태 쓰기 차단은 있지만 전체 변경의 마감 검사 없음 | 모든 업무 변경·승인·되돌리기에 공통 마감 검사 |
| 업무에 승인된 개별 마감 필드 없음 | 업무 마감 저장·승인·변경 버전 |
| 인증 요청에서 이메일을 읽지만 멤버에 수신 주소를 저장하지 않음 | 백그라운드 발송을 위한 인증된 연락처 연결 |
| 초대 링크는 생성하지만 이메일을 보내지 않음 | 독촉 이메일 전송 연결, 예약·중복·실패 기록 |
| 자유 문서 입력과 운영 AI 연결 없음 | 붙여넣기·원문 보존·변경안 검토·적용·되돌리기 |

주요 근거: `web/lib/projects.ts`, `web/lib/sprint.ts`, `web/lib/sprint-store.ts`, `web/app/api/sprint/route.ts`, `web/db/schema.ts`, `web/wrangler.local.jsonc`. 기존 마이그레이션을 수정하지 않고 새 마이그레이션으로 상태를 확장한다. 기존 프로젝트를 새 합의에 자동 동의한 것으로 처리하지 않는다.

## 9. 구현 단위와 검증 기준

이 문서는 전체 제품 계약이다. 한 번의 변경으로 모든 기능을 묶지 않고 다음 단위로 구현 계획을 나눈다.

1. **운영 규칙과 상태:** 준비·시작, 목표 고정, 결과물 확인, 공통 공수, 마감 후 읽기 전용. 1명 시작 거절, 합의 변경 후 재동의, 목표 수정 거절, 보고 없이 결과물로 완주, 마감 경계에서 모든 쓰기 거절을 검증한다.
2. **업무 마감과 이메일:** 승인된 업무 마감 및 연락처 저장, 예약, 정기 실행, 전송 기록. 가짜 시계·전송기로 세 개 업무 단계와 다섯 개 프로젝트 단계, 완료 시 중단, 담당자·마감 변경, 중복 실행, 묶음 발송, 지연 복구, 전송 실패를 검증한다. 실제 발송은 운영 연결과 테스트 수신 대상을 별도로 확인한 뒤 검증한다.
3. **AI 변경안:** 붙여넣기, 원문 사실·추정 구분, 기존 업무 매칭, 부분 승인·편집, 권한·버전 검사, 되돌리기. AI 출력만으로 DB를 바꾸지 않는지, 원문 재처리 중복 생성 방지, 오래된 제안 거절, 목표 고정 우회 방지를 검증한다.
4. **팀 파일럿:** 실제 두 계정으로 초대·목표 합의·업무 승인·진행 공유·결과물 확인을 점검한다. 관리 시간, 제안 수정량, 오승인과 복구, 알림 전달·반응, 기한 내 결과물 달성을 관찰한다.

기존 공개 원문 50건은 짧은 해석 평가용이다. 실제 이전 업무 상태와 기대 변경 결과가 없으므로 자동 반영 품질의 근거로 확대 해석하지 않는다. 원문을 변형하지 않은 별도 평가 버전과 사람 검토 라벨로 변경안 평가를 확장한다. 기존 데이터와 모델 결과는 덮어쓰지 않는다.

## 10. 이번 문서 작업의 범위

이번에는 설계와 구현 차이를 문서화한다. 애플리케이션 코드, 운영 DB, 사이트 배포, 메일 계정·제공자 설정, 정기 실행 등록은 변경하지 않는다. 결제·보증금·환급·매칭·외부 대화 자동 수집은 이 설계의 구현 범위가 아니다.

Q1~Q25에서 확정한 제품 규칙과 별도로, 이 문서의 구현 제안은 문서 검토 후 구현 계획으로 구체화한다.
