# A — Sprint Policy Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 준비와 진행을 분리하고, 합의한 결과물과 기한을 고정하며, 결과물만으로 완주를 판정한다.

**Architecture:** 기존 프로젝트·멤버·업무 저장 구조를 확장한다. 공통 정책 검사와 기존 `save`의 원자적 쓰기 경계를 통해 모든 변경 경로에서 같은 규칙을 적용한다.

**Tech Stack:** 기존 TypeScript, D1/SQLite, Drizzle, React, Node 테스트.

**Spec:** [집중 스프린트 설계](../specs/2026-09-09-spartan-sprint-design.md), [시작 문서](2026-09-09-claude-handoff.md).

## Global Constraints

- 목표 축소·기한 연장·자동 이월 금지. 개인 가용시간 입력 제거.
- 준비 중 목표 변경은 가능하나 이전 동의는 무효화한다. 시작한 목표는 되돌리기로도 바꿀 수 없다.
- 보고나 AI 제안 수용 여부를 완주 조건으로 사용하지 않는다.
- 현재 데이터와 기존 마이그레이션을 삭제·수정하지 않는다. 새 마이그레이션으로 확장한다.
- 본 문서는 코드 없는 계획이다. 각 작업에서 시작 문서의 실패 테스트 → 구현 → 검증 순서를 따른다.

| `web/lib/sprint-policy.ts` — 신규 | 유효한 프로젝트 상태와 `assertProjectMutationAllowed` |

| `web/lib/projects.ts`, `web/lib/sprint-store.ts` | 조회 모델, 준비/시작, 기존 원자적 저장 확장 |
| `web/app/api/projects/route.ts`, `web/app/api/sprint/route.ts` | 기존 요청 계약에 준비·합의·시작·결과물 확인 추가, 공통 권한 적용 |
| `web/lib/sprint.ts` | 개인 시간 슬롯을 공통 작업량 계산으로 교체 |

| `web/tests/sprint-policy.test.ts` — 신규, 기존 API/일정 테스트 | 정책·시간 경계·원자성·회귀 검증 |

별도 결과물 화면이 필요하면 `web/components/deliverable-review.tsx`로 분리한다. 일반적인 워크플로 프레임워크는 만들지 않는다. 내보내기는 기존 프로젝트 GET에 명시적인 export 조회 형식을 추가하는 안을 우선한다.

## A1. 상태·합의·결과물 저장 기반

- [ ] `draft`, `active`, `completed`, `expired`와 `startedAt`, `deadline`을 정의한다. 진행 상태가 DB에 남아 있어도 서버 시각이 마감에 도달하면 유효 상태는 종료다.
- [ ] `goalVersion`과 멤버의 `agreedGoalVersion`을 저장한다. 업무 변경용 `revision`과 분리한다.
- [ ] 결과물마다 안정적인 `deliverableId`를 부여한다. 시작 당시 목표·기능 범위·완료 기준·결과물 목록을 보존한다. 증빙과 팀장의 확인 이력은 고정 내용과 별도로 갱신한다.
- [ ] 기존 프로젝트를 새 규칙에 자동 동의한 것으로 변환하지 않는다. 기존 기록을 보존하는 호환 조회를 유지하고, 새 정책 적용은 명시적인 전환 또는 새 프로젝트로 구분한다. 기존 진행 프로젝트를 임의로 종료하지 않는다.
- [ ] 빈 DB와 기존 데이터가 있는 DB 모두에 새 마이그레이션을 적용해 기록·관계·식별자가 보존되는지 확인한다.

검증: 기존 1인 프로젝트를 불러와도 새 스프린트 시작 자격이 자동으로 생기지 않는다. 기존 결과물 텍스트와 업무 기록은 남는다. 새 결과물의 증빙을 수정해도 시작 합의 내용이 바뀌지 않는다.

## A2. 준비·동의·시작 및 공통 쓰기 검사

선행 조건: A1. 정확한 마감 계산은 시작 문서의 미확정 항목을 확인한 뒤 구현한다.

- [ ] 생성은 준비 상태로 저장한다. 팀장은 준비 중 목표·결과물·완료 기준을 편집하고, 멤버는 최신 버전에 동의한다. 변경 후 모든 멤버에게 재동의 필요 상태를 표시한다.
- [ ] 시작 시 팀장 권한, 실제 가입한 최소 2명, 현재 멤버 전원의 최신 목표 동의, 선택한 7~10일 기간을 한 번에 검사한다. 초대만 보낸 사람은 가입 인원으로 세지 않는다.
- [ ] 시작과 목표 스냅샷·확정 기한 저장을 원자적으로 처리한다. 중복 시작은 기한을 다시 계산하지 않는다. 진행 중 참여자는 고정 목표에 동의해야 하며 목표를 다시 열지 않는다.
- [ ] `assertProjectMutationAllowed`를 모든 사용자 변경 진입점에 연결한다. 팀원은 본인 업무 상태·남은 공수·완료 보고, 팀장은 생성·담당 변경·실행 일정·결과물 확인을 처리한다.
- [ ] `save`의 실제 쓰기 조건에도 현재 상태·기한·예상 revision 검사를 둔다. 요청 시작 시각의 검사만으로 기한을 넘긴 쓰기가 성공해서는 안 된다. 검사 실패 시 업무·이력·관련 쓰기는 함께 취소한다.
- [ ] 초대 생성·수락·취소, 체크인, 참여 중단 보고, 향후 AI 승인·되돌리기까지 정책 적용 목록을 작성한다. 마감 후 사용자 변경은 거절하고 조회·내보내기는 허용한다. 내부 종료/알림 처리 기록은 업무 편집 권한과 분리한다.

검증 상황:

| 입력/상황 | 기대 결과 |
|---|---|
| 1명 가입 또는 2명 중 1명만 최신 목표 동의 | 시작 거절, 기간 미소모 |
| 전원 동의 직후 팀장이 목표 편집 | 이전 동의로 시작 거절 |
| 두 요청이 동시에 시작 | 한 시작 시각·한 기한만 확정 |
| 일반 편집으로 시작 후 목표/최종 기한 변경 | 팀장도 거절 |
| 마감 1초 전 검사, 마감 후 실제 저장 | 저장 거절, 부분 변경 없음 |
| 서버 시각이 정확히 마감과 같음 | 변경 거절 |
| 다른 멤버의 업무 완료 요청 | 거절, 상태 유지 |

## A3. 결과물 기반 완주·읽기 전용 내보내기

- [ ] 고정 결과물별 증빙과 팀장 확인을 연결한다. 저장소·실행 방법, 데모 또는 영상, 팀원별 기여를 확인할 수 있게 한다. 프로젝트에서 별도 합의하지 않은 배포 URL을 일괄 강제하지 않는다.
- [ ] 기존 완주 조건의 체크인 존재·최소 업무 수·모든 업무 행 완료 검사를 결과물 충족 검사로 대체한다. 팀장의 확인은 사람의 판단이며 AI 자동 보증으로 표시하지 않는다.
- [ ] 완주 저장은 마감 전, 팀장 권한, 고정 결과물 전체 확인, 최신 버전을 원자적으로 검사한다. 완료 상태는 이후 일반 변경을 막는다.
- [ ] 멤버만 읽을 수 있는 내보내기에 시작 합의, 결과물 증빙·확인, 업무, 변경 이력을 포함한다. 다른 멤버의 이메일·인증 정보는 포함하지 않는다.

검증: 체크인이 0건이어도 원래 결과물을 모두 확인하면 완주 가능하다. 업무가 전부 완료여도 필수 결과물 하나가 미확인이면 거절한다. 결과물과 무관한 미완료 관리 업무가 결과물 완주를 막지 않는다. 마감 후 증빙을 추가해서 소급 완주할 수 없다. 미완주 종료 프로젝트도 멤버는 내보낼 수 있고 비멤버는 거절된다.

## A4. 공통 공수와 목표를 유지하는 가이드

- [ ] 개인별 가용시간 입력·저장 API를 새 정책에서 제거한다. 기존 개인별 9시 시작 슬롯 계산을 그대로 사용하지 않는다.
- [ ] 전원 하루 8시간을 기본 작업량으로 사용하는 단순 모델을 명시한다. 날짜별 작업량, 남은 기간의 일수 환산, 의존 관계 및 한 담당자의 중복 배정을 어떻게 계산하는지 문서와 테스트로 고정한다. 실제 근무시간 기록으로 해석하지 않는다.
- [ ] 예상 종료와 승인된 업무 마감은 별개로 유지한다. B 전에는 예상치를 확정 마감처럼 저장하거나 표시하지 않는다.
- [ ] `optional`/`deferred` 기반 기능 보류 복구안을 새 정책에서 차단한다. 재배정·진행 순서·구현 방법 변경을 가이드로 제공하되 필수 결과물을 삭제하지 않는다.
- [ ] 참여 중단은 당사자가 보고하고 팀장이 남은 팀 기준 변경안을 검토하게 한다. 개인별 시간 입력을 다시 만들거나 자동으로 담당자를 바꾸지 않는다.
- [ ] 하루 한 번 완료·남은 일·막힘을 정리할 안내를 제공한다. 미응답은 실패 판정이나 별도 이메일 사유로 사용하지 않는다.

검증: 같은 조건의 두 멤버는 같은 공수 가정을 적용받는다. 선행 업무보다 후행 업무가 먼저 끝나는 제안을 만들지 않는다. 공수가 남은 예산을 초과하면 위험을 표시하며 목표를 줄이거나 가능하다고 위장하지 않는다. 참여 중단 보고만으로 배정이나 최종 기한이 바뀌지 않는다.

## A5. 화면·회귀·문서 마무리

- [ ] 준비 화면에 인원·동의 상태, 진행 화면에 고정 목표·기한·결과물 확인, 종료 화면에 읽기 전용 사유·내보내기를 표시한다.
- [ ] 기능 보류·개인 시간·이월 버튼을 제거하고 오래된 직접 API 요청도 거절되는지 확인한다. 노션형 작업 공간의 기존 탐색·표·보드 흐름은 유지한다.
- [ ] 새 테스트를 `web/package.json`에 등록하고 전체 회귀·타입·관련 린트·빌드를 실행한다. 기존 테스트 중 이전 정책을 단정한 기대값은 변경 근거를 기록한다.
- [ ] 실제 두 계정으로 준비 → 목표 변경 → 재동의 → 시작 → 결과물 확인 → 완주를 검증한다. 가짜 시계 테스트로 기한 종료 흐름을 별도로 확인한다.
- [ ] 구현과 일치하도록 `docs/current-sprint.md`, README, 오래된 규칙이 있는 CLAUDE.md를 갱신한다. 문서만 보고 구현 완료를 판단하지 않는다.

인계 결과: B·C가 재사용할 정책 검사·원자적 저장·상태·결과물 계약, 실행한 검증 결과, 기존 데이터 호환 방식, 남은 제약을 기록한다.
