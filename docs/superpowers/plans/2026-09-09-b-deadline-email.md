# B — Deadline Email Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 승인된 마감에 따라 미완료 업무와 프로젝트의 독촉 이메일을 예약하고, 최신 상태 확인 후 중복을 억제해 발송한다.

**Architecture:** D1의 업무 마감·연락처·예약·발송 기록을 기준으로 독립 실행기가 처리한다. 외부 전송은 별도 어댑터이며 업무 상태를 수정하지 않는다.

**Tech Stack:** 현재 웹/D1, Node 가짜 시계·전송 테스트. 메일 제공자와 정기 실행 환경은 B4에서 확인한다.

**Spec:** [집중 스프린트 설계](../specs/2026-09-09-spartan-sprint-design.md), [시작 문서](2026-09-09-claude-handoff.md).

## Global Constraints

- A의 상태·권한·원자적 저장 계약에 의존한다. 브라우저가 닫혀도 작동해야 한다.
- 업무는 2시간·1시간·30분 전, 프로젝트는 48시간·24시간·2시간·1시간·30분 전이다.
- 완료/종료 후 미래 독촉을 중단한다. 승인되지 않은 원문 보고는 완료 상태가 아니다.
- 같은 수신자·동일한 예정 시각의 알림만 합친다. 별도 정시·체크인 이메일은 추가하지 않는다.
- 제공자와 실제 테스트 수신자가 확인되기 전에는 가짜 전송으로 검증한다.

| `web/lib/projects.ts`, `web/lib/sprint-store.ts`, 기존 API | 인증 연락처와 업무 마감 변경의 저장·검사 |

| `web/lib/reminder-dispatch.ts` — 신규 | 최신 상태 확인, 묶음 구성, 전송·결과 연결 |

정기 실행 진입 파일은 B4에서 지원 환경 확인 후 결정한다. 인증된 외부 실행기를 선택할 경우 `web/app/api/internal/reminders/route.ts`를 사용할 수 있다. 지원 여부를 확인하기 전에 경로만 만들고 운영 연결 완료로 처리하지 않는다.

## B1. 승인된 업무 마감과 연락처

- [ ] 업무에 `dueAt`과 `deadlineVersion`을 추가한다. `dueAt`은 UTC 절대 시각으로 저장하고 화면·메일은 한국 시간으로 표시한다. 예상 종료와 구분한다.
- [ ] 팀장의 명시적인 편집/승인만 마감을 확정·변경하게 한다. 최종 프로젝트 기한을 초과하는 마감은 거절한다. 준비 중 미정 마감은 허용하되 독촉이 예약되지 않음을 표시한다.
- [ ] 인증 계층이 제공한 사용자 ID·이메일을 연결한다. 초대 주소나 임의 요청 본문 주소를 인증된 연락처로 승격하지 않는다. 이메일이 없으면 발송 불가 상태를 기록하고 수신 주소를 추측하지 않는다.
- [ ] 승인된 마감·담당자 변경, 완료·재개, 프로젝트 시작·완주가 예약 갱신과 같은 원자적 변경에 참여하도록 연결한다. 과거 발송 기록은 삭제하지 않는다.
- [ ] 담당 변경 시 이전 담당자의 미발송 항목을 취소한다. 새 담당자에게 미래 단계만 배정한다. 동일 마감에 담당자가 바뀌었다 돌아와도 이미 보낸 단계가 다시 발송되지 않도록 고유성을 정의한다.

검증: 일정 예상치 재계산은 `dueAt`을 바꾸지 않는다. 팀원의 무권한 마감 변경은 거절된다. 연락처 없는 팀원을 다른 사람 이메일로 대체하지 않는다. 업무 변경 저장이 실패하면 예약만 바뀌는 부분 성공이 없다.

## B2. 예약과 시간 경계

- [ ] 예약 항목에 프로젝트/업무, 수신 사용자, 마감 버전, 단계, 예정 시각, 처리 상태, 묶음 식별자를 저장한다. 논리적으로 같은 항목의 중복 생성을 DB 제약으로 막는다.
- [ ] 새 생성·마감 변경 시 과거 단계는 만들지 않고 미래 단계만 예약한다. 시각이 정확히 현재와 같은 단계는 도래한 단계로 처리하는 경계를 테스트로 고정한다.
- [ ] 기존 예약 처리 지연으로 여러 단계가 밀렸다면 같은 대상의 가장 최근 도래 단계만 처리하고 앞선 단계는 건너뛴 사유를 남긴다. 대상 마감 이후에는 보내지 않는다.
- [ ] 업무 완료·프로젝트 완주/종료 시 남은 예약을 취소한다. 재개 가능 기간에 업무가 재개되더라도 지난 단계를 소급 발송하지 않는다.

필수 시계 예시:

| 상황 | 기대 예약/처리 |
|---|---|
| 업무 마감 2026-09-20 18:00 KST | 같은 날 16:00, 17:00, 17:30 |
| 프로젝트 마감 2026-09-20 18:00 KST | 9/18 18:00, 9/19 18:00, 9/20 16:00·17:00·17:30 |
| 9/20 16:30에 업무 마감을 18:00으로 새 확정 | 17:00·17:30만 생성 |
| 기존 16:00·17:00 예약을 실행기 장애로 17:20에 처리 | 17:00 단계만 처리, 16:00은 건너뜀 |
| 위 항목을 18:00 이후 처리 | 발송 없음 |
| 완료 후 미래 예약 처리 | 발송 없음 |

## B3. 확보·묶음·재시도·최신 상태

- [ ] 병렬 실행기가 같은 항목을 가져가지 못하도록 원자적 확보와 만료 가능한 처리 소유권을 둔다. 영구 잠금과 무조건 재시도 둘 다 피한다.
- [ ] 수신 사용자와 동일한 절대 예정 시각을 기준으로 묶음을 한 번 확정한다. 같은 시점 업무 여러 건과 프로젝트 알림은 한 통에 포함한다. 병렬 실행기가 항목을 나누어 별도 메일을 만들지 못하도록 묶음 경계에도 고유성과 원자적 확보를 적용한다.
- [ ] 전송 직전에 프로젝트 유효 상태, 업무 완료 여부, 승인 마감 버전, 현재 담당자·멤버십·연락처를 다시 읽는다. 무효 항목을 제외하고 빈 묶음은 보내지 않는다.
- [ ] 묶음에 안정적인 전송 식별자, 포함 항목, 시도 시각, 제공자 메시지 ID, 결과·실패 이유를 남긴다. 재시도는 동일 식별자를 쓴다.
- [ ] 제공자가 수신했는지 불명확한 응답은 별도 상태로 남긴다. 제공자의 멱등 전송 또는 조회 계약으로 확인한 뒤 재시도한다. DB만으로 외부 메일의 정확히 한 번 전달을 보장한다고 설명하지 않는다.
- [ ] 장애 중 회복 및 재시도 때도 상태·기한을 재검사한다. 발송 직후 완료되는 경쟁에서는 제공자가 이미 접수한 메일을 회수할 수 없음을 운영 문서에 명시한다.

검증: 실행기 두 개 동시 실행, 확보 후 프로세스 중단, DB 결과 기록 실패, 제공자 접수 후 응답 유실, 확실한 전송 거절, 재시도 전 업무 완료·담당 변경을 각각 검증한다. 전송 실패는 업무나 완주 상태를 변경하지 않는다. 서로 다른 예정 시각은 처리 시각이 같아졌다는 이유만으로 합치지 않는다.

## B4. 제공자와 실제 정기 실행 연결

- [ ] 현재 Sites/Workers 공식 문서와 프로젝트 설정으로 예약 실행 지원 방식을 확인한다. 기존 `vinext/server/fetch-handler`가 예약 이벤트를 처리한다고 가정하지 않는다. `.openai/hosting.json`은 임의로 덮어쓰지 않는다.
- [ ] 가능한 방식 중 최소 구성 하나를 고르고 실행 간격·예상 지연·중단 시 복구를 기록한다. 권장 목표는 1분 단위 확인이며 제공자 지원 범위와 실제 메일 전달 지연을 구분한다.
- [ ] 외부 HTTP 실행기를 쓴다면 서버 비밀값 등 제공 환경의 인증 방식으로 보호한다. 일반 사용자 세션이나 위조 플랫폼 사용자 헤더로 배치 작업을 실행하지 않는다. 무인증 호출·다른 프로젝트 지정 우회를 테스트한다.
- [ ] 사용자에게 사용 가능한 메일 제공자·발신 도메인·자격 정보와 테스트 수신자를 확인한다. 비용 발생·가입·운영 발송을 임의로 시작하지 않는다. 비밀값을 저장소·로그·UI에 남기지 않는다.
- [ ] 모의 전송 전체 통과 후 확인된 테스트 주소로 실제 이메일을 검증한다. 브라우저를 닫아도 실행되고 한국 시간·링크·발신자·제공자 기록이 맞는지 확인한다.

외부 설정이 없으면 B1~B3과 모의 전송은 완료할 수 있다. 이때 B4는 운영 연결 대기로 남기고 이메일 기능 전체를 운영 완료로 표시하지 않는다.

## B5. 문구와 사용자 흐름 검증

- [ ] 업무 메일에는 업무명·승인 마감·남은 시간·현재 기록 상태·해당 업무 링크를 넣는다. 프로젝트 메일에는 최종 기한·미확인 필수 결과물·미완료 업무를 넣는다.
- [ ] 사람마다 개별 발송하고 다른 팀원의 이메일을 노출하지 않는다. 메일 링크를 연 뒤에도 기존 멤버십 인증을 요구한다.
- [ ] 단호하게 다음 행동을 안내하되 보고 누락을 실제 미작업으로 단정하지 않는다. AI 거절·메일 무응답을 처벌하는 상태를 만들지 않는다.
- [ ] 팀 화면에는 지연·막힘·남은 기한을 객관적으로 표시한다. 별도 관리자 제품을 만들지 말고 운영자가 기존 로그/저장 기록에서 실패와 미확정 전송을 확인할 수 있게 한다.
- [ ] 새 테스트를 npm 실행 대상에 등록하고 A 회귀, 타입·관련 린트·빌드를 확인한다. 실제 전송 검증 여부와 운영 연결 절차를 문서화한다.

인계 결과: C가 마감 변경을 승인할 때 호출할 저장·예약 계약, 전송 상태 정의, 검증한 시간 사례, 운영 설정과 미완료 항목을 기록한다.
