# ProjectMate Claude Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 사용자가 승인한 집중 스프린트 규칙, 이메일 독촉, AI 변경안 검토 흐름을 현재 ProjectMate 웹에 구현한다.

**Architecture:** 기존 `web/`의 Workers 호환 API와 D1을 기준 상태로 유지한다. 운영 규칙을 먼저 고정한 뒤 업무 마감·이메일, 원문·AI 변경안 순서로 연결한다. 알림 실행과 모델 호출은 서버의 권한·목표·기한 검사를 우회하지 못한다.

**Tech Stack:** 현재 React 19·TypeScript·vinext/Vite·Cloudflare Workers 호환 환경, D1/SQLite, Drizzle, Node 내장 테스트. 제공자 추가 전에 기존 버전과 실행 환경을 확인한다.

**Spec:** [집중 스프린트 설계](../specs/2026-09-09-spartan-sprint-design.md).

## Global Constraints

- 포트폴리오가 시급한 취준생·대학생이 다른 일정 없이 7~10일 동안 소프트웨어 개발 프로젝트에 전념하도록 돕는 팀 작업 공간이다.
- 최소 2명. 혼자 준비할 수 있지만 단독으로 스프린트를 시작하지 못함.
- 시작 시 합의한 결과물, 기능 범위, 완료 기준 변경 불가.
- 시작 후 기한 연장 불가.
- 개인별 입력 없음. 전원 하루 8시간을 내부 계산의 초기 공통 가정으로 사용.
- 사용자가 변경안을 편집·선택·제외하고 승인한 내용만 반영.
- 보고 횟수, AI 제안 수용 여부, 독촉 응답 여부는 완주 조건이 아니다.
- 마감 이후 해당 스프린트의 업무 추가·수정·완료 처리 금지. 열람·내보내기는 허용.
- 자동 연장 및 다음 스프린트 이월 기능 없음.
- 개별 업무 알림: 2시간·1시간·30분 전. 프로젝트 알림: 48시간·24시간·2시간·1시간·30분 전.

## 클로드에게 전달할 작업 지시

설계 문서와 이 시작 문서를 먼저 읽고 A → B → C 순서로 구현한다. 이 문서 작성 단계에서는 애플리케이션 코드나 테스트 코드를 생성하지 않았다. 실행 담당자인 클로드가 각 작업의 실패 조건을 테스트로 작성하고 구현한다.

사용자 합의와 다른 예전 기획을 되살리지 않는다. 특히 목표 축소, 부가 기능 보류로 완주 처리, 마감 연장, 개인별 가용시간 입력, 체크인 누락에 따른 미완주 판정을 구현하지 않는다. AI는 가이드이며 사용자의 최종 선택을 대신하지 않는다.

각 단계는 독립적으로 검토 가능한 변경으로 마무리한다. 문서 예시만 넣고 실제 상태·권한·저장을 연결하지 않은 채 완료로 보고하지 않는다. 모의 전송/모의 모델 검증과 실제 운영 연결 검증을 구분한다.

## 착수 전에 처리할 기술 결정

아래는 제품 규칙을 다시 묻는 항목이 아니다. 사용자가 확정하지 않은 기술/시간 해석만 최소한으로 확인한다. 영향을 받지 않는 다른 작업은 진행할 수 있다.

| 결정 | 현재 상태 | 실행 담당자의 처리 |
|---|---|---|
| 정확한 프로젝트 마감 계산 | 기존 코드는 마지막 날짜 18시. 설계서는 실제 시작 시각 + 선택한 일수를 제안했지만 사용자가 별도로 확정하지 않음 | A2의 시작 시각·알림 달력을 확정하기 전에 이 차이만 사용자에게 확인. 시작 전 2인 동의와 시작 후 기한 고정은 재질문하지 않음 |
| 시간당 슬롯과 하루 8시간의 환산 | 사용자 합의는 공통 계산 가정이며 출퇴근 시간대 지정이 아님 | A4에서 날짜별 공통 작업량 모델을 제시. 오전 9시 슬롯을 그대로 숨겨서 사용하는 방식 금지 |
| 이메일 전송 제공자·발신 주소 | 미선정 | B4에서 실제 사용 가능한 서비스·발신 도메인·자격 정보를 확인. 임의 가입·결제 금지. 자격 정보가 없으면 모의 전송 검증까지 진행하고 운영 발송 미완료로 표시 |
| 정기 실행 환경 | 현재 앱에 등록된 실행기 없음 | B4에서 Sites/Workers의 현재 공식 지원 방식을 확인. 브라우저 타이머나 사용자 인증 헤더 위조로 대체하지 않음 |
| 운영 모델 제공자·인증·예산 | Codex CLI 비교 실험만 있음 | C2에서 사용자에게 허용된 운영 모델 연결을 확인. 기존 CLI 평가 스크립트를 웹 요청 처리기로 가져오지 않음 |

기존 최대 4명 제한, 새 파일·함수 이름, 상태 이름은 이 계획의 구현 제안이다. 기존 코드와 더 단순하게 통합되는 대안은 같은 계약을 지키면서 선택하고 변경 근거를 기록한다. 제품 규칙을 임의로 바꾸는 근거로 사용하지 않는다.

## 공통 검증 방식

각 작업에서 아래 순서를 반복한다. 테스트는 실제 동작·권한·시각 경계·원자성을 검증하며 단순 필드 존재 검사로 대체하지 않는다.

- [ ] 해당 작업의 명시된 입력/상황으로 실패하는 테스트를 작성한다.
- [ ] 변경 전 실패 이유가 기대한 동작 차이인지 확인한다. 단순 import 오류만으로 회귀 재현을 대신하지 않는다.
- [ ] 해당 파일·경계의 최소 구현을 진행한다.
- [ ] 대상 테스트와 관련 회귀 테스트를 실행한다.
- [ ] 단계가 끝나면 타입 검사, 관련 코드 린트, 빌드, 실제 UI 흐름을 확인한다.
- [ ] 변경 파일만 묶어 검토 가능한 커밋을 만들고 결과를 기록한다. 푸시·배포는 사용자 요청 범위를 확인한다.

명령은 모두 `web/`에서 실행한다. 의존성 설치는 `npm ci`, 기존 회귀는 `npm test`, 타입 검사는 `npx tsc --noEmit`, 빌드는 `npm run build`, 로컬 DB 적용은 `npm run db:migrate`다. 린트는 `npx oxlint`에 실제 수정한 서비스 파일을 전달한다. 기존 UI 카탈로그 전체 린트 실패를 새 변경의 실패와 혼동하지 않는다.

`npm test`는 현재 두 파일만 명시한다. 새 테스트 파일을 만들 때 반드시 `web/package.json`의 실행 대상에 포함시키고, 실행 로그에서 새 테스트 이름이 실제로 실행됐는지 확인한다. 테스트 환경은 `node:sqlite`를 지원해야 한다. 저장소 기록의 Node 25.6.1이 검증 기준이며, package.json의 최저 버전 선언만으로 SQLite 테스트 실행 가능성을 단정하지 않는다.

## 전체 완료 기준

1. 최소 2명과 최신 목표 합의 없이는 시작할 수 없으며 준비 기간이 소모되지 않는다.
2. 시작 후 목표·최종 기한을 일반 편집·AI 승인·되돌리기 어느 경로로도 변경할 수 없다.
3. 보고 없이도 합의 결과물을 충족하면 완주 가능하다. 반대로 체크리스트만 모두 완료해도 결과물이 부족하면 완주 불가다.
4. 마감 이후 모든 사용자 상태 변경이 서버에서 차단되고 열람·내보내기는 유지된다.
5. 개인별 가용시간과 목표 축소·이월 UI/API가 새 프로젝트에 남지 않는다.
6. 이메일은 정확한 3단계/5단계 대상과 현재 수신자 기준으로 처리되며 완료·종료·중복·겹침을 검증했다.
7. AI는 원문 사실과 추정을 구분하고, 사용자가 선택·편집·승인한 변경만 권한·버전 검사 후 적용한다.
8. 승인 후 복구는 다른 사용자의 후속 수정과 목표·마감 고정을 침해하지 않는다.
9. 실제 두 계정으로 주요 흐름을 검증하고, 모의 연결만 확인한 부분은 운영 완료로 보고하지 않는다.

이 계획은 구현을 클로드에게 인계하기 위한 문서다. 작성자는 이 턴에서 소스·테스트·DB·배포·실제 이메일을 변경하지 않는다.
