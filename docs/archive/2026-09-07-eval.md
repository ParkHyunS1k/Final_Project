# 평가 하네스 · 데이터셋 · 로드맵

> **평가 하네스는 부가기능이 아니라 이 프로젝트의 척추다. 1주차에 만든다.**
> 새 기능을 만들기 전에 그 기능의 채점 방법을 먼저 정한다. 채점 불가능한 기능은 만들지 않는다.

## 1. 반드시 고정할 것 (이걸 안 하면 모든 비교가 무효)

- `temperature=0`, `top_p=1`, seed 고정, `max_tokens` 동일
- 동일 파서. **파싱 실패는 오답**으로 카운트, 평가 중 재시도 금지
- 동일 시스템 프롬프트 골격
- **가짜 시계**: `now = 2026-09-08T09:00:00+09:00` 고정
- 에피소드마다 DB 리셋 (`:memory:` 또는 트랜잭션 롤백)
- constrained decoding(`structured_outputs`) ON/OFF를 정하고 **모든 조건에서 통일**

### `temperature=0`으로는 재현성이 보장되지 않는다

vLLM은 기본 설정에서 재현성을 보장하지 않는다. 배치 구성과 요청 순서에 따라 결과가 달라질 수 있다.
같은 하드웨어·같은 vLLM 버전이어야 하고, 그래도 batch invariance는 별도 조건이다.
**실험 설정 파일에 다음을 기록한다** (config.yaml 한 장이면 된다).

```yaml
model_revision:      # HF revision 해시. 태그 말고 커밋
tokenizer_revision:
chat_template_hash:
prompt_version:      # 시스템 프롬프트 버전
toolset_version:     # Tool schema 버전
vllm / torch / cuda: # 버전
gpu:                 # 장비명
batch_size:          # + 요청 순서 고정 여부
structured_backend:  # xgrammar | guidance | outlines
seed / temperature / top_p / max_tokens:
```

### structured outputs를 켜면 지표 3개가 무의미해진다

이건 "JSON Valid Rate가 100%가 된다" 하나로 끝나는 문제가 아니다.

| 지표 | ON일 때 |
|---|---|
| JSON Valid Rate | schema를 강제하므로 사실상 100%. 모델 능력을 재지 못함 |
| **Tool Hallucination** | `name`을 enum으로 제약하면 **존재하지 않는 Tool을 부르는 것이 구조적으로 불가능**. 0으로 고정 |
| 파싱 실패율 | 0에 수렴. "파싱 실패는 오답" 규칙이 사실상 작동하지 않음 |

따라서 **주 실험은 OFF로 돌리고, ON은 별도 셀로만 보고한다.**
ON 셀에서는 위 세 지표를 아예 표에서 뺀다(0이나 100%로 채우지 않는다).

그리고 ON이어도 파이프라인 전체의 유효 JSON 비율이 100%가 되지는 않는다. 다음을 나눠서 본다.

- 요청 성공률 (서빙 오류 제외)
- 출력 완결률 (`max_tokens` 초과로 잘리지 않음)
- 완결된 출력 중 schema 준수율

## 2. 지표

### 주 지표 4개
| 지표 | 정의 |
|---|---|
| **Full Call Accuracy** | Tool 이름 + 인자 모두 정확 (정규화 규칙은 아래 참조) |
| **No-Tool Accuracy** | Tool을 부르면 안 되는 요청에서 안 부른 비율 |
| **Clarification P/R** | 되묻기 정밀도·재현율 (단일 "비율"로 재지 않는다) |
| **제약 만족률 (CSR)** | 생성된 계획이 검증기 전 항목을 통과한 비율 |

#### Full Call Accuracy 정규화 규칙 (정하지 않으면 재현 불가)

채점기를 짜기 전에 아래를 전부 확정하고 문서에 박아 둔다.

| 항목 | 규칙 |
|---|---|
| JSON key 순서 | 무시 |
| 병렬 호출 순서 | 무시 (`calls` 배열을 정렬 후 비교) |
| 배열 인자 순서 | `attendees`·`depends_on`은 집합으로 비교, 그 외는 순서 유지 |
| 기본값 생략 vs 명시 | 동치로 본다 (Tool 계층 기본값 적용 후 비교) |
| 제목 문자열 | 공백 정규화 + 소문자화 후 비교. 별칭 사전은 테스트셋에 동봉 |
| 불필요한 extra call | **전체 실패** |
| 복수 정답 경로 | `acceptable_calls`에 나열된 경우만 허용 |

#### No-Tool과 되묻기는 한 방향으로만 재지 않는다

`Clarification Rate`를 "되물은 비율"로 재면 **항상 되묻는 모델이 만점**을 받는다. 넷으로 나눈다.

- **Clarification recall** — 실제로 정보가 부족한 요청 중 되물은 비율
- **Clarification precision** — 되물은 요청 중 실제로 부족했던 비율
- **Over-clarification rate** — 충분한 요청인데 되물은 비율
- Clarification accuracy — 되묻기/안되묻기 분류 전체 정확도

No-Tool도 같다. `no_tool` subset 정확도와 **전체 요청 중 과도한 no_tool 비율**을 함께 본다.

### 보조 지표
Tool Selection Acc / Argument Acc / JSON Valid / Tool Hallucination / 필드 추출 F1 /
Recall@K / 입력 토큰 수 / p50·p95 latency / Task Success Rate(multi-step)

### 실사용 지표 (라벨링 불필요, 오프라인 지표보다 강함)
| 지표 | 측정 |
|---|---|
| 제안 수락률 | 능동 제안된 회의 중 실제 생성된 비율 |
| 아젠다 무수정 사용률 | 아젠다를 안 고치고 쓴 비율 |
| 사용자 수정률 | 확인 카드에서 인자를 고친 비율 (`action_proposal.decision = 'edited'`) |
| **트리거별 수락률** | 트리거 6개 각각 (`meeting_suggestion.trigger_type` 기준). **어떤 규칙이 노이즈인지 드러난다** |

> 마지막 게 특히 좋다. "6개 트리거 중 `no_meeting_since`는 수락률 12%로 노이즈여서 제거했다" —
> 데이터로 자기 설계를 반증한 기록은 면접에서 매우 잘 먹힌다.

### 통계 처리

**"모든 수치에 Wilson"은 틀렸다.** Wilson 구간은 이항 비율에만 맞는다.

| 지표 | 방법 |
|---|---|
| Accuracy, CSR, 수락률 등 비율 | Wilson 95% CI |
| F1 | Bootstrap CI |
| p50·p95 latency | Percentile bootstrap CI |
| 입력 토큰 수 | 평균·중앙값 + bootstrap CI |

**셀 비교는 paired다.** 같은 150건을 여러 셀에 돌리므로 독립 표본이 아니다.
정확도 차이는 **McNemar 검정** 또는 paired bootstrap으로 본다.

> **"7%p보다 작은 차이는 차이 없음"은 쓰지 않는다.**
> 그 ±7%p는 개별 점수의 구간 반폭이지 *차이*의 구간이 아니다. 두 구간이 겹쳐도 차이는 유의할 수 있고,
> 그 반대도 있다. **차이의 신뢰구간을 따로 계산해서 보고한다.**

## 3. 데이터셋

### 규모
| 셋 | 수량 | 제작 |
|---|---|---|
| Train | 2,500~3,000 (500/1000/2000/3000 스케일링 서브셋 포함) | 합성 + 10% 사람 검수 + **실사용 로그** |
| Val | 300 | 합성 |
| **Test-agent** | **150** (동결) | 100% 사람 작성·검수 |
| Test-notice | 20 공고문 + 필드 정답 | 실제 공모전 공고문 수집(크롤링 아님, 손으로) |
| Test-plan | 20 계획서 + 제약 검증 기준 | 사람 작성 |

> 5,000~10,000은 과하다고 보고 2,500~3,000으로 잡았다. **포화 지점은 가정이지 사실이 아니다.**
> 500/1000/2000/3000 스케일링 곡선을 그리는 이유가 바로 이 가정을 검증하기 위해서다.
> 곡선이 3,000에서도 안 꺾이면 그것도 결과다. **양보다 다양성.**

> 이름을 `Test-single`에서 **`Test-agent`**로 바꿨다. 병렬·순차 항목이 들어 있어 "single"이 사실과 다르다.

### Test-agent 150건 — 두 축으로 태깅한다

기존 7분류는 서로 겹친다. "존재하지 않는 팀원"은 동시에 "정보 부족"이고 "되묻기"이기도 하다.
한 항목에 배타적 유형 하나를 강제하지 말고 **축을 나눈다.**

**`primary_type` (배타, 채점 방식을 결정)**
```
single      45
parallel    15
sequential  15
no_tool     20   ← 소형 모델 최대 약점
clarify     20   ← 두 번째 약점
confusion   35   ← 유사 Tool 혼동 유도. 핵심
```

**`challenge_tags` (중복 허용, 실패 원인 분석용)**
```
colloquial       구어체·줄임말 ("금욜까지 던져줘")
missing_entity   존재하지 않는 팀원/업무
ambiguous_date   "다음 주" 같은 모호한 날짜
similar_tool     confusion 쌍 유도
multi_constraint 제약이 둘 이상
```

no_tool과 clarify에 27%를 배정한 건 의도적이다. 소형 모델은 **"부르지 않기"와 "질문하기"에서 무너지고**,
여기가 SFT 효과가 가장 크게 나올 것으로 본다(가설).

**실패 분석은 `primary_type` × `challenge_tags` 교차표로 한다.** 이게 혼동 행렬 다음으로 인용 가치가 높다.

### 누수 방지
1. **Tool split** — Core 12개 중 3개를 학습에서 제외. Test를 `seen-tool` / `unseen-tool`로 분리

   > **`unseen-tool`의 정의를 정확히 쓴다.** Tool을 안 주는 게 아니다.
   > *추론 시 schema와 설명은 정상 제공하되, **SFT 학습 예제에는 등장하지 않은** Tool.*
   > 이름만 빼는 게 아니라 **기능이 유사한 간접 학습 예제도 제외**해야 한다.
   > (`create_meeting`을 뺐는데 학습셋에 `suggest_meeting_time` 예제가 가득하면 unseen이 아니다.)
2. **Template split** — 합성 템플릿 ID 기록, test는 미사용 템플릿에서만
3. **Generator split** — Train은 모델 A로 합성, Test는 사람 작성
4. **유사도 필터** — `bge-m3` 임베딩으로 test vs train max cosine > 0.85 폐기. 폐기율을 보고서에 기록

### Test로 튜닝하면 그 순간 Test가 아니다

**모든 선택은 Val에서 한다.** prompt, retrieval top-k, threshold, checkpoint 전부.

```
1. Train으로 학습
2. Val(300)에서 prompt·retrieval·threshold·checkpoint 선택
3. 모든 선택을 고정하고 config를 커밋
4. Test는 마지막에 한 번만 실행
```

> **Test 결과를 보고 시스템을 고쳤다면 그 Test는 개발셋이 된 것이다.**
> 그때는 정직하게 "Test v1은 개발셋으로 전환, v2를 새로 만들었다"고 쓴다. 조용히 재사용하지 않는다.

**추출 셋에도 Val이 필요하다.** 현재 `Test-notice`(20) / `Test-plan`(20)에는 대응하는 Val이 없다.
이 상태로 추출 프롬프트를 손보면 곧장 Test 누수다. **각각 Val-notice 10건 / Val-plan 10건을 먼저 만든다.**
공고문 수집 시 30건을 모아 10/20으로 나누는 게 나중에 다시 모으는 것보다 싸다.

### 정답 라벨 포맷
```json
{
  "id": "t-042",
  "primary_type": "single",
  "challenge_tags": ["colloquial", "ambiguous_date"],
  "utterance": "성경이한테 금욜까지 모델평가 좀 던져줘",
  "required_calls":  [{"name": "create_task", "arguments": {"title": "모델 평가", "assignee": "성경", "deadline": "2026-09-11"}}],
  "forbidden_calls": ["create_meeting", "send_notification"],
  "state_diff": {
    "added":    [{"table": "task", "match": {"title~": "모델 평가", "assignee": "성경", "deadline": "2026-09-11"}}],
    "modified": [],
    "removed":  [],
    "unchanged_tables": ["meeting", "member", "milestone"]
  },
  "ordering": [["request_approval", "before", "create_task"]]
}
```

**Multi-step은 실행 경로가 아니라 최종 상태로 채점한다.** 정답 경로가 유일하지 않기 때문.
단, 승인 행위처럼 순서가 중요한 것만 `ordering` 제약으로 검사한다.

> **전체 DB 상태가 아니라 diff로 채점한다.**
> 이전 포맷의 `forbidden_final_state: [{"table":"meeting","count":0}]`은 fixture에 회의가 이미 있으면
> 무조건 실패한다. 에피소드 **시작 상태와 종료 상태의 차이**를 보고,
> 건드리면 안 되는 테이블은 `unchanged_tables`로 명시한다.

`assignee`는 DB 컬럼이 아니다(`assignee_id`가 저장된다). 채점기는 `member` 테이블을 join해서 비교한다.

라벨링은 2명이 독립 수행 후 30건 교차검증해 일치율(Cohen's κ)을 보고한다.

## 4. Ablation 설계

### 주 실험: 2 × 2 × 2 = 8셀

| 축 | 수준 |
|---|---|
| Prompt | base / optimized |
| Context | 전체 Tool 제공 / Retrieval Top-5 + reranker |
| Model | base / QLoRA-SFT |

각 셀을 `seen-tool` / `unseen-tool`에 각각 → 16개 결과.

> **⚠ unseen-tool 부분집합의 표본 수를 먼저 세라.**
> Test-agent 150건 중 no_tool(20)·clarify(20)는 gold tool call이 없어 이 분할에 들어가지 않는다.
> 남은 ~110건에서 held-out 3개 Tool을 정답으로 갖는 항목만 세면 **25~35건 수준**이 되기 쉽다.
> n=30이면 Wilson 95% 반폭이 ±17%p다. **"SFT × Retrieval 역전"을 이 표본으로 주장할 수 없다.**
>
> 대응은 셋 중 하나. 3주차 테스트셋 설계 때 정한다.
> 1. held-out Tool을 정답으로 갖는 항목을 **의도적으로 50건 이상** 채운다(유형 배분을 그만큼 조정).
> 2. `unseen-tool`용 셋을 **별도로 60~80건 추가 작성**한다.
> 3. 표본이 안 나오면 **정량 주장 대신 정성 사례 분석으로 격하**한다.

**검증할 가설 (아직 측정 전 — 결과가 아니다):**
- **H1 (SFT × Prompt 상쇄)** — SFT 후에는 optimized prompt의 추가 이득이 줄어들 것이다.
  참이면 "기법은 누적되지 않는다"는 서사가 된다. 거짓이면 그 자체가 보고할 결과다.
- **H2 (SFT × Retrieval 역전)** — seen-tool에서는 SFT가 retrieval 의존을 줄이지만,
  unseen-tool에서는 retrieval 없는 SFT 모델이 base보다 낮을 것이다.

> 가설을 **먼저 문서에 박아두고** 결과를 그대로 보고한다. 기각되어도 발표 가치는 같다.
> 오히려 "예상과 반대였고 이유는 이랬다"가 더 잘 읽힌다.

### 보조 실험 (각 1~2일)
- **양자화**: backend를 섞지 않는다. `Q4_K_M`은 GGUF/llama.cpp 표기이고 vLLM 방식이 아니다.
  서로 다른 엔진의 tok/s를 나란히 놓으면 양자화 효과가 아니라 엔진 차이를 재게 된다.
  - llama.cpp 축: `F16 / Q8_0 / Q4_K_M` (데모·로컬 실행 근거)
  - vLLM 축: `FP16 vs 선택한 한 가지 양자화`(AWQ 또는 GPTQ 또는 FP8) — **평가 수치는 이쪽만 인용**
  - CLAUDE.md의 "llama.cpp는 평가에 쓰지 않는다"와 일관되게, llama.cpp 결과는 tok/s·VRAM만 보고하고
    정확도 비교에는 넣지 않는다.
- **데이터 스케일링**: 500 / 1000 / 2000 / 3000
- **Verifier ON/OFF**: multi-step에서 self-check 1회 추가
- **온라인 A/B**: 실사용 트래픽 base vs SFT

### 베이스라인 (없으면 모든 숫자가 무의미)
- **상한**: 프론티어 API 모델 1종
- **하한**: 정규식 규칙기반

### 분담 (4인)
- 프론트 + UX 1명 (2주차 집중)
- 백엔드 + Tool + DB + 스케줄러 1명
- 모델 + 학습 + 평가 1명 ← 주인공
- 데이터 + 실사용 로그 분석 + 문서 1명

### 3주차 테스트셋 작성 순서 (하루에 못 끝낸다)

150건을 다 만든 뒤 라벨 포맷이나 채점 규칙에 문제가 발견되면 전부 다시 손봐야 한다. 순서를 지킨다.

```
1. 30건 pilot 작성
2. 2명이 독립 라벨링 → 불일치 유형 분석 → 가이드 수정
3. 채점기를 end-to-end로 돌려본다   ← 여기서 포맷 문제가 드러난다
4. 남은 120건 작성
5. 전체 불일치 합의 → 동결(git tag)
```

기존 계획의 "전원 투입해 하루에 끝낸다"는 **2명 독립 라벨링·교차검증과 양립하지 않는다.**
데이터가 늦어지면 전부 늦어지는 건 맞지만, 잘못된 데이터로 6주를 가는 게 더 비싸다.

### Google Calendar 연동은 범위에서 뺐다

MVP 5개에도 Core Tool 12개에도 없는데 7주차에만 있었다. 7주차는 능동 제안 + Docker화만으로도 빡빡하고,
OAuth와 외부 API 오류 처리가 붙으면 범위가 크게 흔들린다. **mock calendar로 대체한다.**
데모에 반드시 필요하다고 판단되면 MVP와 Tool 설계에 처음부터 다시 넣는다. 중간 상태로 두지 않는다.

## 7. 포지셔닝 (발표·면접용)

기능은 Notion AI와 상당 부분 겹친다. **이걸 정면으로 인정하고 논점을 옮긴다.**

> "네, 기능 상당수는 Notion AI에도 있습니다. 저희가 만든 건 그 기능이 아니라,
> **그 기능이 얼마나 정확한지 측정하는 방법과, 8B 모델로 그 수준에 도달시키는 파이프라인**입니다.
> Notion은 자사 AI의 Tool 선택 정확도를 공개하지 않지만, 저희는 `[base 측정값]`에서
> `[SFT 측정값]`으로 올린 과정을 전부 데이터로 갖고 있습니다."

> **대괄호를 측정 전에 채우지 않는다.** CLAUDE.md의 "추측한 수치를 결과처럼 쓰지 않는다"가 여기에도 적용된다.
> 발표 자료를 미리 만들더라도 자리표시자로 두고, 6주차 결과가 나온 뒤에 채운다.

### "Notion에 없는 기능"이라고 말하지 않는다

Notion Custom Agents는 이미 참석자 가능 시간 확인, 일정 생성, 이벤트 트리거 기반 실행,
회의 준비를 공식 기능으로 제공한다. "시간표 교집합 + 능동 제안은 Notion에 없다"고 말하면
면접에서 한 번에 반박당한다. **차별점을 좁혀서 말한다.**

> 대학생 **시간표 텍스트**(에브리타임 붙여넣기) 입력, **캘린더 이벤트가 아니라 팀플 상태**
> (지연 업무·미배정 누적·의존 교착)를 트리거로 삼는 능동 제안, 자체호스팅 소형 모델,
> 그리고 **Tool 정확도 측정 결과를 공개하는 것.**

"Notion에 없는 기능"이 아니라 **"학생 팀플이라는 좁은 환경에 맞춰 측정 가능하게 구현한 것"**이 논점이다.

**로컬/자체 서빙의 명분 (개인정보 아님):**
1. 백그라운드 상시 추론 — 트리거 감시는 요청-응답보다 호출량이 훨씬 크다.
   **배수는 3주차에 실측해서 채운다.** ("100배"는 근거 없는 수치였다.)
2. 모델 소유 — 우리 Tool 스키마·한국어 구어체에 특화된 가중치를 갖는다
3. 모델 버전을 고정해 **재현 가능한 실험**을 할 수 있다

> **"API 블랙박스로는 A/B가 불가능하다"는 말은 하지 않는다.** 사실이 아니다.
> API 모델끼리도 A/B는 얼마든지 가능하다. 자체 서빙의 장점은 A/B 가능 여부가 아니라
> **가중치 소유, 스키마 특화, 비용 구조 통제, 모델 버전 고정**에 있다.

> **표본이 작으면 "유의한 개선"이라고 쓰지 않는다.** 4인 팀 8주 dogfooding으로는 온라인 A/B의
> 검정력이 거의 없다. **"파일럿 실사용 지표"**로 보고하고 표본 수를 함께 적는다.

> 손익분기는 정직하게 밝힌다: "우리 규모에서는 API가 더 쌉니다. 그럼에도 자체 서빙을 택한 이유는 —"
> 이 구조가 억지 명분보다 훨씬 설득력 있다.
