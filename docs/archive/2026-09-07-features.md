## 1. 자연어 → Tool 실행

### Agent 상태머신 (직접 구현, ~200줄)

**조회 Tool과 변경 Tool의 경로가 다르다.** DB를 바꾸는 Tool은 승인을 받은 뒤에 실행한다.

```
PLAN → RETRIEVE_TOOL → DECIDE
  ├ parse error → ERROR    (재시도 없음. 평가에서는 오답)
  ├ clarify     → FINISH   (되묻기. Tool 호출 없음)
  ├ no_tool     → FINISH   (답변만. Tool 호출 없음)
  └ tool_calls
      ├ 전부 조회      → EXECUTE → OBSERVE → REPLAN → FINISH | ERROR
      └ 변경 포함      → PROPOSE → WAIT_APPROVAL   ← 여기서 턴이 끝난다
                          └ resume(proposal_id, decision, edited_arguments)
                              ├ approved → EXECUTE → OBSERVE → REPLAN → FINISH
                              ├ edited   → EXECUTE(수정된 인자) → OBSERVE → REPLAN → FINISH
                              └ rejected → FINISH (실행 안 함. 제안은 action_proposal에 남음)
```

**`clarify` / `no_tool` / parse error도 상태다.** 이 셋은 Tool을 부르지 않으므로 `tool_call_log`에
행이 생기지 않는다. `model_invocation`에 기록해야 No-Tool Accuracy와 Clarification P/R을 잴 수 있다.

**승인 대기에서 턴을 끝낸다.** `run()` 안에서 사용자 입력을 기다리지 않는다. `propose()`가 제안을
`decision='pending'`으로 저장하고 반환한 뒤, 별도 호출인 `resume()`이 이어받는다. CLI에서는 차이가
없지만 웹에서는 요청이 끊겼다 이어지므로 이 구조여야 한다.

**혼합 호출 정책:** 한 `calls` 배열에 조회와 변경이 섞이면 **전부 승인 대상으로 보낸다.**
조회만 먼저 실행하면 사용자가 거절했을 때 이미 읽은 상태를 되돌릴 수 없고, 부분 실행이
사용자 기대와 어긋난다.

**부분 승인:** `calls`의 원소 1개 = `action_proposal` 1행. 사용자는 행별로 승인/수정/거절한다.
승인된 것만 실행하며, 하나가 실패해도 나머지를 되돌리지 않는다(원자적이지 않다).
업무 20개 중 3개가 실패했다고 17개를 날리는 게 더 나쁘기 때문이다.

- multi-step은 **2~3단계 상한**. 그 이상은 4B/8B에서 오류가 누적되어 신호가 사라진다.
- 파싱 실패 시 평가 모드에서는 재시도하지 않는다(오답 처리). 서비스 모드에서만 1회 재시도 후 API 폴백.

### 출력 포맷 — 단일 envelope

Tool 호출·되묻기·무호출을 **서로 다른 형태로 뱉지 않는다.** 파서가 하나여야 "파싱 실패=오답" 규칙이 성립한다.

```json
{"decision": "tool_calls", "calls": [
  {"name": "create_task", "arguments": {"title": "모델 평가", "assignee": "성경", "deadline": "2026-09-11"}}
]}
```

```json
{"decision": "clarify", "missing_fields": ["deadline"], "question": "마감일이 언제인가요?"}
```

```json
{"decision": "no_tool", "answer": "현재 진행률은 ..."}
```

병렬 호출은 `calls` 배열에 원소를 더 넣는다. 순서가 의미 없는 병렬은 채점 시 순서를 무시한다.

> 이 포맷은 **5주차 SFT 데이터 생성 전에 확정**한다. 학습 후에 바꾸면 데이터를 전부 다시 만들어야 한다.

### 라우터 (1주차 필수)

```python
def route(request, ctx):
    if not gpu_healthy():                 return "api"        # 폴백
    if estimated_difficulty(request) > T: return "api"        # 고난도
    return "local"                                            # 기본 (목표: 70~80%)
```

`ab_group`은 **라우터보다 앞에서** 사용자·프로젝트 단위로 고정 배정한다. 라우팅 결과로 그룹을 정하면
GPU가 살아있고 난도가 낮은 요청만 실험에 들어가 표본이 편향된다.

```
사용자/프로젝트 단위로 A/B 고정 배정 → 난도·GPU 상태로 route 결정
→ assigned_group, served_model, route_reason 전부 기록
```

**나중에 붙이기 어려우므로 처음부터 넣는다.**

## 2. 문서 → 프로젝트 부트스트랩

### 문서 계층

| 문서 | 추출 대상 | 생성물 |
|---|---|---|
| **공고문/요강** (`notice`) | 제출 마감, 발표일, 중간점검일, 제출물 목록, 팀 인원 제한, 평가 기준 | **앵커 마일스톤** (locked) |
| **계획서/기획안** (`plan`) | 기능 목록, 기술 스택, 역할 분담 | 파생 마일스톤 + 업무 + 의존관계 |
| **회의록** (`minutes`) | 결정사항, 액션아이템 | 업무 추가/수정 |
| **피드백** (`feedback`) | 수정 요구사항 | 업무 추가 + 우선순위 |

### Stage 1: 공고문 → 앵커

한국어 날짜 표기는 다양하다. 모두 커버해야 한다.
```
"10.01(수) 15시까지"   "2026년 10월 1일"   "10/1 오후 3시"
"접수마감 10.1"        "제출기한: 10월 첫째 주 금요일"
```

출력 스키마:
```json
{
  "anchors": [
    {"title": "기획안 제출", "date": "2026-08-28", "time": "15:00",
     "kind": "anchor", "event_type": "submission"},
    {"title": "본선 발표",   "date": "2026-10-02",
     "kind": "anchor", "event_type": "presentation"}
  ],
  "deliverables": ["PT 자료", "코딩 산출물"],
  "constraints": {"team_size_max": 4, "requires_major": true},
  "criteria": ["창의성", "기술성", "실용성", "발표력", "팀워크"]
}
```

**`kind`와 `event_type`은 다른 축이다.** `kind`는 `anchor | derived`(일정의 성격),
`event_type`은 `submission | presentation | checkpoint`(행사의 종류). 한 필드에 섞지 않는다.

`deliverables` / `constraints` / `criteria`는 마일스톤이 아니므로 `project_meta` 테이블에
JSON으로 저장한다(→ `docs/tools.md`). 저장 위치가 없으면 추출해도 쓰이지 않는다.

**이 단계는 정답이 명확하므로 exact-match 자동 채점이 가능하다.** 필드 추출 F1이 가장 깔끔한 결과 지표.

### Stage 2: 계획서 → 업무 (2단계 분해 필수)

한 번에 20개를 계획시키면 소형 모델의 출력 품질이 급격히 떨어진다고 보고 쪼갠다.
(가설 H0. 3주차 베이스라인에서 일괄 생성 vs 분해 생성을 1셀로 측정해 확인한다.)

```
2-a) 계획서 + 앵커 → 마일스톤 4~6개 (제목 + 산출물만, 날짜 없음)     ← 4B로 충분
2-b) 마일스톤별로 업무 3~4개 생성 (병렬 5회 호출)                    ← 각각 단순
2-c) 제약 검증 → 위반 시 해당 마일스톤만 재생성                       ← 부분 재시도
```

**LLM 출력에 날짜 필드를 넣지 않는다.** 업무·공수·의존관계만:
```json
{"id": "t3", "title": "모델 학습", "effort_hours": 15, "depends_on": ["t2"], "role": "ml"}
```

### Stage 3: 계획서가 없는 팀

계획서가 없는 팀이 적지 않고, 작성을 강요하면 이탈한다고 본다. **질문 3개로 대체:**

1. 무엇을 만드나요?
2. 어떤 기술을 쓰나요?
3. 팀원별 역할은? (자동완성 제공)

이 3줄이 계획서 대신 컨텍스트가 된다. 나중에 계획서를 올리면 diff merge.

### 부분 승인 UI (필수)

20개 업무를 한 번에 생성했는데 절반이 이상하면 사용자는 전부 지운다.
**체크박스로 골라서 생성 + 인라인 수정**이 반드시 필요하다. 여기서 나오는 수정/거절 로그가 재학습 데이터다.

## 3. 의존관계 기반 역산 스케줄러 (코드)

> **이름 주의.** 엄밀한 CPM이 아니다. CPM은 전진·후진 패스를 모두 돌려 slack을 구하고 자원 제약을
> 가정하지 않는다. 여기서는 담당자별 가용량 제약이 들어가므로 자원제약 스케줄링에 가깝다.
> 발표에서 "CPM을 구현했다"고 말하지 않는다.

### 알고리즘

```
입력: 앵커 마일스톤(고정 날짜), 업무 목록(공수·의존관계), 팀원별 주간 가용시간
1. 의존 그래프 위상정렬 (networkx). 사이클이면 즉시 에러.
2. 전진 패스: 착수 가능일부터 earliest_start / earliest_finish 계산
3. 후진 패스: 각 업무가 속한 마일스톤 앵커에서 latest_finish / latest_start 계산
   ※ 앵커가 여러 개면 최종 앵커 하나가 아니라 업무별 소속 앵커에서 역산한다.
4. slack = latest_start - earliest_start.  크리티컬 패스 = slack == 0 인 경로
5. 기간 환산은 달력일이 아니라 가용일 기준:
   남은 공수를 담당자의 요일별 가용시간에서 차감해 소진되는 날짜를 찾는다.
   (주말·공강 0인 날은 건너뛴다. effort_hours / (weekly_hours/7) 같은 균등 분할은 쓰지 않는다.)
6. 자원 평준화: 같은 담당자의 업무가 같은 날 겹치면 slack이 큰 쪽을 뒤로 민다.
7. 담당자별로 (마일스톤 기간 내 가용량 < 배정 공수)이면 OVERRUN 플래그 + 초과 일수
```

### 공수 → 기간 변환 ← 시간표 재활용

```
시간표(busy_slot) → 팀원별 "요일별" 가용시간  (현민: 월3h 화0h 수4h 목2h 금3h 토0h 일0h)
LLM              → 업무별 예상 공수          (API 개발: 15h)
코드             → 마감일에서 거꾸로 가용시간을 차감해 착수일을 찾는다
                   (15h 소진에 필요한 실제 날짜 = 5일치 가용일)
```

주간 총합(12h/주)만 쓰면 주말과 공강 0인 날이 무시된다. **요일별로 들고 있어야 한다.**

**시간표 데이터가 3중으로 쓰인다:** 회의 시간 찾기 · 일정 산정 · 업무량 균형.
"시험기간 가용시간 30% 감소" 같은 대학생 특화 규칙도 여기에 붙는다.

### 제약 검증기 (자동 채점의 핵심)

```python
def validate(plan) -> list[Violation]:
    assert not has_cycle(dep_graph)                    # 의존 사이클 없음
    assert all(t.deadline <= anchor.date for t in ...)  # 앵커 위반 없음
    assert all(t.assignee in members)                   # 존재하지 않는 팀원 없음
    assert no_unassigned_tasks()                        # 미배정 없음
    assert milestone_dates_monotonic()                  # 마일스톤 순서 정합
    assert per_member_capacity_ok()                     # 담당자별·마일스톤별 가용량 내
```

**제약 만족률(CSR)** = 위반 0인 계획의 비율. 완전 자동 채점되고 그래프 하나로 발표된다.

마지막 항목이 바뀌었다. **전체 공수 합계 ≤ 전체 가용량**은 의미가 약하다.
한 사람에게 몰려도 팀 합계로는 통과하기 때문이다. 담당자별로, 그리고 해당 마일스톤 기간 안에서 본다.

`workload_imbalance_ratio < 2.0`은 **하드 제약에서 뺐다.** 2.0이라는 임계값에 보편적 근거가 없고,
정답이 아닌 이유로 CSR이 떨어지면 주 지표가 흔들린다. 업무량 균형은 별도 **품질 지표**로 따로 보고한다.

OVERRUN이면 LLM에게 축소안을 요청한다: *"현재 계획은 3일 초과입니다. 어디를 줄일까요?"*

## 4. 능동 회의 제안 (킬러 기능)

### 원칙: 판단은 규칙, 문장만 LLM

```python
TRIGGERS = [
    milestone_within(days=3),          # 마일스톤 D-3
    blocking_task_delayed(days=2),     # 후속을 막는 업무 지연
    unassigned_tasks(count=3),         # 미배정 누적
    no_meeting_since(days=7),          # 회의 공백
    pending_decisions(count=1),        # 이전 회의 미결정 사항
    dependency_deadlock(),             # 선행 대기 교착
]
```

트리거가 발동하면 LLM에 넘긴다:
```
입력:  발동 트리거 + 관련 업무 3~5개 + 직전 회의록 미결정 항목(search_documents)
출력:  아젠다 한 줄 + 논의 항목 3개
```

**프롬프트에서 강제할 것:** 반드시 특정 업무명·담당자·날짜를 포함하고, *결정해야 할 질문 형태*로 쓸 것.
"진행 상황 공유" 같은 무의미한 문장이 나오면 아예 제안하지 않는다. 밋밋한 제안 하나가 신뢰를 다 깎는다.

### 산출물 카드

```
┌────────────────────────────────────────────┐
│ 💡 이번 주 회의가 필요해 보여요             │
│                                            │
│ 📅 목 14:00–15:00  (팀원 4명 전원 공강)     │
│                                            │
│ 주제: 데이터 수집 방식 확정                 │
│   • 수집 업무가 3일 지연 (담당: 현민)       │
│   • D-5에 모델 학습 착수 예정 → 병목        │
│   • 지난 회의 미결정: 라벨링 외주 여부      │
│                                            │
│      [수락]   [다른 시간]   [무시]          │
└────────────────────────────────────────────┘
```

이 카드 하나에 시간표 교집합 + 상태 추론 + 문서 검색 + 아젠다 생성 + Tool 실행이 전부 들어있다.
**데모 하이라이트는 이것으로 확정.**

### 알림 피로 방지 (이 기능의 사망 원인)

- 주 1회 상한. 여러 트리거가 발동해도 가장 강한 것 하나만.
- 무시당한 트리거는 7일 쿨다운(같은 사유로 재제안 금지).
- 팀별 on/off 설정.

**이 세 규칙과 eval.md의 "트리거별 수락률"은 `meeting_suggestion` 테이블 없이는 구현도 측정도 불가능하다.**
제안을 보여준 시각, 트리거 종류, 사용자 반응(수락/다른시간/무시)을 남겨야 상한·쿨다운을 판정할 수 있다.
스키마는 `docs/tools.md` 참조. **2주차 dogfooding 시작 전에 만든다.** 나중에 붙이면 그 기간 데이터는 영영 없다.

### 시간표 교집합

```
주간 30분 슬롯 비트마스크(7일 × 48슬롯)
→ 팀원별 busy 마스크
→ common_free = NOT(busy_A OR busy_B OR busy_C ...)
→ 회의 가능 시간대(예: 09:00~22:00)로 마스킹
→ duration_min 이상 연속 구간만 추출
```

> **busy 마스크끼리 AND 하면 안 된다.** 그건 "모든 팀원이 동시에 바쁜 시간"이다.
> 합집합의 여집합(위 식)이거나, 동치로 `free_A AND free_B AND free_C`.

에브리타임 시간표 텍스트 붙여넣기 → 파싱 → `busy_slot` 저장. 1~2일이면 구현된다.

## 5. 서빙 · 폴백 · A/B

```
요청 → GPU 헬스체크 ─ OK   → vLLM (Qwen3-8B + LoRA)
                     └ DOWN → API 폴백 (동일 Tool 계약 유지)
```

- **평소엔 GPU를 끄고, 발표·면접 데모 때만 켠다.** 서비스는 항상 살아있고 포트폴리오 링크가 죽지 않는다.
  백그라운드 트리거 감시는 규칙 기반이라 **CPU 워커로 충분하다.** GPU를 24시간 켤 이유가 없다.
- 폴백은 "기능 100% 유지"가 아니다. 기능은 유지되지만 **품질·비용·지연이 달라지므로 그 차이를 기록**한다.
- A/B: 실사용 트래픽을 base 모델 / SFT 모델로 분할 → 실사용 성공률·사용자 수정률 비교.
- multi-LoRA 핫스왑으로 모델 교체를 무중단 처리. 단 vLLM의 **runtime LoRA 로딩은 기본 비활성**이고
  (`VLLM_ALLOW_RUNTIME_LORA_UPDATING`), 외부에 노출하면 보안 위험이 있다.
  **기본은 시작 시 base와 SFT adapter를 미리 등록**하고, 동적 로딩은 내부 관리자 경로로만 연다.

### 관측성 대시보드 (페이지 1개)
Tool Call 로그, p50/p95 latency, 실패 유형 집계, GPU 이용률, 라우팅 비율(local/api/fallback).
실무 감각 어필 대비 구현 비용이 가장 싼 항목이다.
