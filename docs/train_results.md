## 1.1 보조 클래스 ablation — 효과를 검출하지 못했다

`worker` AP 0.889 가 전체 mAP 를 가려서 주 클래스 개선을 못 본다는 문제 때문에,
보조 클래스(`SO-02` work_platform / `WO-01` worker)를 빼고 `guardrail` 하나만
학습해 짝지어 비교했다 (`guardrail_solo` 타겟).

**프레임 집합은 건드리지 않았다.** `require: [SO-01]` 을 그대로 두었기 때문에
현장 단위 fold 배정이 baseline 과 **글자 그대로 같다** (`split.json` 의 assignment
4폴드 전부 일치 확인). 바뀐 것은 `classes` 뿐이라 폴드를 1:1로 짝지을 수 있다.

| fold | test 현장 | n_test | 3클래스 | 단일 | 차이 |
|---|---|---:|---:|---:|---:|
| fold0 | A17 | 432 | 0.4619 | 0.4037 | −0.0582 |
| fold1 | A08 | 430 | 0.4915 | 0.5814 | **+0.0899** |
| fold2 | A21 | 96 | 0.4229 | 0.1918 | **−0.2311** |
| fold3 | A04 | 954 | 0.0844 | 0.1705 | +0.0862 |
| **mean** | | | **0.3652** | **0.3369** | −0.0283 |
| std | | | 0.1893 | 0.1941 | |
| **프레임 가중** | | | **0.2782** | **0.3167** | **+0.0385** |

(`guardrail` AP@0.5. 단일 클래스 모델은 클래스가 하나라 mAP50 이 곧 이 값이다.)

**결론: 보조 클래스의 효과는 이 실험으로 검출되지 않는다. 없다는 뜻이 아니라,
있어도 이 잡음 아래 묻힌다는 뜻이다.** 근거 셋:

1. **부호가 갈린다.** 2개 폴드는 오르고 2개는 내린다.
2. **차이가 잡음보다 작다.** 폴드 간 std 가 양쪽 다 0.19 인데 평균 차이는 0.028 이다.
   폴드별 차이는 −0.231 ~ +0.090 으로 평균 차이의 8배까지 벌어진다.

> **철회한 근거 하나.** 처음에는 "단순 평균(−0.028)과 프레임 가중(+0.039)이 반대
> 결론을 낸다" 를 근거로 들었다. **이 논거는 취소한다 — 프레임 가중 AP 자체가
> 근거가 약하다.** AP 는 비선형 지표라 폴드별 AP 를 프레임 수로 가중한 값은
> 전체 out-of-fold AP 와 같지 않다. 게다가 A04 를 954프레임 찍었다는 사실이
> 배포 환경에서 A04 형 현장이 더 자주 나온다는 뜻도 아니다.
> **"새 현장 하나에서 어떤가" 가 질문이면 현장 매크로 평균이 주지표**이고,
> pooled 성능이 필요하면 모든 out-of-fold 예측을 합쳐 PR/AP 를 다시 계산해야 한다.
> 위 1절과 이 표의 "프레임 가중" 행은 참고값으로만 읽을 것.
> (`train_kfold.py` 의 `weighted_mean` 은 단순히 test 프레임 수로 가중한다.)

> **그러므로 보조 클래스를 빼지 않는다.** 해를 끼친다는 증거가 없고, `work_platform`
> 은 뒤에 쓸 여지가 있다. 대신 **전체 mAP 를 대표값으로 쓰지 않는다** — 이건
> 클래스 구성의 문제가 아니라 보고의 문제이고, 클래스별 AP 를 항상 같이 적는
> 것으로 해결된다 (README 9절).

### 이 실험이 드러낸 더 큰 문제 — 현장 A04

세 표를 겹쳐 보면 보조 클래스보다 훨씬 큰 효과가 보인다. **A04 가 test 인 fold3 은
어느 구성에서도 혼자 무너진다** (3클래스 0.084, 단일 0.171). 다른 세 현장은
0.19~0.58 구간에 있다. 게다가 A04 는 test 프레임이 954장으로 전체의 절반이라
프레임 가중 평균을 혼자 끌어내린다 — 위 표에서 가중 평균이 단순 평균보다
0.05~0.09 낮은 이유가 이것이다.

**다음 수는 보조 클래스가 아니라 A04 다.** 클래스 구성을 바꿔서 얻을 수 있는
폭(0.03)보다 A04 한 현장을 이해해서 얻을 수 있는 폭이 훨씬 크다.

### 분할 seed 반복은 여기서 성립하지 않는다

README 8절과 `data_plan.md` 6절은 "학습 seed 만 바꾸지 말고 분할 seed 도 바꾸라"
고 요구한다. **guardrail 에서는 그 요구가 무의미하다.** 현장이 4곳이고 k=4 라
각 폴드가 정확히 현장 하나를 받고, `carve_val` 은 seed 를 받지 않는다. 즉 분할
seed 는 **폴드 번호만 뒤섞을 뿐 실험 집합이 완전히 같다.** seed 0/1/2 로
배정을 생성해 집합이 동일함을 확인했다.

따라서 이 타겟에서 반복 가능한 것은 **학습 seed 뿐**이고, 위 표의 std 는
seed 편차가 아니라 **현장 간 편차**다 (그 편차 자체는 4현장으로 고정이다).

## 1.2 A04 진단 — 경계 문제가 아니라 회수율 문제다. 그리고 전 현장 공통이다

1.1 에서 A04 가 병목이라는 것까지 나왔다. 원인을 좁히려고 네 현장의 정답 박스를
원천 위에 그려 봤다 (6절의 교훈대로 코드보다 crop 을 먼저 봤다).

**라벨 관행은 네 현장이 같다** — 비계 한 칸에 박스 하나다. 다른 것은 카메라
거리다. A08 은 한두 칸이 화면을 채우고(면적비 0.181), A04 는 여러 층짜리 비계
전체가 들어와 거의 똑같이 생긴 칸이 격자로 이어 붙는다(면적비 0.048, 4.51개/프레임).

| 현장 | 프레임 | 클립 | 박스/프레임 | 면적비 중앙값 |
|---|---:|---:|---:|---:|
| A04 | 954 | 20 | **4.51** | **0.0477** |
| A08 | 430 | 7 | 1.57 | 0.1811 |
| A17 | 432 | 7 | 2.99 | 0.0619 |
| A21 | 96 | 2 | 2.00 | 0.1569 |

여기서 **"이어 붙은 칸의 경계를 못 맞춰서 IoU 0.5 를 놓치는 것" 이라는 가설**을
세웠다. `scripts/instance_probe.py` 로 검증했고 **틀렸다.**

각 폴드를 자기 test 현장을 안 본 모델로 쟀다. conf 는 0.01 — AP 가 PR 곡선을
conf≈0 까지 적분하므로 운용 임계로 재면 AP 와 어긋난다 (실제로 conf 0.25 로
먼저 쟀다가 AP 0.42 인 폴드가 프레임당 0.00개를 내는 모순을 봤다).

| fold | 현장 | 정답/f | 예측/f | 회수@0.5 | 회수@0.3 | 회수@0.1 | 합집합 IoU |
|---|---|---:|---:|---:|---:|---:|---:|
| fold0 | A17 | 2.99 | 2.2 | 46.5% | 46.8% | 52.8% | 0.438 |
| fold1 | A08 | 1.57 | 0.8 | 36.4% | 36.4% | 40.4% | 0.339 |
| fold2 | A21 | 2.00 | 0.6 | 12.0% | 12.0% | 12.0% | 0.070 |
| fold3 | A04 | 4.51 | 2.5 | **13.4%** | 15.9% | 18.2% | **0.142** |

**IoU 임계를 0.5 에서 0.1 로 5배 느슨하게 해도 3~6%p 밖에 오르지 않는다.**
경계가 문제라면 여기서 크게 올라야 한다. 합집합 IoU(개별 박스를 어떻게 쪼갰든
"난간이 있는 영역" 을 맞혔는지)도 A04 는 0.142 다. **모델은 A04 의 난간을
칸으로 잘못 나누는 것이 아니라 아예 찾지 못한다.**

### 더 큰 발견 — 회수율이 전 현장에서 낮다

같은 표를 세로로 읽으면 A04 보다 넓은 문제가 보인다. 위 표는 conf 0.01 기준이고,
그보다 더 내리면 회수율이 더 오른다 (아래 "운용점" 절). 그래도 **가장 좋은 폴드가
59.3%** 다. AP@0.5 0.46 은 정밀도를 높게 유지한 대가로 회수율 절반을 버려서 얻은 값이다.

그리고 운용 임계에서는 더 나쁘다.

| 현장 | 예측/f @0.25 | 회수@0.5 (conf 0.25) |
|---|---:|---:|
| A17 | 0.83 | 26.4% |
| A08 | 0.32 | 20.1% |
| A21 | 0.00 | **0.0%** |
| A04 | 0.49 | **3.3%** |

**conf 0.25 에서 네 현장 중 두 곳은 사실상 아무것도 검출하지 않는다.**
지금까지 보고한 AP 가 이것을 가렸다 — AP 는 conf≈0 까지 적분하기 때문이다.
미설치 판정이 제품 요구사항인데, 안 본 현장에서 난간을 96.7% 놓치는 모델은
"난간 없음" 을 계속 출력한다. 3절의 낮은 오검출률(0.1~1.2%)도 이 각도에서
다시 읽어야 한다. 짖지 않는 모델은 헛짖지도 않는다.

> **그러므로 다음 수는 클래스 구성도 A04 도 아니라 회수율이다.** 보고 지표를
> AP 단독에서 **운용 임계에서의 클래스별 recall** 로 바꾸고, 거기서부터 올려야
> 한다. 71407 실패(2절)도 recall 0.06~0.16 이었다 — 같은 증상이 외부에서 먼저
> 보였던 것이고, 내부 test 에서도 원래 그랬다는 것을 이제 확인했다.

### 운용점부터 틀렸다 — 재학습 없이 F1 +0.17

`--sweep` 으로 conf 를 훑었다 (guardrail 단일 클래스, IoU 0.5, 신뢰도 순 탐욕 매칭).

> **처음엔 그리드 하한을 0.01 로 뒀다가 고쳤다.** 네 폴드 전부 최적점이 최저
> conf 에서 나와 **경계에 걸려 있었다.** 경계에 걸린 값을 "천장" 이라 부르면 안
> 된다. 0.001/0.003/0.005 를 추가하니 수치가 크게 바뀌었다. Ultralytics val 도
> conf 0.001 을 쓰므로 이제 AP 와 같은 구간이다.

| conf | A17 P / R / F1 | A08 P / R / F1 | A21 P / R / F1 | A04 P / R / F1 |
|---|---|---|---|---|
| **0.001** | 0.373 / **0.593** / 0.458 | 0.634 / **0.534** / **0.580** | 0.361 / **0.344** / **0.352** | 0.162 / **0.275** / 0.204 |
| 0.005 | 0.506 / 0.536 / 0.521 | 0.695 / 0.448 / 0.545 | 0.336 / 0.229 / 0.272 | 0.208 / 0.205 / **0.206** |
| 0.01 | 0.630 / 0.465 / **0.535** | 0.695 / 0.364 / 0.478 | 0.377 / 0.120 / 0.182 | 0.241 / 0.134 / 0.172 |
| 0.10 | 0.804 / 0.340 / 0.478 | 0.894 / 0.250 / 0.391 | 0.750 / 0.016 / 0.031 | 0.259 / 0.051 / 0.086 |
| 0.25 | 0.947 / 0.264 / 0.412 | 0.993 / 0.201 / 0.335 | 0.000 / 0.000 / 0.000 | 0.307 / 0.033 / 0.060 |
| 0.50 | 0.992 / 0.181 / 0.307 | 1.000 / 0.136 / 0.240 | 0.000 / 0.000 / 0.000 | 0.246 / 0.017 / 0.031 |

**F1 이 conf 에 대해 거의 단조 감소한다.** 지금 쓰는 0.25 는 F1 기준 운용점이
아니다. 재학습 없이 A21 은 0.000 → 0.352, A08 은 0.335 → 0.580 이다.
정밀도 0.99 를 회수율 0.18 에 사고 있었다.

> **이 conf 를 그대로 배포에 쓰면 안 된다.** test 현장으로 고른 값이다.
> 여기서 알 수 있는 것은 **"지금 값이 그만큼 나쁘다"** 까지다. val 로 고르는
> 시도는 1.3절에 있다.

**낮은 conf 의 회수율도 "천장" 이 아니다.** 0.001 은 여전히 그리드 하한이고,
회수율이 오르는 만큼 정밀도가 무너진다 (A17 0.630 → 0.373). 지금 말할 수 있는
것은 **"관측된 저임계 회수율"** 까지다. 회수율이 는다고 운용 가능해지는 것도 아니다.

A04 는 성격이 또 다르다 — **정밀도가 0.16~0.24 로 낮다.** A17/A08 은 저신뢰에서도
0.37~0.70 을 유지한다. A04 에서는 난간이 아닌 것을 난간이라 하고 있고, 이는
2절의 71407 A26 과 같은 도메인 시프트로 읽힌다.

## 1.3 운용 임계를 val 에서 고르기 — 클래스에 따라 갈린다

1.2 에서 conf 0.25 가 운용점이 아니라는 것까지 나왔다. 그래서 `train_kfold.py` 가
**val 에서 F1 최대 conf 를 골라 test 에 적용**하도록 했다
(`src/eval/operating_point.py`, 신뢰도 순 탐욕 매칭 IoU 0.5). test 로 고르면 test
현장에 맞춘 값이 되므로 val 로 골라야 한다 — 그것이 원칙이다.

비교용으로 고정 임계 0.01 을 나란히 찍는다.

| 클래스 | val 선택 conf(평균) | val 선택 F1 | 고정 0.01 F1 |
|---|---:|---:|---:|
| `guardrail` | 0.105 | 0.322 | 0.342 |
| `work_platform` | 0.275 | 0.206 | **0.452** |
| `worker` | 0.325 | **0.839** | 0.700 |

폴드별 `guardrail`:

| fold | 현장 | val 이 고른 conf | test F1 | 고정 0.01 F1 |
|---|---|---:|---:|---:|
| fold0 | A17 | 0.010 | 0.535 | 0.535 |
| fold1 | A08 | 0.001 | **0.580** | 0.478 |
| fold2 | A21 | **0.400** | **0.000** | 0.182 |
| fold3 | A04 | 0.010 | 0.172 | 0.172 |

> **이 절의 결론은 한 번 크게 틀렸다가 고쳤다.** conf 그리드 하한이 0.01 이던
> 때에는 fold1 의 val 이 0.70 을 골라 test F1 이 0.125 였고, `guardrail` 평균이
> 0.208 대 0.342 였다. 그래서 **"val 기반 임계 선택은 실패한다"** 고 썼다.
> 하한을 0.001 로 내리자 fold1 은 0.001 을 골라 0.580 이 됐고 평균은 0.322 대
> 0.342 로 거의 동률이 됐다. **그때의 실패는 상당 부분 그리드 경계가 만든
> 인공물이었다.** 결론을 아래와 같이 좁힌다.

### 지금 말할 수 있는 것

- **`guardrail` 은 val 선택과 고정 0.01 이 사실상 동률이다** (0.322 대 0.342).
  2개 폴드는 동점, 1개는 val 이 이기고, 1개(A21)는 val 이 0.40 을 골라 0 이 된다.
  **val 선택이 체계적으로 나쁜 게 아니라, 가끔 파국적으로 틀린다.**
- **`worker` 는 val 선택이 확실히 낫다** (0.839 대 0.700). COCO 사전학습 지식이
  먹혀 현장이 바뀌어도 신뢰도가 유지되는 유일한 클래스다 (1절, AP 0.889).
- **`work_platform` 은 val 선택이 확실히 나쁘다** (0.206 대 0.452).

즉 **클래스가 현장을 넘어 일반화할수록 val 기반 임계 선택이 잘 작동한다.**
방향은 그대로지만, `guardrail` 에서 "실패" 라고 단정할 만큼 크지는 않다.

### val 이 편향돼 있다 — 이것도 원인이다

`split.carve_val` 은 현장이 4곳뿐이라 val 을 **train 현장의 세션에서** 뗀다.
게다가 세션을 크기순으로 정렬해 작은 것부터 결정적으로 고르며, 현장 균형을
맞추지 않는다 (`src/data/split.py` `carve_val`). 실제 결과:

| fold | test 현장 | val 이 걸친 현장 | 세션 수 |
|---|---|---|---:|
| fold0 | A17 | A04, A21 | 3 |
| fold1 | A08 | A04, A21 | 3 |
| fold2 | A21 | **A04 뿐** | 3 |
| fold3 | A04 | A17, A21 | 2 |

현장별 세션 수가 A04 5 / A08 1 / A17 2 / A21 2 라 **A08 은 세션이 하나뿐이라
어떤 폴드에서도 val 에 들어가지 못한다.** fold2 의 val 은 A04 세션뿐이다.

따라서 지금 결과는 "val 기반 선택 일반" 에 대한 판정이 아니라 **"이 편향된
seen-site 세션 val 로는 안 본 현장의 임계를 옮기지 못할 때가 있다"** 이다.

### 그래서 무엇을 할 것인가

- **고정 0.01 도 최종 운용값이 아니다.** test 스윕을 보고 고른 사후 진단값이다.
  독립적으로 고른 값이 아님을 알고 쓸 것.
- 제대로 하려면 **nested / cross-fitted** 가 원칙이다 — outer test 현장을 뺀 세
  현장에서 inner leave-one-site-out 예측을 모아 임계를 고른다. 다만 현장이 셋뿐이라
  여전히 불안정하다. 현장을 늘리는 것이 근본이다.
- **보고에는 두 값을 모두 적는다.** `train_kfold.py` 가 둘 다 찍고
  `kfold_metrics.json` 에 저장한다.

## 1.4 해상도 probe — 960 재학습을 기각한다

960 4폴드 재학습(2~3시간) 전에 재학습 없는 민감도 probe 를 먼저 했다
(`scripts/imgsz_probe.py`, 로그 `outputs/imgsz_probe.log`).

**같은 conf 로 비교하지 않았다.** 해상도가 바뀌면 신뢰도 분포가 통째로 움직여
같은 conf 가 같은 운용점이 아니다. **같은 오검출 예산(FP/frame)** 에서 회수율을
비교했다.

| FP/frame 예산 | imgsz 640 | imgsz 960 | 차이 |
|---|---:|---:|---:|
| 0.25 | 0.190 | 0.036 | −0.154 |
| 0.50 | 0.270 | 0.056 | −0.214 |
| 1.00 | **0.327** | 0.153 | **−0.174** |
| 2.00 | 0.387 | 0.191 | −0.197 |

(4폴드 평균 `guardrail` 회수율. 가중치는 전부 640 학습이고 960 은 추론만 올렸다.)

**전체로는 크게 진다. 960 재학습을 정당화할 근거가 없다.**

### 그런데 현장별로 부호가 갈린다 — 그리고 크기 순서와 정확히 맞는다

| 현장 | 난간 면적비 중앙값 | 960 회수율 차이 (FP/frame 1.0) |
|---|---:|---:|
| A04 | **0.0477** | **+0.117** |
| A17 | 0.0619 | −0.208 |
| A21 | 0.1569 | −0.229 |
| A08 | 0.1811 | −0.376 |

**난간이 작은 현장일수록 960 이 유리하다. 순위가 완전히 단조다** (피어슨 r = −0.80).
유일하게 이득을 본 A04 가 정확히 내가 960 을 제안했던 그 현장이다.

> **그러나 이것은 "해상도가 디테일을 살린다" 는 근거가 아니다.**
> 구간별 분해가 반증한다 — A04 의 이득은 최소 변 160~320 px 에서 +0.110,
> **320 px 이상에서 +0.175 로 큰 박스 쪽이 더 컸다.** 해상도가 원인이라면 이득이
> 작은 박스에 몰려야 하는데 반대다.
>
> 더 잘 맞는 설명은 **테스트 시점 스케일 정렬**이다. A04 의 난간은 학습에 쓰인
> 다른 현장(A08 0.181 / A21 0.157)보다 훨씬 작다. 960 으로 올리면 A04 객체가
> 픽셀 기준으로 커져 모델이 배운 스케일 분포에 가까워진다. 반대로 이미 큰
> A08/A17/A21 은 배운 범위 밖으로 밀려나 손해를 본다.
>
> **2절에서 71407 을 축소해 스케일을 맞췄을 때와 같은 현상이다.** 그때도 10~24배
> 올랐지만 절대값이 0.075 를 못 넘었다. 스케일 정렬은 효과가 있으나 천장이 낮다.

### 결론

- **960 4폴드 재학습은 하지 않는다.** 전체 회수율이 −0.17 이고, 유일한 이득은
  스케일 정렬로 설명되며 그 경로의 천장은 2절에서 이미 낮다고 확인했다.
- 학습 해상도를 올리면 **모든** 현장의 객체가 커진다. A04 형에는 맞고 나머지에는
  안 맞는다. `imgsz` 는 현장별 스케일 차이를 다루는 도구가 아니다.
- 진짜 문제는 **현장마다 난간의 화면 내 크기가 4배 차이** 난다는 것이고,
  그것을 흡수하려면 스케일 증강 범위나 멀티스케일 학습을 봐야 한다.
  `rtx4070.yaml` 의 `scale: 0.5` 를 넓히는 쪽이 `imgsz` 보다 직접적이다.

> **해석의 한계.** 640 학습 가중치를 960 으로 추론한 것은 960 으로 학습하는 것과
> 다르다. 3개 현장의 패배는 학습/추론 스케일 불일치 탓일 수 있어 근거가 약하다.
> 반면 **A04 의 승리는 불리한 조건에서 나온 것이라 신뢰할 만하다.**
> 그리고 현장이 4곳뿐이라 위 단조 관계는 n=4 다. 시사점이지 증명이 아니다.

## 1.6 미설치 판정을 처음 쟀다 — **구역이 주어졌을 때의** 구역 단위

> **이 절의 수치는 전부 구역 가중치다. 주지표는 1.7절의 클립 macro 로 바뀌었다.**
> 4.1절이 요구하는 집계 단위는 클립인데 이 절은 구역으로 나눴다. 아래 표는
> **기술통계로만 남긴다.** 특히 "A17 conf 0.005 적발 90.1%" 는 클립 macro 로
> 다시 재면 **72.5%** 이고 합격 기준 0.80 에 미달한다.

1.5절에서 확보한 집합으로 **이 프로젝트가 한 번도 재 본 적 없는 숫자**를 냈다
(`scripts/zone_eval.py`, 로그 `outputs/zone_eval.log`).

### 프레임 단위로 재면 안 된다

`SO-01` 은 UC 상황에 **아예 라벨되지 않는다** (`targets.yaml` 11행: 비계작업 UC
5,070프레임 SO-01 0건). 그 0건은 "난간이 없다" 가 아니라 **"라벨하지 않았다"** 이고,
실제로 미설치 프레임의 화면 다른 곳에는 난간이 보인다. **난간이 없다고 보장되는
것은 `UC-01` 박스 안쪽뿐이다.**

따라서 구역 단위로만 잴 수 있다. 두 구역에 **같은 규칙**을 건다 — "구역 면적의
30% 이상을 덮는 `guardrail` 예측이 있으면 난간 있음". (IoU 를 쓰지 않는 이유:
미설치 구역은 난간이 없어 칸 전체를 잡으므로 정상 구역보다 크다. IoU 는 그
크기 차이 때문에 두 구역을 다른 잣대로 재게 된다.)

**알람 = 모델이 그 구역에서 난간을 못 찾음.** 미설치 구역에서 울리면 정답이다.

### 결과 (각 현장은 그 현장을 안 본 폴드로 측정)

| 현장 | conf | 정상구역 검출 | 미설치 적발 | 오경보율 | **J** |
|---|---:|---:|---:|---:|---:|
| **A17** | 0.005 | 53.3% | **90.1%** | 46.7% | **0.434** |
| A17 | 0.001 | 67.2% | 73.3% | 32.8% | 0.405 |
| A04 | 0.001 | 38.0% | 96.8% | 62.0% | 0.348 |
| A21 | 0.001 | 41.7% | 87.0% | 58.3% | 0.287 |

`J` = Youden's J = 미설치적발률 + 정상구역검출률 − 1.
**0 이면 그 운용점의 balanced accuracy 가 0.5** 라는 뜻이다 (모델이 문자 그대로
무작위라는 뜻은 아니다).

### 가장 중요한 것 — 높은 적발률은 대부분 미검출의 부산물이다

**`A21` 이 그것을 그대로 보여준다.**

| conf | 정상구역 검출 | 미설치 적발 | J | 정밀도* | F1* |
|---|---:|---:|---:|---:|---:|
| 0.25 | **0.0%** | 99.4% | **−0.006** | 73.6% | **0.846** |
| 0.50 | **0.0%** | 100.0% | **0.000** | 73.7% | **0.849** |

**F1 이 0.85 인데 J 는 0 이다.** 모델이 아무것도 검출하지 않아 모든 구역에 알람을
울렸고, 평가셋의 74% 가 미설치라 정밀도가 저절로 0.74 가 된 것이다.
**이 F1 을 보고하면 거짓말이 된다.**

> **그래서 공동 주지표는 `미설치 적발률` 과 `오경보율` 두 개이고, `J` 는 요약값이다.**
> 셋 다 유병률과 무관하다. J 를 단독 합격 지표로 쓰지 않는 이유는 J 가 미탐과
> 오경보의 비용을 같게 두기 때문이다 — README 9절은 **recall 우선**을 요구한다.
> 합격 기준은 "적발률 ≥ X 이면서 오경보율 ≤ Y" 처럼 두 제약으로 정해야 한다. 정밀도·F1 은 이 평가셋의 정상:미설치 비율에 의존하고
> 실제 현장은 정상 구역이 훨씬 많으므로 배포 시 정밀도는 이보다 **낮다.**

### 읽는 법

- **최선의 운용점은 A17 conf 0.005 — 미설치의 90%를 잡되 정상 구역의 47%에
  헛경보한다.** 두 구역 중 하나꼴로 잘못 울리므로 그대로 배포할 수 없다.
- **세 현장의 관측값에서 J > 0 이었다.** 그 이상은 말할 수 없다. 임계를 test
  현장에서 골라 oracle Jmax 에 가깝고, 아래 표대로 독립 표본이 클립 2~9개다.
  통계적으로 무작위보다 우수하다는 주장은 **하지 않는다.**
- 박스 AP(0.365)나 박스 F1(0.206~0.580)보다 **제품 질문에 가까운 축**이다.
  다만 아래 oracle ROI 조건 때문에 아직 "제품 성능" 이 아니다.
- **프레임 단위로 갔다면 지표 세탁이었을 것이다.** "하나라도 찾았는가" 는 한 칸만
  정상이어도 다른 칸의 누락을 숨긴다. 애초에 위에서 본 이유로 성립하지도 않는다.

### 한계 — 이 수치는 "제품 성능" 이 아니라 조건부 탐색 결과다

**1. 구역이 정답에서 온다 (oracle ROI).** `zone_eval.py` 는 `SO-01`/`UC-01` 정답
박스를 그대로 ROI 로 쓴다. 배포에는 그 구역을 만들어 줄 것이 없고, README 5절
아키텍처에도 구역 생성 단계가 없다. 따라서 위 수치는
**"판정할 구역이 주어졌을 때"** 의 값이다. 제품이 되려면 둘 중 하나여야 한다.

  - 사용자가 점검 구역을 지정하는 제품 → 제품 정의에 그 전제를 명시
  - 자동 시스템 → 구역 제안기를 포함해 엔드투엔드로 평가

**2. 독립 표본은 구역 수가 아니라 클립 수다.**

| 현장 | 정상구역 / 클립 | 미설치구역 / 클립 |
|---|---|---|
| A04 | 4,306 / 20 | 125 / **2** |
| A17 | 1,290 / 7 | 1,051 / 9 |
| A21 | 192 / **2** | 539 / 6 |

A04 의 미설치 125구역은 **클립 2개**에서, A21 의 정상 192구역도 **클립 2개**에서
나온다. 인접 프레임은 거의 동일하므로 구역 수를 표본 수로 읽으면 안 된다.
**양쪽 다 클립이 7·9개인 A17 만 그나마 성립한다.**

**3. 구역 크기가 달라 판정 규칙이 편향된다.** 커버율을 구역 면적으로 나누므로,
미설치 구역이 크면 같은 예측이 "난간 있음" 판정을 받기 어려워지고 적발률이
유리해진다. 크기 차이는 현장마다 다르다.

| 현장 | 정상구역 면적비 | 미설치구역 | 배율 | J |
|---|---:|---:|---:|---:|
| A04 | 0.0477 | 0.1028 | **2.15배** | 0.348 |
| A17 | 0.0619 | 0.0900 | 1.45배 | 0.434 |
| A21 | 0.1569 | 0.1571 | **1.00배** | 0.287 |

> **다만 편향이 결과를 지배하지는 않는다.** 편향이 J 를 끌어올린 주범이라면
> 순서가 A04 > A17 > A21 이어야 하는데 실제는 A17 > A04 > A21 이다.
> **그러나 크기가 같아 편향이 0인 유일한 현장 A21 의 J 가 가장 낮다(0.287).**
> 정직한 값은 낮은 쪽이라고 봐야 한다.

**4. 판정 규칙이 단일 박스 기준이다.** 구역을 30% 덮는 예측이 **하나** 있는지만
본다. 조각난 올바른 예측 여러 개는 실패하고, 거대한 오검출 하나는 통과한다.

**5. 촬영 조건 교란.** 1.5절대로 정상/미설치가 같은 현장이지만 **다른 클립**이라
상태 판별과 클립 난이도를 분리하지 못했다.

**6. 임계를 test 현장에서 골랐다.** 배포 임계는 여기서 고르면 안 된다 (1.3절).

> **그러므로 이 수치로 합격을 선언할 수 없다.** 프로토콜 설계를 위한 탐색
> 결과로만 쓰고, 합격 판정에는 아직 손대지 않은 현장이 필요하다.

### 판정 규칙 민감도 — 규칙은 결론을 바꾸지 않는다

위 한계 3·4번(크기 편향, 단일 박스 기준)이 결과를 만들어낸 것인지 확인했다.
각 칸은 conf 를 훑은 **oracle Jmax** 다.

| 현장 | cov 0.1 | cov 0.2 | cov 0.3 | cov 0.4 | cov 0.5 |
|---|---:|---:|---:|---:|---:|
| A04 | 0.450 | 0.360 | 0.348 | 0.369 | 0.342 |
| A17 | 0.437 | 0.455 | **0.434** | 0.426 | 0.418 |
| A21 | 0.386 | 0.274 | 0.287 | 0.289 | 0.280 |

**커버 임계를 0.1~0.5 로 바꿔도 J 가 안정적이다.** 특히 A17 은 0.418~0.455 안에
있다. 0.3 은 유리하게 고른 값이 아니었다.

**단일 박스 대 합집합도 차이가 거의 없다** (전 조합에서 |ΔJ| < 0.05, 대개 < 0.02).
조각난 예측을 놓치거나 거대 오검출이 통과하는 경로가 이론적으로 존재하지만
**실측에서는 결론을 바꾸지 않는다.**

### 면적 구간별 — 크기가 결정적이다

정상·미설치 구역을 **같은 면적대로 제한**해 비교했다. 다만 구간마다 클립 수가
달라서, **양쪽 다 클립이 5개 이상인 구간만 읽을 수 있다.**

| 현장 | 면적대 | 정상 (구역/클립) | 미설치 (구역/클립) | J | 적발 | 오경보 | 읽을 수 있나 |
|---|---|---|---|---:|---:|---:|---|
| A17 | 0.05~0.10 | 789 / 5 | 383 / 6 | 0.375 | 74.2% | 36.6% | **O** |
| A17 | 0.10~0.20 | 373 / 5 | 387 / 6 | **0.924** | **96.1%** | **3.8%** | **O** |
| A17 | 0.00~0.05 | 128 / **1** | 192 / 3 | 0.000 | 100% | 100% | X |
| A04 | 0.10~0.20 | 134 / 3 | 89 / **1** | 0.985 | 100% | 1.5% | X |
| A21 | 0.10~0.20 | 26 / **1** | 265 / 6 | 0.110 | 87.9% | 76.9% | X |

**읽을 수 있는 두 줄이 같은 방향을 가리킨다.** A17 에서 구역이 커질수록
(0.05~0.10 → 0.10~0.20) J 가 **0.375 → 0.924** 로 뛴다. 그 구간에서는 난간의
96.1% 를 찾고 빈 칸에는 3.8% 만 헛경보한다.

> **즉 이 시스템은 "가까이 크게 잡힌 구역" 에서는 실제로 작동한다.**
> 실패는 작고 먼 구역에 몰려 있다. 1.2절에서 회수율이 낮았던 것도, 1.4절에서
> A04(가장 작은 난간)만 해상도 이득을 본 것도 같은 축이다.
>
> **이것은 크기 편향을 제거한 결과가 아니라 모델의 크기 의존성을 드러낸 것이다.**
> 두 구역을 같은 크기로 맞춰 비교했더니, 크면 잘 되고 작으면 안 된다는 것이 남았다.
> 배포 범위를 "일정 크기 이상으로 잡히는 구역" 으로 제한하면 성립할 수 있다는
> 뜻이고, 이는 검증 가능한 가설이다.

**A04·A21 의 면적 구간 결과는 쓰지 않는다.** 한쪽이 클립 1개라 사실상 n=1 이다.
A04 의 J 0.985, A21 의 0.110 둘 다 그 이유로 해석하지 않는다.

## 1.7 클립 macro 로 다시 쟀다 — 헤드라인이 내려갔고, 크기 효과는 살아남았다

1.6절의 약점 두 가지를 고쳤다 (`scripts/zone_eval.py`, 로그
`outputs/zone_eval_clipmacro.log`).

1. **집계 단위**를 구역에서 클립으로 올렸다. 4.1절이 요구하던 것인데 1.6절은
   구역으로 나눴다. A04 정상 4,306구역이 20클립에서 나오므로 큰 클립 몇 개가
   지표를 지배했다. 이제 클립별 비율을 내고 클립을 **동일 가중**해 평균한다.
   클립 단위 백분위 bootstrap 95% 구간을 병기한다.
2. **면적 구간 비교를 paired 로** 바꿨다. 1.6절은 구간마다 클립 집합이 달라서
   "크면 잘 된다" 와 "가까이 찍은 클립이 쉬웠다" 가 섞여 있었다. 이제 두 면적대를
   **모두** 가진 클립만 골라 클립별 차이를 내고 그 차이를 평균한다.

### 헤드라인이 내려갔다

| 현장 | conf | 적발률 (클립 macro) | 오경보율 (클립 macro) | J | 참고: 구역 가중 |
|---|---:|---:|---:|---:|---|
| **A17** | 0.005 | **72.5%** [49–92] | **39.0%** [24–53] | 0.335 | 90.1% / 46.7% |
| A17 | 0.010 | 78.4% [59–94] | 42.8% [27–56] | 0.357 | 93.2% / 50.5% |
| A04 | 0.001 | 94.4% [89–100] | 56.7% [45–67] | 0.378 | 96.8% / 62.0% |
| A21 | 0.001 | 88.5% [78–96] | 66.2% [55–77] | 0.224 | 87.0% / 58.3% |

대괄호는 클립 bootstrap 95% 구간이다.

**1.6절이 "현재 최선" 으로 보고했던 A17 conf 0.005 의 적발 90.1% 는 클립 macro 로
72.5% 다.** 합격 기준의 최소 적발률 0.80 에 미달한다. 구역 가중치가 큰 클립 쪽으로
지표를 끌어올리고 있었다.

**구간이 매우 넓다.** A17 적발률의 95% 구간이 49~92% 다. 클립이 7~9개뿐이니
당연한 결과이고, **이 폭 자체가 이 데이터로 할 수 있는 주장의 한계다.**

### 크기 효과는 paired 비교에서 살아남았다

같은 클립 안에서 두 면적대를 비교한 결과다 (conf 0.005 고정, 정상 구역).
촬영 거리·조명·세션이 상수다.

| 현장 | 비교 | 공통 클립 | 검출률 | Δ |
|---|---|---:|---|---:|
| A17 | 0.05~0.10 → 0.10~0.20 | 3 | 8.3% → **100.0%** | **+91.7%p** |
| A04 | 0.05~0.10 → 0.10~0.20 | 3 | 52.3% → 73.2% | +21.0%p |
| A04 | 0.00~0.05 → 0.05~0.10 | **8** | 19.7% → 28.0% | +8.3%p |

**두 현장에서 방향이 같다.** 클립을 고정했으므로 "큰 구역이 쉬운 클립에 몰려
있었다" 는 대안 설명은 이제 배제된다. 1.6절의 결론이 교란으로 만들어진 것은
아니었다.

### 다만 세 가지를 함께 봐야 한다

1. **크기 효과는 전부 정상 구역 쪽에서 나온다.** A17 미설치 구역의 검출률은
   면적대와 무관하게 2.7~5.8% 로 평평하다 (paired, 공통 3클립에서 Δ −1.2%p).
   즉 이것은 **"모델이 큰 난간을 잘 찾는다"** 이고, 1.2절의 회수율 문제를
   구역 단위로 다시 쓴 것에 가깝다. 새로운 능력이 아니다.
2. **가장 큰 면적대에서 뒤집힌다.** 0.20~1.00 구간의 정상 검출률은 A04·A21
   양쪽에서 **0.0%** 다 (각 공통 1클립). 구역이 화면의 20% 를 넘으면 단일 예측
   박스가 그 30% 를 덮지 못한다 — **모델 성질이 아니라 `cov` 규칙의 산물일 수
   있다.** 크기 하한을 정한다면 상한도 함께 봐야 한다.
3. **합격 기준을 넘는 칸은 여전히 A17 0.10~0.20 하나다.** 클립 macro 로도
   적발 89.4% / 오경보 3.5% (J 0.859) 로 기준을 통과한다 — 헤드라인과 달리
   이 칸은 클립 macro 보정을 견뎠다. 하지만 정상 5클립 / 미설치 6클립이고,
   4.4절에 따라 이 네 현장은 development CV 이므로 **합격 선언에 쓸 수 없다.**

### 전 현장 공통 운용점은 없다

면적대 0.10~0.20 으로 제한해도, conf 0.001 은 A04(적발 100%/오경보 1.4%)를
통과시키고 A17(75.1%/1.5%)을 적발률에서 떨어뜨린다. conf 0.005 는 A17(89.4%/3.5%)
을 통과시키고 A04(100%/26.8%)를 오경보율에서 떨어뜨린다. A21 은 두 임계 모두
오경보 76.9~96.2% 다. **하나의 고정 임계로 세 현장을 동시에 합격시키지 못한다.**

### 가설 두 개 중 하나는 답이 나왔고 하나는 아니다

**가설 2 (A04 의 낮은 정밀도 중 일부는 "맞았는데 정답이 없어서 틀렸다고 세어진
것") — 부분 성립하되 작다.** 상한이 34%이고 그마저 구조물 하나다. **절반 이상은
반사이고 이것은 정직한 오검출이다.** A04 의 낮은 정밀도(AP 0.084)를 라벨 누락으로
설명할 수 없다.

**가설 1 (미라벨 난간이 "난간은 배경" 신호가 되어 회수율을 누른다) — 이 probe
로는 답할 수 없다.** 회수율이 27~59%인 모델의 미매칭 예측으로는 **예측되지 않은
미라벨 난간**을 볼 수 없다. A08 미매칭 0개는 "라벨이 완전하다" 가 아니라
"모델이 라벨된 칸 말고는 아무것도 못 찾는다" 와 구분되지 않는다.

### 그래서 정답만 그려서 봤다 — 라벨은 확실히 부분적이다

`outputs/unlabeled/gt/*.jpg` (모델을 거치지 않는다). **A08 은 실내 시스템비계가
화면을 가득 채우는데 정답 박스가 1개**이고, **A21 은 난간이 화면을 가로지르는데
작업자 주변 2칸만** 라벨돼 있다. 라벨은 "화면의 모든 난간" 이 아니다.

### 다만 "작업자가 있는 칸에만" 도 아니다 — 단순 형태는 기각됐다

라벨 txt 만으로 쟀다 (모델 없음). 난간 박스가 작업자 박스를 가로로 끼는 비율:

| 현장 | 프레임 | 난간/frame | 작업자/frame | 작업자 낀 난간 |
|---|---:|---:|---:|---:|
| A17 | 432 | 2.99 | 1.00 | 39.0% |
| A08 | 430 | 1.57 | 0.86 | 54.9% |
| A21 | 96 | 2.00 | 1.00 | 60.4% |
| A04 | 954 | 4.51 | 1.00 | 36.6% |
| 전체 | 1,912 | 3.38 | — | **39.7%** |

프레임당 작업자는 1명인데 난간은 3.38개이고 그중 39.7%만 작업자를 낀다.
**라벨은 작업 구역 주변의 연속된 칸 묶음을 덮는다** — 작업자 칸 하나가 아니다.
빠지는 것은 **다른 층 · 화면 가장자리에서 잘린 칸 · 멀리 있는 구조물**이다.

### 남은 것

누락률을 수치로 내려면 정답만 그린 프레임에서 **보이는 칸 대 라벨된 칸**을
층화 표집해 세야 한다. 이번에는 A08·A21 에서 "부분적이다" 를 확인하는 데까지만
갔다. 그리고 **회수율과의 인과는 여전히 미검증이다** — 부분 라벨이 원인인지,
아니면 부분 라벨과 낮은 회수율이 둘 다 "난간이 시각적으로 반복되는 격자" 라는
같은 성질에서 나오는지 가르지 못했다.

## 1.9 크롭을 눈으로 봤다 — **4요소 스키마가 성립하지 않는다**

`scripts/zone_crops.py`, 산출물 `outputs/zone_crops/`. VLM 파일럿과 4요소 라벨링에
착수하기 전 필수 절차다 (`README.md` 10절 순서 1). GPU 를 쓰지 않는다.

**표집.** 현장 × 정상(`SO-01`)/미설치(`UC-01`) × 면적대 4구간 × 클립으로 층화하고
면적대마다 서로 다른 클립 3개를 뽑았다. **crop 은 원본 해상도로 자른 뒤 확대**한다
(축소하면 판정 가능성을 과대평가한다). **53장 / 36클립 / 4현장**을 봤다.

| 현장 | 정상 crop / 클립 | 미설치 crop / 클립 |
|---|---:|---:|
| A04 | 10 / 8 | 2 / 2 |
| A08 | 9 / 6 | — (`UC-01` 0건) |
| A17 | 7 / 6 | 12 / 6 |
| A21 | 3 / 2 | 10 / 6 |

### 발끝막이판이 없다 — 작아서 안 보이는 게 아니다

착수 전 가설은 **"발끝막이판이 30px 안팎이라 안 보일 것"** 이었다. 틀렸다.
**정상 crop 29장 전부에서 발끝막이판이 확인되지 않는다.** 그리고 이것은 해상도
문제가 **아니다** — A08 의 정상 구역은 폭 1,065~1,082px 인데도 발판 가장자리가
맨 철판이다. **물리적으로 설치돼 있지 않다.**

> 그러면 **제13조를 엄격히 적용하면 `SO-01` 구역도 전부 위반**이다.
> **"`SO-01` = 적법" 이라는 전제가 깨진다.** 4요소를 정답 스키마로 삼으면
> 데이터셋의 자체 라벨과 채점 결과가 정면으로 어긋난다.

### 난간기둥은 판별력이 없다 — 미설치 쪽에도 서 있다

A17 미설치 구역은 **기둥만 서 있고 가로 난간대가 없다.** 즉 `난간기둥` 은
정상·미설치 **양쪽에 존재**한다.

**4요소 중 실제로 판별에 쓰이는 것은 상부 난간대·중간 난간대 둘뿐이다.**
발끝막이판은 양쪽 다 없고, 난간기둥은 양쪽 다 있다. 두 요소는 **퇴화 상수**다.

| 요소 | 정상(`SO-01`) | 미설치(`UC-01`) | 판별력 |
|---|---|---|---|
| 상부 난간대 | 있음 | 없음 | **있다** |
| 중간 난간대 | 있음 | 없음 | **있다** |
| 난간기둥 | 있음 | **있음** | 없다 |
| 발끝막이판 | **없음** | 없음 | 없다 |

### 정상/미설치 구분 자체는 육안으로 쉽다 — 다만 A21 은 경계다

| 현장 | 미설치가 어떻게 보이는가 | 판정 |
|---|---|---|
| A17 | 기둥만 서 있고 가로대가 전무 | 명백 |
| A04 | 발판 바깥쪽에 아무것도 없다 | 명백 |
| A21 | **비계 프레임의 다음 층 가로재(ledger)가 보인다** | **경계** |

A21 미설치 crop 에는 가로 철관이 여러 개 보이지만 그것은 프레임 구조재이고,
**해당 발판 위 90cm 높이에 난간대가 있는가**를 따져야 미설치임을 안다. 비계
기하를 아는 사람이라야 가른다 — **라벨러 불일치가 여기서 난다.** kappa 0.60
요구가 형식이 아니라는 뜻이다.

### A17 미설치의 작은 면적대는 판정 단위가 아니다

`A17` `UC-01` 의 0.00~0.05 밴드는 100×415px · 129×360px · 151×1080px 같은
**세로로 긴 슬리버**다. "비계 한 칸" 이 아니라 발판 가장자리 띠다. 이 구역들을
지표 분모에 넣으면 **판정 불가능한 대상으로 성능을 재게 된다.**

### A04 미설치는 클립 2개다 — 다시 확인됐다

면적대별로 쪼개면 `A04` `UC-01` 은 각 밴드가 **클립 1개**다 (0.05~0.10 에 36구역
1클립, 0.10~0.20 에 89구역 1클립). 1.6절의 "A04 미설치 적발 94.4%" 는 **클립 2개
위에 서 있다.** 6절 8번이 실측으로 재확인된 것이다.

### 그래서 무엇을 바꿔야 하는가

1. **4요소 정답 스키마를 그대로 쓰면 안 된다.** 판별 요소 2개 + 상수 2개다.
   상수 2개를 채점에 넣으면 정확도가 자동으로 부풀고, 법령대로 채점하면
   `SO-01` 이 전부 위반이 된다. **둘 중 무엇을 할지 정해야 한다** (아래 셋 중 하나).
2. **A21 을 라벨링 파일럿에 반드시 포함한다.** 쉬운 A17·A04 만으로 kappa 를 재면
   실제 난이도가 가려진다.
3. **면적대 하한을 정답 스키마 단계에서 건다.** 슬리버 구역을 판정 대상에서
   제외하는 규칙이 필요하다. 지금의 0.10 하한은 측정값이 아니라 `bands`
   하드코딩 경계다.

## 1.10 VLM zero-shot 파일럿 — **오경보율이 8배 줄었다. 적발률은 그대로다**

`scripts/vlm_zeroshot.py`, 산출물 `outputs/vlm_zeroshot/raw.json`.
Qwen2.5-VL 7B (Apache-2.0) 4bit, 272구역 / 46클립 / 3현장.
집계는 `zone_eval.py` 와 **같은 정의**다 — 클립 macro 가 주지표, 대괄호는 클립
bootstrap 95%.

> **이 수치는 제품 성능이 아니다.** ① **oracle ROI** — 구역이 정답 박스에서 온다.
> ② **development set** — 세 현장은 이미 의사결정에 쓰였다(`eval_protocol.md` 4.4).
> ③ **crop 여백을 이 현장들의 결과를 보고 골랐다**(아래 ablation). 셋 다 합격
> 선언을 막는다.

### 실행 전에 고정한 규칙

1. **채점 요소는 상부·중간 난간대 둘뿐**이다 (1.9절의 스키마 결정).
2. **알람 규칙: 상부 난간대가 `없음` 이면 미설치 알람.** 제13조의 필수 요소다.
3. **기권은 빼고 재고 기권율을 병기**한다. 경계 두 개(기권=전부 알람 / 전부 무알람)를
   민감도로 함께 낸다.
4. **서브샘플은 클립당 균등** 6구역.

### 서브샘플이 대표성을 갖는다 — paired YOLO 가 기준 B 를 재현한다

같은 272구역에 `zone_eval.py` 와 같은 판정 규칙(cov 30%, 현장별 oracle conf)을
걸었다. 1.7절의 전수 결과와 거의 같다.

| 현장 | paired YOLO (이 표본) | 1.7절 전수 |
|---|---|---|
| A04 | 91.7% / 57.5% | 94.4% / 56.7% |
| A17 | 74.1% / 38.1% | 72.5% / 39.0% |
| A21 | 91.7% / 66.7% | 88.5% / 66.2% |

### 주 결과 — 같은 구역에서 paired

| 현장 | | 적발 | 오경보 | J |
|---|---|---:|---:|---:|
| **A17** | **VLM** | **72.2%** [54–89] | **4.8%** [0–14] | **0.675** |
| | paired YOLO | 74.1% [52–94] | 38.1% [17–57] | 0.360 |
| | 면적 baseline(oracle) | 31.5% | 0.0% | 0.315 |
| A04 | **VLM** | **0.0%** [0–0] | 4.2% [1–8] | −0.042 |

퇴화 해는 두 개 다 J 0.000 이다 ("전부 있음" 0%/0%, "전부 없음" 100%/100%).

### 헤드라인 — A17 에서 적발률은 같고 오경보율이 8배 낮다

**적발 72.2% 대 74.1%, 오경보 4.8% 대 38.1%.** J 는 0.675 대 0.360 으로 거의 두 배다.
오경보율은 기준 B 에서 **세 현장 모두 미달이던 항목**이고(39.0~66.2%),
**VLM 은 세 현장 전부 오경보 기준(≤20%)을 통과한다** (4.2 / 4.8 / 0.0%).

**그러나 합격은 아니다.** 합격 기준은 적발 ≥ 0.80 **이면서** 오경보 ≤ 0.20 이다.
A17 은 **적발에서 7.8%p 부족**하고, A04·A21 은 적발이 무너진다.

### 실패 진단 — "못 본다" 가 아니라 "난간대와 구조재를 못 가른다"

미설치인데 `있음` 이라 답한 구역을 **모델이 본 것과 같은 tight crop 으로** 열어
봤다 (`outputs/vlm_smoke_tight/why/`). 스모크 표본 10건 중 **6건이 A21**이고
원인이 하나다.

**구역 박스의 위쪽 모서리에 비계 프레임의 다음 층 가로재(ledger)가 걸려 있다.**
발판 위 90cm 에 난간대가 없어도 crop 안에는 가로 철관이 보인다. 모델은 그것을
난간대로 읽는다. A04 는 여기에 **대각선 가새**가 더해진다 — 프롬프트에 "가새는
난간대가 아니다" 를 명시했는데도 그렇다.

**이것은 사람도 A21 에서 헷갈리는 바로 그 지점이다** (1.9절, 사실 37번).
판정에 필요한 것은 "가로재가 있는가" 가 아니라 **"이 발판 위 90cm 에 있는가"**
라는 공간 관계인데, 지금 프롬프트는 물체 존재를 묻고 있다.

현장별 응답이 이를 그대로 보여 준다. **A17 미설치는 기둥만 남고 가로재가 전무해서
70%(35/50)를 맞히고, A21 은 32/36 을 `있음` 이라 답한다.**

| 현장 | 미설치 구역 `없음` | 정상 구역 `있음` |
|---|---|---|
| A17 | 35/50 (70%) | 40/42 (95%) |
| A21 | 4/36 (11%) | 12/12 (100%) |
| A04 | 0/12 (0%) | 115/120 (96%) |

### crop 여백이 교란이었다 — 스모크 단계에서 잡았다

여백을 구역 크기의 0.25배 주면 **이웃 칸의 난간이 딸려 들어온다.**

| 여백 | A17 적발 | A17 오경보 | J |
|---|---:|---:|---:|
| 0.25 | 11.1% | 0.0% | 0.111 |
| **0.00** | **77.8%** | 0.0% | **0.778** |

(클립당 1구역 스모크 표본. 본 측정은 여백 0 이다.)
**여백 0 을 고른 것은 이 현장들의 결과를 보고 내린 판단**이므로, 위 경고 ③ 이
여기서 나온다.

### 중간 난간대는 요소로 쓸 수 없다

272구역 중 **259개(95.2%)가 `판정불가`이고 `있음` 은 0건**이다. 모델이 중간
난간대를 사실상 판정하지 못한다. "둘 중 하나라도 없음" 규칙은 적발을 못 올리고
오경보만 올린다 (A17 4.8% → 23.8%).

→ **1.9절에서 판별 요소로 남긴 둘 중 하나가 이 모델·프롬프트로는 죽어 있다.**
실질 판별 요소는 **상부 난간대 하나**다.

### 기권 신호가 없다 — 3.8절의 기권 예산을 이 출력으로 구현할 수 없다

상부 난간대에 대해 **`판정불가` 가 0건**이다. 그래서 기권 처리 규칙 세 개가
전부 같은 값을 낸다. 프롬프트가 "확신할 수 없으면 판정불가" 를 명시했는데도
모델이 쓰지 않는다. **`eval_protocol.md` 3.8 의 기권 예산은 별도 신뢰도 점수
(로짓·자기일관성 등)가 있어야 성립한다.**

### A04 미설치 평가셋은 면적으로 풀린다 — 경고

**A04 면적 baseline 이 J 0.942 (적발 100% / 오경보 5.8%)** 로 VLM(−0.042)과
YOLO(0.342)를 모두 압도한다. 면적비 중앙값이 미설치 0.1014 대 정상 0.0570 으로
**1.8배** 다르다.

**A04 수치를 성능 근거로 쓰면 안 된다.** 크롭 크기만으로 거의 완벽히 갈리는
집합이다. 다만 임계를 test 에서 고른 **oracle 상한**이고 미설치가 **클립 2개**뿐이다.

A21 은 면적비가 미설치 0.1687 대 정상 0.1823 으로 **겹치고**(오히려 정상이 크다),
면적 baseline 이 J 0.306 에 그친다.

### 한계

- **oracle ROI.** 구역이 주어졌을 때의 조건부 값이다.
- **development set.** 합격 선언에 쓸 수 없다 (`eval_protocol.md` 4.4).
- **표본이 매우 불균형하다.** A04 미설치 12구역/**2클립**, A21 정상 12구역/**2클립**.
  A04 의 "적발 0.0%" 와 A21 의 "오경보 0.0%" 는 클립 2개 위에 서 있다.
- **프롬프트 1개, seed 1회.** 프롬프트 민감도를 재지 않았다.
- 판별 요소가 실질 **1개**로 줄었다 (위 중간 난간대 절).

구조물을 타이트하게 잡은 정상 박스다. **스케일과 구조가 함께 다르다.**

| | 507 (학습) | 71407 A18 | 71407 A26 |
|---|---|---|---|
| 난간 면적비 | 0.058 | 0.26 | **0.45 ~ 0.77** |
| 장면 | 실외 비계에 길게 붙은 난간대 | 실내 개구부 사각 난간 (근접) | 실내 개구부 사각 난간 (광각·대형) |

예측을 눈으로 확인하면 A18 의 소형 난간은 conf 0.95 로 정확히 잡는 반면, A26 에서는
아무것도 출력하지 않거나 난간 일부를 `worker` 로 오인한다.

### 스케일 인과 진단 — 스케일을 맞춰도 충분하지 않다

"화면을 뒤덮는 스케일이 원인" 이라는 가설을 증강을 건드리기 전에 검증했다.
`scripts/scale_probe_71407.py` 로 A26 이미지를 s 배 축소해 회색 캔버스 가운데 붙이고
정답 박스도 같이 변환했다. 장면 내용은 그대로다. 다만 이 변환은 객체 크기 외에
**위치(중앙 정렬), 회색 여백, 재표본화**도 함께 바꾸므로 "스케일만 분리했다" 고는
말할 수 없다. 스케일이 지배적인 변화라는 정도로 읽어야 한다.

| 배율 s | 난간 면적비 중앙값 | fold0 mAP50 | fold1 mAP50 |
|---|---:|---:|---:|
| 1.00 (원본) | 0.464 | 0.0031 | 0.0057 |
| 0.60 | 0.167 | **0.0750** | 0.0465 |
| 0.36 | **0.060** | 0.0286 | **0.0543** |
| 0.25 | 0.029 | 0.0198 | 0.0463 |

(507 학습 데이터의 난간 면적비 중앙값은 0.058 이다. s=0.36 이 그 분포와 거의 같다.)

스케일을 맞추면 **원본 대비 10~24배** 오른다. 스케일의 인과 효과 자체는 작지 않다.
그러나 **절대값이 0.075 를 넘지 못한다.** 내부 test(0.47~0.66)는 물론 같은 데이터셋의
A18(0.32~0.39)에도 한참 못 미치고 recall 은 전 구간 0.06~0.16 이라 실무적으로는
여전히 못 쓰는 수준이다.

따라서 결론은 **"스케일 정렬만으로는 충분하지 않다"** 이다. `scale` 증강 확대가
무의미하다는 뜻이 아니라, 그것만으로는 해결되지 않고 구조·배경 도메인 시프트가
남는다는 뜻이다. 남은 차이는 구조(실외 비계에 길게 붙은 난간대 대 실내 개구부를
둘러싼 사각 파이프 난간), 배경, 조명, 카메라다.

> **폴드 순위가 뒤집힌다.** 내부 test 에서 fold2 는 0.6203 으로 2등이었으나 외부에서는
> 0.0712 다. 내부 지표로 폴드를 고르면 외부 일반화가 가장 나쁜 것을 고를 수 있다.

`WO-06` 이 라벨된 4,041 프레임이 전부 현장 A03 한 곳이라 내부 홀드아웃이 성립하지

가중치 `D:/yolo/hook/runs/all_train/weights/best.pt`.

> **이 2클래스 모델은 폐기했다.** `WO-06` 은 고리가 아니라 작업자 몸통, `UA-01` 은
> 전신이어서 같은 사람의 중첩 박스를 두 벌로 검출하고 있었고, 클래스명
> (`hook_unfastened`)이 라벨에 없는 상태 정보를 주장했다.
> `hook_stage1`(단일 클래스 `worker`)로 재정의해 다시 학습했다 — 4.2절.

**보고할 성능 수치가 없다.** 학습 종료 시점의 mAP50 0.995 는 `data.yaml` 의 val 이
train 을 가리키는 자기평가값이며, 4,041장을 100 epoch 외운 결과다. 외부 검증셋을
확보해야 실제 성능을 알 수 있다 (`docs/data_plan.md` 8절).

### 4.1 진단 — 데이터에 체결/미체결을 가를 근거가 없다

`scripts/hook_probe.py`. 로그 `outputs/hook_probe.log`.

**1단계, 라벨만.** 공통 UA 15,934 프레임의 구성이다.

| 프레임 | 라벨 |
|---|---|
| 4,042 | `UA-01` 1개 + `WO-06` 1개 (우리 학습셋) |
| 11,892 | `UA-02`/`WO-05` 4,056 · `UA-03`/`WO-07` 4,009 · `UA-04`/`WO-04` 2,942 (안전모 미착용 등 다른 불안전행동) |

시나리오마다 **프레임당 정확히 1개**씩 붙고 서로 겹치지 않는다. 그리고 **공통
파티션에는 작업자 클래스 `WO-01` 이 0건**이다. 공통 WS 2,664 프레임에는 우리가 보는
클래스 라벨이 아예 없다.

**2단계, COCO person 으로 작업자를 센다.** `WO-01` 이 없어 라벨로는 "표시되지 않은
작업자" 를 셀 수 없으므로 사전학습 모델로 셌다 (각 300 프레임 표본).

| 집합 | 사람 수 | `UA-01` 박스로 덮인 사람 | hook 모델 검출 / 사람 |
|---|---|---|---|
| `WO-06` 있는 프레임 | 298 (프레임당 0.99) | **100%** | 1.01배 (사람과 겹침 98% / 80%) |
| `WO-06` 없는 UA 프레임 | 297 (프레임당 0.99) | 0% | 0.33~0.48배 (겹침 71~95%) |

**결론 1 — 대조군이 존재하지 않는다.** 학습 프레임에는 사람이 딱 한 명이고
그 한 명이 곧 정답이다. "같은 장면에 있는 체결된 작업자" 가 단 한 명도 없으므로
**이 데이터로는 체결/미체결을 가르는 것을 배울 수 없다.** 원리적 한계이며 라벨링
방식이나 모델을 바꿔서 해결되지 않는다.

**결론 2 — 그렇다고 순수 사람 탐지기는 아니다.** 다른 불안전행동 프레임에서는
사람의 33~48% 에서만 발화한다. 순수 사람 탐지기면 1.0배에 가까워야 한다.
다만 **무엇에 반응하는지는 특정할 수 없다.** 그 프레임들은 시나리오·세션·카메라가
달라 체결 여부가 아니라 촬영 조건 차이에 반응했을 수 있고, 애초에 그 작업자들이
체결 상태라는 보장도 없다 (안전모 미착용 시나리오다).

> 따라서 **체결 여부는 507 안에서 해결할 수 없다.** 다만 이것은 탐지의 과제가
> 아니다. 프로젝트 설계상 체결 판단은 VLM 이 맡는다 (README 5절). 탐지가 책임질
> 것은 "VLM 이 볼 곳" 을 정확히 잘라 주는 것뿐이고, 위 표의 1.01배·97.7% 겹침은
> **그 역할은 이미 잘 하고 있다** 는 뜻이다.

### 4.2 재정의 — `hook_stage1`, VLM 입력 크롭 제공

고리를 YOLO 로 직접 탐지하는 경로를 검토했으나 **크기 때문에 성립하지 않는다.**
원본 1920×1080 에서 고리를 눈금자로 재보니 약 18~25 px 이고, imgsz 640 에서는
6~8 px 다. 반면 전신 박스(중앙값 168×491 px)를 잘라 640 으로 키우면 1.30 배가 되어
23~33 px, VLM 입력을 896 으로 올리면 33~46 px 가 된다. 몸통 박스(109×286)로 좁히면
2.24 배까지 오르지만 앵커가 잘린다. 표는 `docs/data_plan.md` 5절.

그래서 타겟을 다음으로 바꿨다.

| 항목 | 이전 (`hook`) | 지금 (`hook_stage1`) |
|---|---|---|
| 클래스 | `hook_unfastened`(몸통) + `worker_unfastened`(전신) | `worker` 하나 |
| 소스 | `WO-06` + `UA-01` | `UA-01` (전신) |
| 이름이 주장하는 것 | 체결 여부 (라벨에 없는 정보) | 관측된 물체 |
| 역할 | 불명확 | VLM 입력 크롭 제공 |

전신을 고른 이유는 4.1절 실측이다 — 사람과의 겹침이 전신 97.7%, 몸통 80.3% 였고,
체결 여부를 보려면 고리가 걸릴 앵커까지 크롭에 들어와야 한다.

가중치 `D:/yolo/hook_stage1/runs/all_train/weights/best.pt`. 4,042장으로 100 epoch,
3.673시간. 여전히 홀드아웃이 없으므로 **보고할 성능 수치는 없다** (자기평가
mAP50 0.995 / mAP50-95 0.973 은 학습셋을 그대로 잰 값이다).

### 4.3 크롭 제공자로서의 동작 확인

`scripts/hook_probe.py` 를 재정의한 모델로 다시 돌렸다 (각 200 프레임).

| 집합 | COCO person | `worker` 검출 / 사람 | 사람과 겹침 |
|---|---:|---:|---:|
| 학습 분포 (`WO-06` 있는 프레임) | 200명 (프레임당 1.00) | **1.01배** | **98.0%** |
| 다른 UA 시나리오 | 203명 (프레임당 1.01) | 0.14배 | 96.6% |

**학습 분포 안에서는 목적을 정확히 달성한다** — 작업자 한 명당 박스 하나, 겹침 98%.
크롭 제공자로 쓰기에 부족함이 없다.

**그러나 학습 분포 밖에서는 작업자의 14% 만 잡는다.** 2클래스 모델의 0.33배보다
더 떨어졌다. 일반 작업자 탐지기가 아니라 **A03 의 그 촬영 조건에 붙은 탐지기**라는
뜻이다. 현장 하나로 학습했으니 예상된 결과다.

> **여기서 따져 볼 것이 하나 생긴다.** 같은 표에서 **COCO 사전학습 모델이 이미
> 프레임당 1.00명을 잡고 있고, 정답(`UA-01`)이 그 사람들을 100% 덮는다.**
> 즉 VLM 에 넘길 크롭은 사전학습 person 탐지기만으로도 만들어진다. 우리가 학습한
> 모델의 우위는 "건설현장 특화" 여야 하는데 현장이 하나뿐이라 그것을 보일 수 없다.
> 1단계를 COCO person 으로 대체할지 비교해 볼 가치가 있다. 그렇게 되면 hook 쪽
> 학습은 아예 필요 없어진다.

### 4.4 1단계 비교 — COCO person 이 이긴다. hook_stage1 을 버린다

4.3 의 비교는 순환이었다. COCO person 을 "사람이 몇 명인가" 의 **기준자**로 썼기
때문에 COCO 자신의 회수율을 잴 수 없었다. 그래서 정답을 사람이 라벨한 박스로
바꿔 다시 쟀다.

정답은 **비계작업 파티션의 `WO-01`(작업자)** 이다. 현장이 11곳이고, hook_stage1 은
공통 UA 의 현장 **A03 한 곳**으로만 학습했으므로 나머지가 곧 학습 분포 밖이다.
현장당 최대 150프레임을 등간격으로 뽑았다 (`scripts/stage1_recall.py`,
로그 `outputs/stage1_recall.log`). 지표는 **회수율**이다 — 크롭 제공이 목적이면
작업자를 놓치지 않는 것이 전부다.

| 현장 | 정답 | COCO person @0.5 | hook_stage1 @0.5 |
|---|---:|---:|---:|
| A03 *(학습 현장)* | 150 | 99.3% | 100.0% |
| A01 | 150 | 70.0% | 4.7% |
| A04 | 150 | **92.7%** | 4.7% |
| A08 | 150 | 98.0% | 12.7% |
| A10 | 150 | 82.0% | 0.0% |
| A15 | 150 | 96.0% | 73.3% |
| A16 | 126 | 96.8% | 52.4% |
| A17 | 150 | 96.7% | 25.3% |
| A19 | 150 | 94.7% | 85.3% |
| A21 | 150 | 92.7% | 39.3% |
| **학습 분포 밖 합계** | **1,326** | **91.0%** | **32.7%** |

(IoU >= 0.5. conf 0.25 에서도 순위와 폭이 같다 — 93.0% 대 36.3%.)

**결론: 1단계를 COCO 사전학습 person 으로 대체한다.**

- 학습 현장에서는 **무승부**다 (99.3% 대 100.0%). hook_stage1 의 우위는 소수점이고,
  4,042장을 100 epoch 외운 대가로 얻은 것이다 (3.673시간).
- 학습 분포 밖에서는 **2.8배 차이**다 (91.0% 대 32.7%). hook_stage1 은 A10 에서
  0.0%, A01/A04 에서 5% 아래로 떨어진다. 반면 COCO 는 최악의 현장(A01)에서도 70%,
  9개 현장 중 7곳에서 92% 이상이다.
- 즉 hook_stage1 은 작업자 탐지기가 아니라 **A03 의 촬영 조건 탐지기**다.
  현장 하나로 학습했으니 원리적으로 예상된 결과이고, 데이터를 더 넣기 전에는
  고쳐지지 않는다. 그리고 507 에 안전고리 현장은 A03 하나뿐이다 (`data_plan.md` 5절).

> **정밀도는 재지 않았고, 재서도 안 된다.** 이 파티션은 프레임당 `WO-01` 이 약
> 1개라 화면의 모든 작업자가 라벨된 것인지 알 수 없다. 라벨 없는 작업자를 잡은
> 검출을 오검출로 셀 수 없으므로 정밀도는 정의되지 않는다. 회수율은 정답 박스만
> 있으면 정의된다. **다만 이것은 "COCO 가 헛박스를 안 낸다" 는 뜻이 아니다** —
> 파이프라인에서 사람 아닌 크롭이 VLM 에 넘어가는 비율은 아직 모른다.
> VLM 을 붙인 뒤 그쪽 출력으로 재는 것이 맞다.

**따라야 하는 변경**

- `hook_stage1` 학습 라인은 폐기한다. `D:/yolo/hook_stage1/` (와 이미 폐기된
  `D:/yolo/hook/`)은 재현용 기록 외에 쓸 데가 없다.
- `configs/data/targets.yaml` 의 `hook_stage1` 타겟은 남겨 두되 **학습용이 아니라
  평가용**으로만 읽어야 한다. 지우지는 않는다 — 위 비교의 재현에 필요하다.
- 안전고리 파이프라인은 이제 **COCO person 크롭 -> VLM** 두 단계다. 탐지 쪽에서
  남은 작업은 크롭 범위(전신 대 몸통) 결정뿐이고, 그것은 VLM 을 붙여야 정해진다.
- 학습 자원 전부를 `guardrail` 로 돌린다. 그쪽은 주 클래스 AP 가 0.365 다.
