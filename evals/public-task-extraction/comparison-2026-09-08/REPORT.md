이번 짧은 원문 추출 실험에서는 **Terra low를 다음 검증의 우선 후보**로 둘 만하다. 기존 자동 점검에서 Sol low와 같은 34/35건을 통과했고, 관측한 CLI 응답시간도 짧았다. 다만 담당자 오지정처럼 점수가 놓친 문제가 있어, 자동 DB 수정에 사용할 수준이 입증된 것은 아니다. Sol로 올리는 것만으로 모든 문제가 해결되지도 않았다.

추가로 Luna medium의 026은 개발 상황을 배포 진행 업무로 표현했고, Sol의 022는 요약에서 담당자가 미확인이라고 하면서 담당자 필드에는 값을 넣었다. 035의 중복 관계를 별도의 추적·분류 업무로 출력하는 현상도 여러 모델에서 확인했다. 관계 사실을 업무 생성으로 연결할지에 대한 스키마 규칙이 필요하다. 상세 기록은 `manual-review.json`에 남겼으며 이 관찰로 기존 점수를 사후 변경하지 않았다.

048은 첫 발췌의 예상시간 섹션 제목이 빠져 있다. 기존 라벨은 두 값을 같은 업무의 상충 추정치로 기대하지만, 모델이 받은 텍스트만으로는 이를 확정하기 어렵다. **이번 새 모델 출력 확인 전에** `plan.json`에 보조 점수 제외를 선언했다. 원문·기존 라벨·기존 점수는 유지했다. 향후 원문 주변 문맥을 그대로 추가한 별도 데이터 버전을 만들어야 한다.

## 비교 조건과 검증

- 기존 Luna low 35응답 재사용 + Luna medium·Terra low·Sol low 각 35건 새 실행 = 총 140응답 비교, 신규 호출 105회.
- 공개 원문 데이터 50건 중 같은 개발용 35건을 사용. 보류 평가용 15건은 이번에도 실행하지 않았다.
- API 키 없이 기존 ChatGPT 로그인으로 Codex CLI 0.145.0 실행. API 키 환경변수는 제거했다.
- 사례마다 독립된 일회성 세션 사용. 새 실행은 설정별 순차 진행, 각 설정 안에서는 최대 3건 동시 실행.
- 원문, 사례별 입력 프롬프트, 출력 스키마, 채점 기준의 해시가 네 설정 모두 동일함을 검증했다. 원문 수정·합성 사례 추가 없음.
- 모델에는 원문·수집 시점 제목·작성자·시간·null인 과거 상태만 제공. 정답 라벨은 제공하지 않았다. 수집 시점 제목을 과거 시점의 확정 사실로 취급하지 않도록 안내했다.
- 도구 실행을 비활성화했고 모든 응답에서 도구 호출 0건을 확인했다. 실제 업무 생성·수정·배포는 수행하지 않았다.
- 140응답 모두 스키마 검증 통과. 원본 데이터 무결성 검사와 기존 Luna low manifest 검사도 통과했다. 원격 원문 재수집 검사는 이번에 다시 실행하지 않았다.
- 모델명은 CLI에 요청한 식별자다. 서버 내부 모델 리비전의 독립 확인은 하지 않았다.

토큰은 CLI가 보고한 값을 그대로 기록했다. 캐시 입력은 입력의 부분집합이며, 추론 출력도 출력과 별도 합산해 비용을 추정하지 않는다. 추론 출력 0이라는 계측값이 해당 모델이 추론하지 않았음을 입증하는 것은 아니다.

사용자 프롬프트가 같아도 모델별 Codex 내부 지침·처리 등의 차이로 입력 토큰 수가 달랐다. 이 실험은 Codex 환경에서의 모델 설정 비교이며 순수 API 모델만 분리한 실험이 아니다. 지연시간에는 CLI 시작, 네트워크와 스키마 처리 등이 포함된다. 캐시 적중량과 실행 시점도 달라 API 속도·요금으로 환산할 수 없다.

신규 실행 전후 계정 사용량 스냅샷은 단기 8% → 35%, 주간 17% → 22%였다. 이 대화와 계정의 다른 활동까지 포함하는 수치이며 모델별 비용은 아니다.

## 다음 선택

**다음 개발 실험의 기본 후보는 Terra low**로 두되, 담당자 근거·기존 업무 ID 매칭·최신 상태 통합 규칙을 명확히 하는 것이 먼저다. Luna low를 바로 자동 수정에 붙이기에는 이번에 확인된 시간 중복 배정과 조건 필드 오류가 걸린다. Luna medium에서 일부 개선은 있었지만 누락과 불필요한 확인도 남았다. Sol low는 일부 근거 처리에서 나았으나 이번 결과만으로 전체를 Sol로 전환할 이유는 충분하지 않다.

이 자료만으로 업무 누락률·중복 생성률·다른 업무 수정률·잘못된 완료 처리율을 산출할 수 없다. 과거 업무 목록과 실제 변경 대상 ID, 담당자 권한 정보가 모두 없고, 장문 문서나 긴 대화도 평가하지 않았다. 공개 자료가 사전 학습에 포함되었을 가능성과 소표본·단회 실행의 한계도 있다.

사람이 원문과 정답을 검토하고, 실제 이전 업무 목록과 기대 변경 결과가 있는 사례를 추가해야 한다. 수정한 프롬프트·스키마는 별도 버전으로 관리한 뒤 개발용 사례에서 확인하고, 기준이 고정되면 보류 15건을 처음 평가한다. 업무 자동 반영 여부는 모델이 해석한 사실과 실제 DB 변경 대상을 함께 검증한 뒤 판단한다.

## 재확인용 파일

- `comparison.json`: 네 설정의 집계, 사례별 실패 점검과 결과 파일 경로.
- `manual-review.json`: 자동 점수에 넣지 않은 원문 대조 메모.
- `account-usage.json`: 계정 전체 사용량 스냅샷.
- `plan.json`: 실행 전 선언한 비교 조건과 048 제외 방침.
- `compare.py`: 기존 결과를 읽어 동일 입력·무결성을 확인하고 집계하는 스크립트. 모델을 호출하지 않는다.
- 각 설정의 형제 디렉터리: `results/`, `scores.json`, `run.py`, `score.py`, `prompt.md`, `schema.json`, `rubric.json`.
