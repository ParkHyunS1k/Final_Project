# 입·출력 형식을 보완한 Luna low 평가

**형식 보완만으로 핵심 구조화 오류는 줄었지만 전체 점수 우위는 생기지 않았다.**
GPT-5.6 Luna / reasoning effort `low`로 기존 개발용 35건을 한 번씩 새로 실행했다.
35건 모두 새 JSON 스키마를 통과했고 도구 호출은 0건이었다. 기존 Luna low와 비교하면
사례 전체 통과는 동일한 32/35, 개별 점검은 173/177에서 174/177로 1개 늘었다.

이 수치는 동결한 잠정 점검의 결과이지 사람 검증 정확도가 아니다. 보류 평가용 15건은
이번에도 실행하지 않았다.

## 무엇을 바꿨나

- 입력을 `thread`, 명시적 excerpt index·source kind, `known_context`로 구분했다.
- PM-REAL-048에는 수집 당시와 SHA-256이 같은 공개 원문의 바로 앞 제목
  `### 예상 소요 시간`을 복원했다. 정답 라벨이나 해석은 입력하지 않았다.
- 공수를 업무 항목에서 분리해 `effort_mentions`에 한 번만 기록하고, 단일 업무·업무 묶음·
  전체 이슈·불명 범위를 명시하게 했다.
- 조건을 `modality=conditional`과 `condition_ko`로 함께 보존하게 했다.
- 같은 업무의 과거·최신 보고는 최신 상태 한 항목으로 합치고, 관계 사실은 업무로 만들지
  않으며, 작성자를 자동으로 담당자로 간주하지 않게 했다.
- 출력 필드 의미는 JSON Schema description에 두고 프롬프트에는 판단 규칙만 남겼다.

공식 문서상 `gpt-5.6-luna`는 low reasoning과 Structured Outputs를 지원한다.
<https://developers.openai.com/api/docs/models/gpt-5.6-luna>

## 자동 검사 비교

| 항목 | 기존 Luna low | 형식 보완 Luna low |
|---|---:|---:|
| 정상 실행 및 스키마 검증 | 35/35 | 35/35 |
| 선택한 점검 전체 통과 사례 | 32/35 | 32/35 |
| 개별 점검 통과 | 173/177 | 174/177 |
| 모델 도구 호출 | 0 | 0 |
| CLI 응답시간 중앙값 | 9.007초 | 8.029초 |
| 입력 토큰 | 275,228 | 357,659 |
| 출력 토큰 | 10,759 | 8,928 |
| 추론 출력 토큰 | 3,544 | 3,007 |

새 형식은 관측된 중앙값이 약 11% 짧고 출력 토큰이 약 17% 적었지만 입력 토큰은 약 30%
늘었다. 실행 시점과 캐시 입력량이 달라 이 차이를 형식 변경의 인과 효과나 API 비용으로
해석하면 안 된다. CLI 시작과 Codex 내부 지침 비용도 포함된다.

조건 필드와 공수 범위 필드의 조합을 전수 검사했으며 35건에서 내부 형식 모순은 없었다.

## 남은 실패와 새 위험

자동 점검 실패는 PM-REAL-012, 024, 041이다.

- PM-REAL-012: 기능 업무는 `completed`로 맞췄지만 전체 이슈 완료 여부를 `null`로 뒀다.
  기존 잠정 기준은 `true`다. 잘못된 완료 처리 위험은 줄지만 자동 종료 recall도 낮아진다.
- PM-REAL-024: 최신 상태를 하나로 합친 것은 개선이지만, 뒤의 “완료”를 전체 이슈 완료로
  확정하지 않아 `null`이다. 기존 잠정 기준은 `true`다.
- PM-REAL-041: 체크되지 않은 구현 요구사항을 업무로는 추출했지만 상태를 `planned`가 아닌
  `unknown`으로 냈다.

자동 점수가 잡지 못한 회귀도 있다. PM-REAL-046은 “디자인 수정 완료 시”를 선행 조건으로
읽어야 하는데 디자인 수정 자체를 `completed`로 잘못 확정했다. PM-REAL-047은 “새로운 책
추가 시 스티커 부착”을 조건부 상시 규칙이 아니라 일반 asserted 계획으로 표현했다. 따라서
조건 필드를 추가한 것만으로 조건 해석이 안정됐다고 볼 수 없다.

전체 완료 값은 기존의 여러 `false`가 새 출력에서 `null`로 바뀌었다. 이는 제공된 짧은
발췌만으로 전체 미완료를 단정하지 않는 보수적 변화지만, 현재 점검의 `completion_not_true`는
둘을 같은 통과로 취급하므로 별도 recall 평가는 하지 못한다.

## 결론

입·출력 형식 보완은 **Luna low의 알려진 고위험 오류를 실제로 줄였다.** 특히 공수 중복,
조건 필드 불일치, 작성자 오지정, 관계의 업무화에는 효과가 있었다. 그러나 사례 전체 통과는
늘지 않았고 완료 판정 recall과 일부 조건 해석이 나빠졌다. 따라서 Luna low를 무검토 자동
DB 수정에 연결할 근거는 아직 없다.

다음 단계는 이 결과를 유지한 채 같은 새 형식으로 Luna medium을 실행하는 것이다. 그러면
형식이 고정된 상태에서 추론 강도 효과를 비교할 수 있다. PM-REAL-046·047을 포함한 수동 검토
기준을 먼저 동결하고, 보류 15건은 최종 후보가 정해질 때까지 열지 않는 편이 타당하다.

## 재현 파일

- `prompt.md`, `schema.json`: 새 지시와 출력 계약.

- `score.py`, `scores.json`: 동결한 기존 잠정 기준을 새 출력 구조에 맞춰 채점한 결과.
- `results/PM-REAL-xxx.json`: 35개 실제 응답과 입력·스키마·데이터 해시, 시간, 사용량.
- `account-usage.json`: 평가 전후 계정 전체 사용량 스냅샷.

python3 evals/public-task-extraction/luna-low-io-v2-2026-09-10/score.py
