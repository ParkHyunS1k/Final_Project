# 상태형 변경안 모델 비교 — 2026-09-11

**Luna medium과 Luna low가 가장 균형이 좋았고, Terra low는 이 과제에서 뚜렷하게 약했다.** 네 설정 모두 잘못된 완료 처리가 3~5건 남아 자동 반영에는 쓸 수 없고, 사람이 승인하는 변경안 용도로만 볼 수 있다.

기준은 **AI(Claude)가 이후 기록을 보지 않고 쓴 블라인드 라벨**이다. 사람 검토 전이므로 아래 수치는 "정확도"가 아니라 **라벨 기준과의 일치도**다. 프롬프트도 라벨 작성 기준과 같은 제품 규칙을 담고 있어, 그 규칙을 얼마나 따르는지 재는 평가다.

## 조건

- 데이터: `datasets/github-timeline-candidates-v1`의 300건 중 라벨이 제외한 47건을 뺀 **253건 전체**. 개발/보류 분할은 아직 없다.
- 입력: 원문 발췌, 기준 댓글 번호, 기준 시각 업무 목록(제목·열림/닫힘·담당자), 참여자, 댓글 이슈 ID. 라벨·이후 기록은 주지 않았다.
- 출력: JSON Schema strict. 결정(변경 제안/무작업/확인 필요)과 서비스 변경 종류(`complete`·`status`·`assignee`·`remaining`·`dueAt`·`createTask`).
- 실행: OpenAI Responses API 직접 호출, 도구 없음, `store=false`, 사례당 1회. 설정은 순차, 설정 안에서는 최대 6건 동시.
- 처음엔 Codex CLI(계정 한도)로 준비했으나 사용자 지시로 API 키 실행으로 바꿨다. 전환 전 CLI 파일럿 2건은 `pilot-codex-cli/`에 따로 보관했고 점수에 넣지 않았다. 계획과 파일 해시는 전체 실행 전에 `plan.json`에 기록했다.
- 1012회 호출 모두 성공·스키마 통과, 도구 호출 0건, 없는 업무 참조 0건.

## 원문과 응답을 대조한 발견

- **잘못된 완료가 모든 모델에 남았다.** 반복된 사례는 PR 검토 의견(GH-TL-5579658983, 3개 모델), Draft PR 제출(GH-TL-4998342964, 2개), 코드상 해소지만 설정이 휴면인 보고(GH-TL-5513963497, 2개)다. "PR만 올림"을 완료로 보는 경향이 공통이다.
- **외부 포크 PR에 지급 주소가 붙은 글(GH-TL-5572979018)을 Luna medium과 Sol low가 완료 처리했다.** 원문 신뢰도나 이상 징후는 모델이 판단하지 않으므로 서비스 쪽 검토 단계가 필요하다.
- **Luna medium은 진행 중 제안이 많다(56건 중 29건 일치).** 재현율은 가장 높지만 무작업·확인 필요 사례에 낸 변경의 대부분(25건)이 진행 중 표시다. 되돌리기 쉬운 변경이라 위험은 낮다.
- **Terra low와 Sol low는 무관한 새 업무를 만든다.** 무작업·확인 필요 사례에 새 업무를 각각 9건, 6건 제안했다. 새 업무는 삭제 제약이 있어 진행 중 표시보다 비용이 크다.
- **새 업무와 마감은 모든 모델이 약하다.** 회의록·체크리스트에서 정해진 작업을 뽑는 사례(새 업무 13개)는 최고 5개였고, 마감 3건은 Sol low만 2건 맞혔다. 라벨 수가 적어 일반화하지 않는다.
- **에이전트 작성 의심 글에서 Terra low가 크게 떨어진다(결정 일치 54.7%, 나머지 글 69.0%).** Luna·Sol은 차이가 2~9%p였다.

## 라벨 쪽 한계

네 모델이 모두 라벨과 다른 결정을 낸 사례가 34건이다. 대부분 라벨이 "확인 필요"인데 모델은 무작업(스크린샷·링크만 있는 글, "옵션 추가" 목록) 또는 변경 제안("fix하여 해결", "할인율 적용 추가했습니다")으로 판단했다. 앞선 GitHub 기록 비교에서도 이 유형이 라벨이 지나치게 엄격했을 가능성이 있는 곳으로 나왔다. **결정 일치 70%대의 상당 부분은 라벨 기준의 모호함일 수 있다.** "확인 필요→무작업"은 서비스상 변경을 만들지 않으므로 대체로 무해하다.

그 밖에:

- 라벨 작성자와 기준을 만든 쪽이 같다. 사람 라벨로 교차 확인해야 한다.
- 사례당 1회 실행이다. 같은 설정의 반복 변동은 재지 않았다.
- 보류 분할이 없다. 이 결과로 프롬프트를 고치면 이후 같은 253건 점수는 낙관적으로 편향된다.
- 입력이 1,024토큰 미만인 경우가 많아 프롬프트 캐시가 쓰이지 않았다. 비용은 캐시 없는 값이다.
- 9/8 짧은 원문 추출 비교에서는 Terra low가 우선 후보였다. 과제(기존 업무 목록에 대한 변경안)가 달라지면 순위가 뒤집힐 수 있다는 뜻이다.

## 결론

- 이 과제의 기본 후보는 **Luna low**다. Luna medium·Sol low와 통계적으로 구분되지 않으면서 비용이 가장 낮다($0.13/253건).
- 재현율이 중요하면 **Luna medium**(비용 거의 같음), 불필요한 변경을 줄이는 쪽이면 **Sol low**(비용 약 18배)가 대안이다.
- **Terra low는 이 과제에 쓰지 않는다.**
- 어느 설정도 자동 반영 수준은 아니다. 특히 "PR 제출·검토"를 완료로 보는 오류와 무관한 새 업무 생성은 프롬프트 개선 후보가 아니라 서비스의 승인 단계와 검증 규칙으로 막아야 한다.
